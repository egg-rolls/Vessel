# 标准开发流程

> 三段闭环，带反馈回路：**需求分析师**（PRD）→ **架构师**（SPEC + Epic + Issues）→ **开发者**（认领 + PR）。
> 单点修复（修 bug、加参数、小调 UI）跳过前两段，直接走 [collaboration.md](collaboration.md) 快速通道。

## 全貌

```

  ▼

┌──────────────────────────────────────────────────────────────┐

│         worktree 并行 → 开发 → PR → 审查 → 合并                │
```

## 跨阶段反馈回路

三段流程不是单向瀑布。以下回路确保阶段间信息不回丢失：

| 回路 | 触发条件 | 方向 | 动作 |
|------|---------|------|------|
| **架构合规退回** | 阶段 2 预检发现方案违反 AGENTS.md 红线/ADR/Core 冻结 | 架构师 → 售前 | 退回 PRD，标注违规项。售前修订 PRD 后重新进入阶段 2 |
| **技术可行性异议** | 开发者认领 Issue 前发现方案与 Core 约束/ADR 冲突 | 开发者 → 架构师 | 在 Issue 下留言提技术异议，不开始编码。架构师调整 SPEC/Issues 后开发者重新认领 |
| **实现修正回写** | 开发过程中发现 SPEC 接口契约需要调整 | 开发者 → 架构师 | 开发者提 SPEC 修正 Issue。架构师更新 SPEC（状态从 Approved 改为 Implemented 或标注修订日期）。SPEC 是活文档 |

**禁止跳过任何回路**。回路被跳过 → 错误在更晚阶段才发现 → 返工成本指数增长。

## 模块产物路径

每个模块在 `docs/dev/<module-name>/` 下统一管理：

```
docs/dev/<module-name>/
  ├── prd.md       ← 阶段 1 产出（12 章，含 Problem Statement、MoSCoW、NFR 五维、开放问题）
  ├── spec.md      ← 阶段 2 产出（含备选方案与权衡、Goals/Non-Goals、横切关注点、m1 切片）
  └── diagrams/    ← 复杂交互分支的 ASCII 图或用户故事地图（PRD §6 触发时）
```

`<module-name>` 在阶段 1 确定后全程不变，所有角色用同一文件夹名。Epic 和子 Issues 在 GitHub 上追踪，不放在文件夹内。

## 四条不可跳过的规则

### 1. 每个阶段的产出必须经用户确认

PRD 未经用户审阅 → 不进阶段 2。SPEC 未经用户审阅 → 不开放 Issue 认领。

**反面**：写完 PRD 就自己开始拆 SPEC、写代码。用户回头看 PRD，发现 IN/OUT 全理解错了——但代码已经写了。返工成本翻三倍。

**自问**：这个阶段的产出，用户看过并点头了吗？

### 2. 反馈回路必须走通，不可跳过

架构合规预检不过 → 必须退回 PRD，禁止"先拆着，PRD 后面再补"。开发者发现问题 → 必须提技术异议，禁止"自己猜一个实现然后 PR 被拒"。

**反面**：架构师发现 PRD 违规但觉得"改一下就行"自己脑补修正。后果：修正没经过售前确认 → 可能和 PRD 原始意图冲突 → 返工。

**自问**：这个阶段发现的问题，是回退到上游修正了，还是被下游"自行消化"了？

### 3. 模块文件夹在阶段 1 确定，全程不改名

PRD、SPEC、Epic 引用都依赖一致的文件夹名。中途改名的代价是所有引用断裂。

**反面**：阶段 1 取名 `plugin-hot-reload`，阶段 2 觉得 `dynamic-plugin` 更好——改了文件夹名，PRD 和 SPEC 的路径引用全断。

**自问**：这个模块名在三个阶段都用同一个吗？

### 4. 单点修复不走流程

修一个 bug、加一个参数、小调 UI——不需要需求分析师和架构师。直接走 Issue → PR。

**判断线**：这个改动涉及的代码，一个人能在一小时内独立完成吗？能 → 跳过阶段 1 和 2。

## 单点修复的快速通道

单点修复仍走 [collaboration.md](collaboration.md)：Issue → 认领 → PR → 审查 → 合并。分支命名、Commit 格式、审查门禁不变。
