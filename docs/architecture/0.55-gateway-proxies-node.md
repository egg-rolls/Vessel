# Gateway 代理 node（目标态）

> 用户原话：「node 和 gateway 注册后就应该由 gateway 代理访问 node，根本不要我们在 config 里写 node 的 token」。
> 本页是**目标 / 迁移态**，不是现态。现态见 [topology](topology.md) 与 [gateway](gateway.md)；落地后由 current 页承接。

## 1. 现状（为什么要改成代理）

今天 WebUI 的连接方式是「**两步直连**」：

1. 浏览器向平台发 `platform.nodes.credentials`（`packages/serve/src/platform/rpc.ts`）拿到该 node 的 token；
2. 浏览器**直接**连 node 的 `apiUrl`——HTTP 走 node 的 `/`，事件流走 node 的 `/ws`。

平台只承担「目录 + 发凭据」。这套形状带来四个结构性代价：

| 代价 | 具体表现 |
|---|---|
| 凭据外发 | node token 必须交到最不可信的执行环境（浏览器内存 / 扩展 / devtools）；泄露即直进 node |
| 暴露面翻倍 | 每个 node 都得能被浏览器直连：CSP `connect-src` 逐 node 开洞、跨机部署每台 node 各自暴露 TLS/证书/OIDC |
| 记账分散 | `gateway.ws.closed` 与背压计数只存在于 node 侧，平台看不到「谁在慢、谁在掉」 |
| 收口失败 | 「node 只监听回环」这个理想态与「浏览器直连 node」互斥；一旦收口就没人能连 |

0.56 的根密钥派生解决了「**用户不用手写 token**」，但没有解决「**浏览器要拿到 token**」——凭据仍然要外发。代理解决的是后半段。

## 2. 目标态

**一个入口**：浏览器与 CLI 一律只连平台 gateway；node 的 HTTP 与 WS 全部由平台按会话代理。node token 只存在于平台进程内，**永不下发到浏览器**。

```
before:  browser ──credentials──▶ platform        browser ──Bearer node token──▶ node (HTTP+WS)
after:   browser ──platform session──▶ platform ──Bearer node token──▶ node (HTTP+WS)
```

- 平台的 `resolveNodeCredential` 变成**内部**函数：只被代理层调用，不进任何响应体；
- 平台同时成为唯一的鉴权点、记账点、限流点；
- node 可以退回到「只监听 loopback」或「只允许平台源地址」。

### 2.1 HTTP 代理

- 路由：`/nodes/:nodeId/<path>` → `<node apiUrl>/<path>`（仅剥前缀，不改其余路径/查询）。
- 请求头：剔除逐跳头（`connection`、`keep-alive`、`transfer-encoding`、`upgrade`、`proxy-*`、`te`、`trailer`）；`Authorization` 由平台**覆写**为 node token（浏览器带来的任何凭据一律丢弃，防混淆代理）。
- 响应头：同上剔除逐跳；`set-cookie` 直接透传会造成平台域下种 node cookie，**默认剥掉**（node 不需要 cookie 语义）。
- 流式：请求/响应都按流转发，不整体缓冲（否则又是「大文件打爆内存」）。
- `Upgrade: websocket` 一律 400 —— WS 只走 `2.2` 这条有记账的通道。

### 2.2 WS 代理

- 路由：`/nodes/:nodeId/ws` → `<node>/ws`；平台侧带 Bearer（node token），浏览器侧只带平台会话。
- **双端状态机**，两端各自独立判活：
  - 心跳：平台**自己**向两端发 ping（不改用浏览器心跳——浏览器标签页休眠会伪造「上游已死」）；
  - 半开：任一端 `pong` 超时（默认 60s，间隔 25s）→ 双向关闭并记账，这不是「对端断了」，而是「平台判定它断了」；
  - close 传播：下游 close → 上游 close（带同一 code 语义）；上游异常断开 → 下游 `1011`/`1006` 映射，**不让浏览器看到半死连接**。
- 背压：双向都按 `bufferedAmount` 水位（高 1 MiB / 低 256 KiB）暂停读取对端；**绝不无界缓冲**——超硬阈值（8 MiB）直接 `1013` 关闭并记 `reason=backpressure_overflow`。
- 记账（平台侧，唯一入库口径）：`gateway.ws.closed { node_id, session_id, who: 'downstream'|'upstream'|'platform', code, reason, duration_ms, frames_in, frames_out, bytes_in, bytes_out, backpressure_pauses, heartbeat_misses }`。node 侧原有记账保留，但降级为「上游视角」，不再入库（避免双写对账翻倍）。

## 3. 六个必须先裁决的问题

### 3.1 `platform.nodes.credentials`：删还是退化成 CLI 专用？

**裁决：退化成 CLI / 本地自动化专用（`mode === 'token'` 才可取），浏览器直连路径作废。**

- 理由：代理接管 browser→node 后，下发 node token 只剩一个后果——把长期凭据交给浏览器。而 CLI（`vessel --connect`、`doctor --deep`、federation 脚本）确实需要它。
- 迁移顺序：先上代理 → 双轨一个版本 → 观察 `gateway.ws.closed` 里是否还有 `via=direct`（应归零）→ 删浏览器路径。**先删后加必定锁死一次**（0.55 的事故形状）。
- 退化成 CLI 专用时，`vessel token show --purpose node --node <id>` 仍是本机对账手段（只回环 + 交互式才打印值）。

### 3.2 代理额外一跳的延迟预算

不写预算就等于没有预算。判据（同机 loopback，不含 node 处理时间）：

| 指标 | 目标 |
|---|---|
| p50 额外延迟 | < 1 ms |
| p99 额外延迟 | < 5 ms |
| 跨机同区域 p99 | < 10 ms |
| 上游 HTTP 超时 | 30 s（流式响应不受限） |
| WS 握手超时 | 10 s |
| 心跳间隔 / 判死 | 25 s / 60 s |

超出预算的常见原因只有一个：**把流做成了缓冲**（整体读再写）。流式实现下这组数字是平凡的。

### 3.3 鉴权模型（用户会话 → 允许代理哪些方法）

- 会话 principal：`{ sub, role: owner|member|guest, node_scope: nodeId[] }`，由平台 token（未来 OIDC）解析。
- 方法白名单**在平台侧**判定，而且判定的是**方法名**，不是路径：
  - 默认放行：读类（`*.list` / `*.get` / `health.*` / `timeline.*` / `sessions.*` 的读侧）与用户自己的写（`messages.create`）；
  - 默认拒绝：会改变进程生死的（`*.shutdown`、`*.update`、`gateway.install-service`）与跨成员的写（`agents.rotate/close`），除非 `role=owner`；
  - `node_scope` 之外的 node → 一律 403（不要把 404 当保护，那就成了可枚举性探测）。
- 未知方法：**默认拒绝并记账**（fail-closed），而不是「不认识就透传」。

### 3.4 WS 背压 / 半开 / 心跳与统计汇总

见 §2.2。汇总口径三条硬约束：

1. 平台侧是唯一入库口径（`gateway.ws.closed` 只写一次）；
2. `who` 必填：区分「浏览器走了」「node 崩了」「平台主动关」——没有这个字段，掉线永远归因不了；
3. 背压事件必须计数（`backpressure_pauses`），否则「慢客户端」与「node 慢」在数据上无法区分。

### 3.5 多节点选择（`node_id` 缺省规则）

优先级（**唯一规则，不许再加隐式回退**）：

1. 请求里显式 `node_id`；
2. 会话已绑定的 node（`sessions.create` 时确定）；
3. 部署里**恰好一个** node → 用它（G1 兼容）；
4. 其余情况 → `node_required`（400），并列出候选 `node_id`。

**绝不**按名字模糊匹配、绝不「最近用过的」。理由：一旦有隐式就近，加第二个节点的那天必然出现「请求打到错节点」，而且症状是「有时候不对」，最难查。

### 3.6 失败与降级

- node 不可达 → `502` + `node_unreachable`，同时记 `node.health` 事件；**写操作不重试**（幂等未知即不重试），幂等读最多重试一次。
- 代理自身超时 → `504` + `node_timeout`，与 `node_unreachable` 分开记账（排障方向完全不同）。

## 4. 风险清单

| # | 风险 | 判据 / 缓解 |
|---|---|---|
| 1 | **CSP/Origin 收紧后旧前端全挂** | 代理后静态资源与 RPC 同源，`connect-src` 应从「逐 node origin」收回 `'self'`；没有这条，要么全拦要么全放 |
| 2 | **WS 背压被做成无界缓冲** | 慢客户端把平台内存吃光（OOM 比掉线严重）；必须有水位 + 硬阈值关闭 |
| 3 | **两份记账对账翻倍** | 平台与 node 都写 `gateway.ws.closed` ⇒ 统计/计费翻倍；先定唯一入库口径再动代码 |
| 4 | **凭据寿命变长** | node token 从「浏览器内存」变成「平台常驻」；限定 `resolveNodeCredential` 的调用点、不落盘、不进日志 |
| 5 | **代理只是加法不是收口** | node 若仍对外监听非回环，攻击面没减少；目标态要求 node 默认只听 loopback（或仅平台源可达） |
| 6 | **`node_id` 默认规则的粘性** | 「只有一个就默认用它」在加点当天变成错路由；必须「多节点即硬失败」 |
| 7 | **cookie / 逐跳头穿透** | 平台域下种 node cookie、`transfer-encoding` 双重编码导致响应截断 |

### 最容易做错的一处

**把 WS 代理写成「两个 socket 互相 `onmessage` 转发」就收工。** 它没有半开检测、没有背压、close 语义也不对称；表面上「能跑」，但在慢客户端或网络抖动时表现为**随机掉线 + 内存上涨**，且没有任何 counter 能定位。

判据（三条都满足才算实现）：① 平台侧自己打心跳并记 `heartbeat_misses`；② 双向水位 + 硬阈值关闭；③ 每次关闭都落 `gateway.ws.closed`（含 `who` 与时长）。

## 5. 与 0.56 根密钥派生的关系

- 派生 token 解决「**用户不用手写**」：一个 root（`<dataDir>/root-secret`）→ `vessel:platform` / `vessel:hub` / `vessel:node:<id>` / `vessel:proxy:<id>`，显式配置永远优先；
- 代理解决「**浏览器不用直连**」；
- 两者叠加后，node token 只在平台进程内出现，且**没有一份需要用户抄写**。
- 过渡期兼容：`platform.nodes.credentials` 保留的 CLI 专用路径，其返回的 token 可以是派生值（`source: derived`）——显式配置的 node token 仍原样返回。

## 6. 明确不做（本阶段）

- **node→platform 的回连隧道**：先做「平台主动连 node」。回连隧道要处理重连风暴、双向鉴权、nat 穿透，收益是省一次端口开放，不划算。
- **跨 hub 的代理链**：federation 仍由 hub 目录 + 节点直连承担，代理只解决「本平台 ↔ 本地/远程 node」。
- **代理层的协议翻译**：只做透传 + 白名单，不做 node 方法名改写（改写会让「平台视角」与「node 视角」出现两套语义）。
