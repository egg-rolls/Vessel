# 统一 RPC 方法表
<a id="rpc-methods"></a>
- **0.49 入口**：本文方法表属 **Node API**，入口 `POST /v1/rpc`（node 端口，缺省 8644）。Platform Gateway 的 `POST /platform/rpc` 是独立 allowlist（5 个只读 `platform.nodes.list|get|credentials`、`platform.whoami`、`platform.health.get` + `gateway.shutdown` 唯一非只读，Q4-C additive；平台入口走平台自己的门控，见下方 `gateway.shutdown` 条），**不复用**本表、不透传到 node dispatcher。G3：`platform.nodes.credentials({ node_id? })` 在注册多个节点时省略 `node_id` → HTTP 400 `invalid_params`；本地多 node 由 `vessel gateway nodes list|add|remove` 维护 `nodes.json`，`vessel node start --config <path>` 用独立配置启动。`platform.*` 方法不进 canonical 表；`gateway.shutdown` 与 node 侧同名，但平台入口的受理/门控独立（非回环三门控见 [GATEWAY](../operations/GATEWAY.md)）。
- **信封**：请求 `{ v: 1, id, method, params? }`；成功 `{ v: 1, id, ok: true, result }`；失败 `{ v: 1, id, ok: false, error: { code, message, details? } }`。HTTP 入口 `POST /v1/rpc`；WS 复用 `req` / `res`。
- **canonical 方法（v1.1）**：`health.get`；`capabilities.list`；`config.get|sources|set`；`sessions.list|get|search|delete|rename|compact|create|restart|activate`；`runs.list|get|start|cancel|resume`；`agents.list|get|tree` / `agents.create|update|close|send|dispatch`；`attachments.list`；`images.blob`；`events.list|subscribe`；`tools.list`；`plugins.list|reload|catalog`；`metrics.get|reset`；`trace.prune`；`permission.respond` / `ask.respond` / `permissions.setToolPolicy`；`interactions.list`；`evals.run|latest`；`feishu.status`；`mcp.list|reconnect`；`gateway.reload`（admin-only，缺省 `not_supported`）；`gateway.shutdown`（admin-only，缺省 `not_supported`）；`gateway.restart`（write，缺省 `not_supported`；q-restart-tool self-restart 的 vessel 工具面入口）；`teams.list|get|post|retract|members|budget` / `teams.create|update|archive|spawnFrozen`。permission 以表格为准。

当前方法计数与演进历史见 `docs/versions/0.24.0.md`–`0.26.2.md`；契约以本表为准。新增 canonical 方法必须发 addendum，并同时写 `result_schema`（ADR-066）。`plugins.catalog`（read）返回单视图（与 `plugins.list` 同源），`params: {}`、`result: { items: PluginCatalogItem[] }`；只读插件目录，不写 config、不访问网络、不触发 reload、不查 registry。`tools.list` 只有一份资源形状 `{ tools: [{ name, description, input_schema, has_permission_check }] }`：0.51 起不区分节点工具面与成员工具面（用户裁定），也没有 `surface` / `source` / `unavailable` 之类第二层字段。可选 `agent_id`（deprecated，仅诊断）只决定按哪具成员身体读同一份清单，响应形状不变；未知 `agent_id` → `not_found`（不返回空列表）；装配层没注入透传（老装配 / agent 关闭）→ 退化成节点口径，响应仍是同一个形状。判据只在执行内核（`MemberExecutionHost.toolSurface` + `selectTools`）一处，serve 只做形状透传。详见 [tools](tools.md)。
- **`gateway.shutdown`（P0-run-stops P1 addendum，优雅关闭）**：`params: {}` → `result: { stopping: boolean }`；permission `admin`；装配层未注入退出序列 → `not_supported`（与 `gateway.reload` 同口径）。**语义是「受理」不是「已退出」**：handler 先回 `{stopping:true}`，下一拍才跑 asm 注入的现成 `shutdownServeStack`（beginDrain 写 resume 标记 + interrupt('shutdown') → gateway.stop → 关栈 → 进程退出）。**为什么需要它**：Windows 上外部 `process.kill(pid)` 是无条件终止，进程内 SIGTERM 处理器永远跑不到 ⇒ `gateway stop` / `node stop` 先经本方法请 node 自己 drain，再在预算内（请求 3s + 等死 10s）等它自死；**超时/失败一律回退既有强杀 + 补偿清理**（失败模式是「停不掉」，不是「没杀成」），并由停止方代打一行 `node.drain.skipped`（pid + reason）。老服务端没有本方法 → `not_found` → 调用方直接强杀（版本偏斜安全）。停止侧客户端 = `src/gateway/reload.ts` 的 `shutdownGateway`；触发点 = `node stop`、legacy 单进程 `gateway stop`、`stopSpawnedChildren` / `NodeSupervisor.stop` 的 node 子进程、**platform entry**（Q4-C：`gateway stop` 的平台入口同样经 `/platform/rpc gateway.shutdown` 让平台进程内跑退出序列（跑到 owned 池 stop），等死预算 = 停止方 `timeoutMs`，超时/拒绝/老版本 `not_found` 回退强杀 + 一行 `platform.drain.skipped`）与 `vessel stop --connect` 远程停（只认显式 `--connect`，远程不强杀；非回环三门控见 [GATEWAY](../operations/GATEWAY.md)）。hub 没有 run 面，不触发；stall-restart 的 force 路径不触发。headless 一次性进程退出**不打** resume 标记（会话无 agent 绑定，标记永不可准入）；启动恢复对「`no_member` + 会话已完成」的僵尸标记经 RunJournal 单写口清理，`recover_done` 日志附 per-session skip 原因。
- **`gateway.restart`（q-restart-tool，self-restart 的 vessel 工具面入口）**：`params: { session_id, run_id?, prompt?, wait_timeout_ms? }` → `result: { accepted, session_id, run_id, orchestrator_pid, wait_timeout_ms }`；permission `write`（vessel op=rpc 可达：write→ask 确认卡，与 bash 危险操作同口径；`node.restart.self` 保持 admin = CLI 专用，桥硬 deny）；装配层未注入 → `not_supported`。**语义是「预约受理 + 编排者已 spawn」不是「已重启」**：asm handler（bootstrap）整体复用 CLI 的 `selfRestartReserveCommand`——loopback `node.restart.self` 写 continuation 标记（RunJournal 单写口）→ 写 handoff → spawn detached 编排者（`restart --orchestrate`，windowsHide）→ 回填 orchestrator_pid → 立即返回；编排者等触发者 run 终态后优雅 stop/start，fail-safe 等待超时撤销标记不重启，机制与 CLI `vessel restart --self` 完全一致（CLI 保留兼容）。**R-3 启动健壮性**：node bind 撞 `port_in_use`（Windows 杀旧进程后端口释放竞态）时 node-supervisor 有界退避重 spawn（3 次 × 1.5s，证据 = 子进程已死 + 日志尾部 port_in_use；整进程重起无残留态）；编排者在 start 返回后另做**健康确认**——platform 各目标 + 触发者 node 的 `/health` 预算 60s 内都可达才报 restart complete，不达如实报 INCOMPLETE（exit 1），不留半态假成功。**R-5 Windows socket 继承根修**（probe-node-hang 报告实证：Windows Bun 1.3.9 spawn 子进程无条件继承监听 socket handle，stdio 全 ignore 亦然）：Windows 编排者改经 **WMI Win32_Process.Create 干净父系 spawn**（cmd /d /s /c 包装落日志，记录 pid 为 cmd 包装进程；WMI 不可用告警回退 detached），断 node→编排者→新 gateway 僵尸端口继承链；port_in_use 分支**先 interrupt 已起跑 run**（'shutdown' → interrupted 可恢复 checkpoint）再退出，消除失败 node 上百秒 drain 半态；报错附 netstat 持有者 pid（死 pid 归属陷阱提示查活后代）；编排者 start 前预检定点清理**本链孤儿**（持有者 = 编排者后代才 taskkill /T /F，死 pid 归属不盲杀）；R-3 重试证据改扫**本次启动日志段**（spawn 时字节偏移之后，非尾 5 行——drain 日志会淹没尾部证据）。**prompt 可选 = 请求级重启**：缺省时装配层以系统固定的请求级恢复指令（中文常量）替代续作点火写入 continuation.prompt，重启后经既有 `resumeContinuations` startup:true 通道自动起新 run 续作，模型无需给自己写启动提示词；显式传入则必须非空（空串 `invalid_params`）。经 vessel 桥调用时 `session_id` / `run_id` 由 ToolContext 自动补注（显式优先，见 [tools](tools.md) vessel 桥节）。**R-2 空=缺省语义**：vessel op=rpc 路 `session_id`/`run_id` 空串视同缺省，由桥身份补注注入调用者会话/run（`readString` 空=undefined 语义）；显式覆盖须传非空值。网络路（`/v1/rpc`）空串仍 `invalid_params` 校验。`prompt` - **legacy-only（不进 manifest）**：`team.*`、`durable.*`、WS `run.submit|get|cancel`。**HTTP 语义**：信封合法时方法成功或方法级失败都返回 200（失败体 `ok:false`）；400 `invalid_params`（旧路径 `invalid_request`）；401 `unauthorized`；403 `forbidden`；413 体过大；未知方法 200 `not_found`（`details.method`）；500 `internal`。旧 REST 适配器保留既有路径、请求/响应体、状态码与错误码。
- **events**：`events.list` 支持 `run_id` / `since_seq` / `since_ts` / `types` / `type_prefix` / `limit`（默认 50、最大 500），按 `(seq ?? ts)` 升序。`events.subscribe` 支持 `since`（gateway wire seq）/ `since_ts` / `run_id` / `session_id` / `types` / `until_seq`（additive，分段回放上界）；`types` 条目以 `*` 结尾按前缀匹配，空数组等价于未提供。SSE `GET /v1/events` 同样接受 `?session_id=`、`?types=` 与 `?until_seq=`。RPC 回调为 `{ method: 'events.event', params: RunEvent }`；WS 旧 `{ kind: 'event', event }` 不变。
- **订阅 epoch 与有界回放**：每次成功的 WS `events.subscribe` 先发 `hello`（`from_seq` = 本次实际发送的第一条 seq），再发过滤后的有界回放窗口（≤ 1 MiB / 2000 条，从最新往回取），最后发 `res`。更早的区间不在该 epoch 内。`until_seq`（一次性，只作用于下一次 subscribe epoch，不影响实时广播）把回放源裁成 `since < seq <= until_seq`，窗口仍受同一预算约束，所以客户端可以拿 `hello.from_seq - 1` 当下一页上界逐页回退（能力位 `events.replay-range`）。环形缓冲之外的更早历史只能靠分页回退回取，取不到就是取不到。`session_id` 归属由 `data.session_id` 或 gateway 的 `run_id → session_id` 映射决定，映射不到不发（fail-closed）。能力位 `events.session-filter` 供客户端对旧 gateway 降级。**0.54 B1/B2 时间线 epoch**（能力位 `timeline.cursor`，真可用才报）：带 `after_timeline_seq`（排他、与 `since` 互斥、必须带 `session_id`）时该 epoch 改读会话时间线——`hello` 带 `start_seq` / `end_seq`（= `wal_head`，闭区间）/ `count`（只覆盖到 `min(end_seq, published_head)`）/ `timeline_head` / `wal_head` / `published_head` / `holes`，帧的 `seq` 是会话内 `timeline_seq`，且该连接**不再接收**环形广播（一个 epoch 只有一套 seq）。`(published_head, wal_head]` 是允许不被推送的尾部，客户端按 `count` + `holes` 自检，对不上就发客户端帧 `{kind:'timeline_gap'}`（服务端记录为 `timeline.gap_reported`，不改事实源）。旧格式会话（无 timeline 标记）→ `legacy_session_unsupported`（0.55：不再支持，用 0.54 导出）；读面未装配 → `timeline_unavailable`；SSE 的时间线读路径未实现（501）。**0.55 的两处删除**：① `hello.timeline_source` 字段删除 —— 客户端改判「时间线段在不在」（形状本身就是判据）；② 过渡期的 `gap` 帧（`kind:'gap'`）整体删除 —— 它只服务 `timeline_source: 'legacy'` 的老 epoch，现在缺口只有两种解释：写者声明的 `holes`，或客户端自己按 seq 连续性算出来（后者报 `timeline.gap_reported`）。**升级后请刷新页面**：48 小时内没刷新的老前端靠 `timeline_source` 判读时，会看到「这个键没了」而退回老 epoch 行为，表现为假缺口报告；刷新即恢复。
- **`timeline-epoch-end`（0.55，新 kind；能力位 `timeline.epoch-end`）**：时间线 epoch 把这一趟（`hello.start_seq..end_seq`）**整趟发完**之后，服务端在最后一帧之后、订阅 `res` 之前补发一帧 `{ v: 1, kind: 'timeline-epoch-end', node_id, ts, session_id?, end_seq, count, has_more }`。字段口径（唯一口径，别造第二个）：`end_seq` = 本趟**已发**的最后一条 seq（零条已发时 = `start_seq - 1`，与空 chunk 同构，客户端不必为此写分支）；`count` = 本趟**实发**事件帧条数（整趟发完 ⇒ 与 `hello.count` 必然相等，留它是让客户端**核对**而不是推断）；`has_more` = 「后面还有**可读**的、本趟没发的」，判据是 `[end_seq + 1, min(声明 end_seq, published_head)]` 里 `countReadableInRange(…, holes) > 0`，**不是**裸的 `end_seq < min(wal_head, published_head)` —— 尾部若只剩写者声明的洞，裸判据恒为真，客户端带 `after_timeline_seq = end_seq` 续拉会原地打转（每趟 0 条、`has_more` 仍为 true，永不收敛）；没有洞时两者逐字等价，所以这不是改口径，是把「洞」这个已知事实算进去。**只在整趟发完时发**：提前停（连接坏 / 撞 8 MiB 背压硬阈值）**不发** —— 那一刻「发完了」不是事实，客户端改从订阅 `res` 这条显式事实按连续前缀收口续拉。**只由时间线 epoch 发**（`timeline_source: 'timeline'`）：老 epoch 的环形 seq 没有「本趟区间」的声明，给它一个结束标记等于凭空造第二个事实源。老客户端不受影响：这是**新增 kind**，分发是 `switch (frame.kind)` + `default: return`（且 JSON 解析包着 try/catch），未知 kind 与收到空行等价。客户端侧：`apps/web` 收到它就结趟（`EPOCH_IDLE_MS` 400ms 空闲猜测已删除），见 [session-replay](session-replay.md)。
- **能力位 `timeline.epoch-end`（0.55，单开一位）**：`timeline.cursor` 的承诺面**一个字段都没改** —— 新帧由新位声明，因为 0.54 的服务端报 `timeline.cursor` 却不发结束帧；并进旧位等于**偷偷改**它的承诺面（老服务端立刻变成「承诺了却做不到」）。承诺面 = 每个**时间线** epoch 整趟发完后补一帧上述形状、提前停不发。取新串的代价是 0：老客户端忽略未知 feature，行为一字节不变。
- **`gateway.ws.closed`（0.55，连接记账，不是 RPC 方法）**：每条事件 WS 连接关闭时经 `logEvent` 打一行结构化事件（级别按 `wsClosedLevel`：客户端正常关闭 1000/1001 = debug，异常 1006/1011 或服务端发起 = warn，其余 info；审计账不折叠。没有新增 RPC 方法 —— 一条连接的生命周期在进程里只有一次，日志是它唯一自然的位置，事后 grep `gateway.ws.closed` + `conn_id`）。字段：`conn_id`（8 hex 短 id，把同一连接的行串起来，不含 token/principal）/ `close_by`（`client` | `server_drain` | `server_backpressure` | `server_protocol` | `server_heartbeat`）/ `close_code` / `close_reason`（非空才出）/ `frames_sent`（hello / event / res / ping / `timeline-epoch-end` 全算）/ `bytes_sent`（UTF-8，本端写出的帧）/ `epochs`（本连接成功发过几次 epoch `hello`）/ `backpressure_drops`（`admit` 拒收 + 8 MiB 硬阈值拒发的事件帧）/ `last_seq_sent` / `duration_ms` / `buffered_bytes`（关的瞬间积压，读不到报 0），外加断连现场的 `session_id?` / `run_id?` / `timeline_epoch`。**`close_by` 与 `close_code` 分开报**：`1001` 既可能是 drain 也可能是心跳超时，靠 code 分不出来；本端 `ws.close()` 全部收敛到 `closeWsBy()`（先记账再关）。读法：`backpressure_drops` 大 + `frames_sent` 的 `bytes_sent` 均值畸低 = 对端不读（客户端不见了 / 卡死），不是网关丢事件。
- **历史分页**：`sessions.get` 新增可选 `message_limit`（1..500）与 `before`（opaque base64url JSON 游标），返回 `messages_total`（恒返回）与 `next_before`（窗口起点 > 0 时）。缺省且无 `before` 仍是全量 messages（旧客户端行为不变）；缺省且有 `before` 时页大小 100。游标锚定绝对下标 + `messages[i-1]` 的 `timestamp` / `content.length` / `role`；锚点不一致 → `conflict` + `details.reason: "history_changed"`，格式错误 → `invalid_params`；游标不是授权凭据。`sessions.get` 结果另有 `event_cursor`（0.53，additive：`{ derived_upto_seq?, event_count? }`）与 `sessions.events`（0.53，additive：`params { session_id, since_seq?, limit?, types? }` → `{ events, next_seq, has_more }`，`since_seq` 为**排他**游标，单条事件形与 SSE 回放一致、按 seq 幂等合并；供刷新后从磁盘日志回填环形缓冲之外的历史）。`sessions.get` 结果另有**可选** `context_usage: { used, max?, at? }`（会话级上下文用量，从该会话事件日志**尾窗**派生；形状、`max` 来源与读取成本见 [serve.md](../agents/serve.md) 的 0.52 addendum），字段缺省 = 没有可用数据。`teams.get` 新增可选 `before`（稳定 `message_id`）与返回 `messages_has_more`；有 `before` 时从上一页首条向前按 8 MiB 分块回扫，最多 64 MiB，找不到 → `conflict` + `details.reason: "cursor_out_of_window"`（`not_found` 只表示 Team 不存在）；一页可因回扫预算少于 `limit`。
- **manifest**：`capabilities.list` 返回 `{ version, config_schema_version: 1, methods: [{ name, params_schema?, result_schema?, permission }], tools, plugins }`；只含 canonical 方法。manifest 来自启动时的单 bundle，tools / plugins 取 `pluginHost()` / `plugins()`（单视图）。
- **`ask.respond` 与挂起的 ask**：命中 `status=pending` 且 `suspended` 的 ask（headless / 超时挂起）时，应答落定后 gateway 自己发起一次 resume（前置：durable 可读 + resume 已注入、checkpoint 仍是 `interrupted`、记录与 checkpoint 同 `session_id`、该 session 没有 queued/running 的 run；任一不成立只记录答案，RPC 仍是 `ok:true`）。返回体只对这类 ask 追加可选键 `resumed: boolean`；普通阻塞型 ask 的参数 / 返回 / 行为不变。答案进入被恢复 run 的口径见 ADR-082 Errata。
- **`ask.respond` 与 async ask**（0.52）：`mode: "async"` 的 ask 投的是「答案 → 新 run」，**不**续跑旧 run（那个 run 早在工具返回后正常收口了）。应答落定后 gateway 把答案作为一条 user 消息投给提问成员（`AgentService.admit`，注入的 `askAnswerDelivery`）并起一次新 run；返回体追加可选键 `delivered: boolean`（`false` = 只记录了答案，例如没有 live runtime / 成员已关闭）。投放的**唯一触发点**是交互注册表的 `pending → answered` 迁移：handler 只等 `awaitAsyncAskDelivery(requestId)` 的结果填 `delivered`，自己不投（否则同一次答案两个投放者 = 双投）；同进程多个 gateway 装配各注册一份监听，重复通知由 gateway 的进程级单飞拦下。`interactions.list` 的 ask 条目带 `mode`（缺省 = sync）；`answer.delivered_at` 是投放幂等标记（内存 + 投放前重读文件，跨进程 / 跨重启兜底），重复应答（`duplicate`）不会投第二次。async ask 的 `pending` 不随 run 终态转 `orphaned`，重启后仍可答。
- **`ask.respond` 的 `batch_id`（additive，0.52）**：可选字符串参数（1..200 字符），标识「这是待批页的哪一次提交」。同一次提交里的多个 `ask.respond` 带同一个 `batch_id`，装配层按 `(agent_id, session_id, batch_id)` 做 250ms 短窗口合并，把整批答案合成**一条** user 消息 + **一次** run（`interactions` 记录里写 `answer.batch_id`）；缺省 / 校验失败 = 一次一条（旧行为一字不改）。合并只在窗口内发生，窗口之后才到的应答退化成单独一条消息，不丢答案；`answers: []`（拒绝回答）永远单发。参数与返回体的其余部分不变，旧客户端不受影响。
- **客户端**：`RpcClient` 有 `request()` + `subscribe()`；`LocalRpcClient` / `HttpRpcClient`。CLI/TUI 不绕开方法表。本地 `subscribe()` 由装配层桥接到 `runtimeEvents`（只读旁路，不写回事件流）。`--connect <url>` / `VESSEL_CONNECT` 使用 `HttpRpcClient`、不取 data-dir 写锁、不写本地 store / trace；回环可明文，非回环必须 HTTPS + token。token 解析顺序 `--connect-token` > env（`VESSEL_CONNECT_TOKEN` / `connect.token_env`）> `connect.token`；CA 用 `--ca` / `connect.ca_file`。建连后 `health.get` 取远端 node 身份；principal 由 token 决定。connect 模式下 `permission.respond` / `ask.respond` 经 RPC 回远端；TUI / headless 同路径。
- **principal 与错误码**：token → principal（`serve.token`→admin、`serve.tokens` 按条目 role、回环无 token→admin）；一个 node 服务单公司。方法级错误一律 `ok:false`，HTTP 200；冻结集合 `unauthorized` / `forbidden` / `not_found` / `invalid_params` / `data_locked` / `quota_exceeded` / `conflict` / `internal` / `not_supported`，增长类业务码还有 `team_full` / `team_frozen`，会话压缩另有 `session_not_found` / `compact_unavailable`；`sessions.create|restart|activate` 另有 `session_not_found`（活动 run 返回 `conflict`，message `run_in_progress`）。旧路径保留既有错误码映射。
- **`attachments.list`（0.52 addendum，节点侧只读目录浏览）**：`{ dir?, include_hidden?, limit? }` → `{ roots, dir?, parent?, entries: [{ name, path, kind: 'file'|'dir', bytes?, mtime_ms? }], truncated, reason? }`；permission `read`。`dir` 省略 = 只返回 `roots`（配置的 `allowed_roots`；未配时是 node 侧**安全默认根**：`agent.cwd`，再退回 home，绝不默认 `/`），相对路径按 basic-tools 的 `cwd` 解析，`limit` 缺省 200 / 上限 500，已在某个允许根上时不返回 `parent`。只列**单层**、只返回 `name` / 真实路径 / `bytes` / `mtime_ms`（无内容、无 mime、无 hash、不递归、不 watch、不支持远程 URL、不写）；deny 目录**及其条目不出现**（不是列出来再标红）、符号链接按 realpath 判（越界目标同样不出现）、越界 / 无权折成 `entries: []` + `reason`（`refs_invalid` / `refs_denied` / `refs_outside_roots`，与 `runs.start` 的 `refs` 拒绝**同一组**稳定码，不抛 500；`dir` 不存在 / 不是目录 / 读不了也是 `refs_invalid`）。返回的 `path` 必是 realpath，因为它要过 `runs.start` 的闸门。
- **为什么由节点侧列目录**：`refs[].path` 的语义是「将要消费它的那台机器上的绝对路径」（闸门按该 node 的 `allowed_roots` 判，`media` 工具也在 node 上读），谁消费谁产出 —— node 回来的字符串天然自洽（WSL 的 `/mnt/d/...` 与 `D:\...` 不再要人工映射，远程也不必猜路径），而网关侧弹原生对话框在 daemon / 远程 node / 容器里根本没有桌面会话。安全面与 `sessions.get`（已能读全部对话正文）同级：文件名 / 结构属于同一信任层级，新增面靠「限根 + 只读 + 无内容 + 单层 + `limit`」收口。
- **`attachments.stage`（file-ref-ux addendum，A2/A3 暂存上传）**：`{ name, mime?, data }`（`data` = 标准 base64）→ `{ path, sha256, bytes, kind: 'file'|'image'|'document', name, mime?, expiresAt }`；permission `write`。浏览器 drop/paste/选择框的 `File` 拿不到用户机绝对路径 ⇒ 字节上传到 node 落一份**带原文件名的临时副本**：`<dataDir>/attachments/staging/<sha256前2>/<sha256>/<原文件名>`（目录 0700 / 文件 0600）。原始字节 ≤ 8 MiB（与视觉入池 `IMAGE_INGEST_MAX_BYTES` 同值；`/v1/rpc` 请求体对本方法单独放宽到 12 MiB，其余方法仍按 `maxBodyBytes`）；超限 `quota_exceeded`（reason `too_large`），形状非法 `invalid_params`，装配层未注入 `not_supported`（fail-closed）。同 sha256 重传复用副本并刷新 mtime（TTL 续期）；图片同时入 blob 池（内容寻址去重）。`expiresAt` = 落盘时刻 + TTL（60min）；过期副本由装配层 GC 回收（+1h 宽限，按 mtime）。暂存根经 `buildPathBoundary` 追加进允许根（`allowed_roots` 非空时），media / ingest / attachments.list 同一份边界自动放行；deny 仍优先。`path` 可直接进 `runs.start` 的 `refs[]`（形状闸门零改动）。
- **`attachments.preview`（file-ref-ux addendum，A4 缩略图 + 过期探针）**：`{ path }`（绝对路径，≤4096 字符）→ `{ status: 'ok'|'gone'|'denied'|'too_large'|'not_image', staging?, expiresAt?, mime?, bytes?, dataUrl? }`；permission `read`。边界与入池同一份（ask/deny ⇒ `denied`，**不读**）；不存在 ⇒ `gone`（暂存过期 / 文件被删，卡片「已过期」态）；非图片 ⇒ `not_image`；> 4 MiB ⇒ `too_large`（回落种类 ICON）；`ok` 且图片时带 `dataUrl`（原样字节，web 侧再缩到 ≤40×40 缩略图）。路径落在暂存根内时附带 `staging: true` + `expiresAt`（「临时」徽标数据源）。装配层未注入 ⇒ `denied`（fail-closed）。
- **`images.blob`（q-media-image-card addendum，内容寻址图片 blob 只读）**：`{ sha256, session_id }` → `{ sha256, found, bytes?, mime?, base64?, reason? }`；permission `read`。GUI 图片卡（media `action=view` 注入消息的缩略图 / 点击放大）的字节来源。**无路径面**：入参只有 64 位 hex 内容地址 + 会话 id，不拼路径、不递归、不读 URL、永不回源读 `refs[].path` —— 与 `attachments.read 不该存在` 的红线不冲突（那条禁的是按路径读任意文件；池内字节全部经 `ingestImageRefs` 边界闸后落盘，读池 = 读已过闸内容）。**会话可见性闸（fail-closed）**：`session_id` 必填，会话经与 `sessions.get` 同一个读口（`sessionFor` → `loadForRead`/`load`）加载，sha256 必须真实出现在该会话某条消息的 `refs` 里（归属反查只扫这一个会话）；没有读口 / 会话不存在 / 读失败 / 归属不命中一律 `found:false, reason:'blob_missing'`（与真缺失不可区分，不泄漏存在性）。命中时 `mime` 由魔数嗅探（不信扩展名），`base64` 为图片字节；单图上限 8 MiB（与入池同档，超限 `reason:'too_large'`）。旧 gateway 无此方法（`not_found`）⇒ 前端退回纯元数据 chip，不显示破图。
## canonical agent 生命周期契约
- `agents.create`：`{ agents: [{ kind?, name?, model?, system_prompt?, team_id?, workspace?, visibility?, from_session_id?, seed?, keep_messages? }] }`。`kind` 只取 `peer` / `contractor`；peer 必须有 `team_id`、不接受 `workspace`，`workspace` 只对合成 owner 传输开放；`from_session_id` 存在时从源 session 取种子（`seed` 缺省 `copy`，`compact` 必须显式；`keep_messages` 是 `sessions.get().messages` 下标），源 agent / session 零改动且仍可跑；`seed` / `keep_messages` 无来源时 `invalid_params`。成功条目带 `agent`（`owner` 可选）。无 `kind` 的旧形状语义不变。失败条目按 §1.4 映射：`not_found` / `not_visible` / `invalid_params`（含 reason `source_private`）/ `conflict`（reason `not_primary` / `run_in_progress` / `agent_closed` / `team_frozen` / `team_full`）/ `internal`（reason `create_failed`）。`agents.list` / `agents.get` / agent status 条目带 `role`：运行期注册表角色 `main` / `subagent`，或成员角色 `member` / `temporary`（`single` 已删除，存量快照读取时降级为 `member`）；`owner` 对外仍可选（v3 总是写入）。人类管理面 principal（`role:'admin'` 且无 `agent_id`）的 `agents.list` 在事件派生视图外合并无 Team 的 `member`；合成 owner 传输与其它 agent / team token 仍按 viewer 可见性判定，private member / temporary 不放开。
- `agents.update`：`{ agents: [{ agent_id, name?, model?, system_prompt?, role?, team_id? }] }`（每项至少一个字段；`role` 只取 `member` / `temporary`）。`role` / `team_id` 是显式角色转换：`member` 必须绑定 Team、`temporary` 归属转换者（`from`）；handler 传 `team_id → teamId` 与 `from = principal.agent_id ?? 'human'`。成功条目带 `agent` / `changed` / `applies_to: 'next_body'`（仅 model / system_prompt 实际变化时）。`agents.close`：`{ agents: [{ agent_id }] }`；成功条目 `{ ok: true, agent, agent_id, closed: true }`。
- `agents.inbox`（只读）：`{ agent_id?, session_id?, include_held?, message_ids? }` → `{ agent_id?, unread, pending, entries: [{ message_id, from, summary, status: 'unread'|'held', ts, session_id?, from_name?, text? }] }`。`agent_id` 与 `session_id` 二选一（后者由服务端 `resolve()` 反查 agent，缺两者 `invalid_params`）；`session_id` 做归属**等值过滤**，缺该字段的老条目永不命中。摘要来自 inbox 文件已存的 160 字 `summary`；**只有显式传 `message_ids`（≤10，越界 `invalid_params`）才返回 `text`**，且不改变任何状态（不消费、不 hold / unhold）。可见性与 `agents.list` 同一口径（不可见 → `not_found`）。`agents.recall`（write）：`{ agent_id, message_ids }`（≤20，越界 `invalid_params`）→ `{ deleted, skipped: [{ message_id, reason: 'not_found'|'consumed'|'active' }] }`；按 message id 取消它对应的 queued run 并从「将执行」集合拿走 —— **human 源 = 真删**（inbox discard，不留墓碑）/ **agent 源 = unhold 留档**（回可读 unread），正在执行的那条 `skipped: active`（撤回不是打断）。条目没有也不该有 run id，所以不给它加 `run_id` 字段。`agents.claim`（0.51，write）：`{ agent_id, message_ids }`（≤20，越界 `invalid_params`）→ `{ claimed, skipped: [{ message_id, reason: 'not_found'|'consumed' }] }`；把「已经看到正文」的待处理输入从队列里拿走：先撤掉该消息对应的 queued run 并从 body mailbox 出队，再标 `consumed` + 解 hold。与 `agents.recall` 的差别只在出口 —— recall 按 source 真删 / 留档，claim 一律**消费**：拿走的条目不再投递、不再出现在 `agents.inbox`，下一次 append 裁剪时清掉。**不可逆**（没有 unclaim）。没有 `active` 档：正在执行的那条开跑即 consumed，按 `consumed` 跳过。
- `agents.send`：`{ messages: [{ to, content, conversation_id?, interrupt?, notify?, message_id? }] }`。`interrupt` 与 `notify` 互斥（`invalid_params`，reason `conflicting_delivery`）；`message_id` 只配 `interrupt`；`notify` 必须自带 `content`；`important` 已删除，显式传入 → `invalid_params`。成功条目两种：work / urgent `{ ok: true, queued: true, message_id, state }`；notify `{ ok: true, notified: true, message_id, wake, resolution: 'live' | 'gone', resolved_to?, conversation_id? }`。strict send，不 resume。
- `agents.dispatch`：work-only，输入 `{ messages: [{ to, content, conversation_id?, allow_auto_create? }] }`；传 `interrupt` / `message_id` / `notify` / `important` → `invalid_params`；成功 `{ ok: true, status: 'queued', message_id, resolved_to, resolution, conversation_id? }`，`resolution` 取 `live` / `resumed` / `rotating` / `created`；业务拒绝逐条 `{ ok: false, code, error }`（`agent_left` / `resume_failed` / `auto_create_failed` / `auto_create_not_allowed` / `not_visible` / `budget_*` / `conversation_team_mismatch`）。
- 统一结果 `{ results: [...] }`，与输入同序；单条失败 `{ ok: false, code, error }`，不影响其它条目。上述生命周期方法 permission 都是 `write`；结构错误整体 `invalid_params`；team-scoped control token 不能 create / close（`forbidden`），update / send / dispatch 只能操作同 `team_id` 成员，否则逐条 `not_found`；update 的角色转换只能转 `member` / `temporary`（同 Team），不能换到其它 Team（`forbidden`）。`principal.agent_id` 只由合成 owner 传输填 root owner id；handler 以 `ctx.principal.agent_id ?? 'human'` 作为 `from` / `viewer`。owner 端点只做传输：用 `defineMethods([...createAgentMethods, ...createTeamMethods])` 组装与 gateway 同源的方法表，wire 名即 canonical；HTTP 状态映射 `invalid_params` 400、`forbidden` 403、`not_found` 404、`conflict` 409、`internal` 500。
## canonical session 创建 / 切换契约
- `sessions.create`：`{ agent_id?, from_session_id?, seed?, keep_messages?, startup_prompt?, title?, mode?, files? }` → `{ agent_id, session_id, source_session_id?, seed?, keep_messages?, keep_projected?, copied_messages?, title?, primary: true, files_restored?, files_skipped? } (additive param title: names the new session, stored as SessionState.title with title_source='manual' so automatic AI naming never overwrites it; 1-120 chars after trim, blank / overlong -> invalid_params, echoed back as title)`。同一 marker 的出口是 `sessions.list`：`SessionInfo` 带可选 `title_source`，取 `'manual'`（`sessions.create{title}` / `sessions.rename` 人工命名，自动 AI 命名不再覆盖）或 `'generated'`（AI 命名）；additive —— 无标记（旧数据 / 尚未命名 / 旧 gateway）时该 key 不出现，线上形状与旧版一致。归一化与唯一出口见 `packages/core/src/session/session-store.ts` 的 `withTitleSource`（file / sqlite 两个后端与 `toSessionInfo` 共用，非 `manual` / `generated` 的值一律当无标记丢弃、不抛错）。无来源 = 空 session（`agent_id` 必填，`seed` / `keep_messages` / `mode` / `files` → `invalid_params`）；有来源 = 源 primary 的 `[0, keep_messages)` 深拷贝 / 压缩（`agent_id` 可省或必须与源一致）。成功时新 session 成为唯一 primary，源 binding 退役进 `bindingHistory`，源必须 `sessions.activate` 才能再跑。`mode:'both'` 表示先做显式 git restore（`files` 必填），硬失败在切换前中止，未注入回滚端口 → `not_supported`；单路径失败计入 `files_skipped`。错误：`not_found` / `not_visible` / `session_not_found` / `invalid_params` / `conflict`（`not_primary` / `run_in_progress` / `agent_closed` / `team_frozen` / `team_full`）/ `quota_exceeded` / `internal`（`create_failed`）。
- `sessions.restart`：`{ session_id, startup_prompt? }` → `{ agent_id, session_id, from_epoch, epoch }`。同一 session 原地换 binding（epoch+1）；旧 binding 退役进 `bindingHistory`，旧 EU dispose / `releaseHeldFor`（只放这具 body 的持有 —— 多 live body 时不得误放别的 body 的在途队列），transcript / SessionState 不变。错误：`session_not_found`；非 primary → `conflict` + `not_primary`；current primary 有 active run → `conflict` + `run_in_progress`；agent closed / left → `conflict` + `agent_closed`；失败 → `internal`（`restart_failed` / `restart_rollback_failed`）。
- `sessions.activate`：`{ session_id, startup_prompt? }` → `{ agent_id, session_id, previous_session_id, epoch, noop }`。目标限 primary 或 `bindingHistory` 中的 session；目标已是当前 primary 时 `noop: true`；成功时 epoch = 当前 primary epoch+1，原 primary 退役。错误：`session_not_found`；不可见 → `not_found`（details `reason: not_visible`）；current primary 有 active run → `conflict` + `run_in_progress`；agent closed / left → `conflict` + `agent_closed`；失败 → `internal`（`activate_failed`）。三个方法 permission 都是 `write`；team-scoped control token 只加入 `sessions.create`（镜像已删的 `agents.rotate`），handler 校验 `agent_id` / 源 session 所属 agent 与 caller 同 `team_id`，否则 `not_found`。
- **0.39 删除面（已删除）**：`agents.fork` / `agents.rotate` / `agents.restart` / `agents.compactFork` / `sessions.rewind`；替代为 `agents.create{from_session_id}`（fork）、`sessions.create`（rotate / compactFork / rewind 的编辑重试）、`sessions.restart`（restart）。旧事件 `agent.forked` / `agent.compact_forked` / `session.forked` / `system_event:'fork'` 只读渲染。
## canonical runs 契约：附件引用（0.52）
- `runs.start` 新增**可选** `refs: [{ kind: 'file'|'image'|'document', path, name?, mime?, bytes? }]`（≤32 条，`path` 为宿主机绝对路径、≤4096 字符）。additive：不传 = 无引用，旧客户端行为不变。refs **只有路径与元信息**（不存正文 / base64 / 远程 URL），随这次投递写进 `user.message` 事件与 SessionState，`sessions.get` / `SessionDetail.messages[].refs` 原样透出。
- **只拦形状，不拦越界**：handler 只校验形状（绝对路径 / ≤4096 字符 / ≤32 条 / kind 合法），非法才 `invalid_params` + `details.reason: "refs_invalid"`（带被拒的 `details.path`）。路径边界（命中 deny 目录 / 越出 `allowed_roots`）**不在准入处判** —— 用户引用自带意图，提前拒等于把意图丢掉；权限校验发生在模型**读文件那一刻**（`read` / `media` 的 `evaluatePath`，与普通文件工具同一套：denylist 硬 `deny`、`allowed_roots` 越界 `ask`）。同一份 `messageRefSchema` 与同一份 `readRefsParam` 也被 `teams.post` 的可选 `refs` 复用（不传 = 无引用）：团队页的引用随 @ 投递写进成员 session 的 `Message.refs`（成员靠 `[refs]` 行用 `media` 工具按需读），**同时也写进 Team 日志**（`TeamLogEntry.refs`，只在非空时写）并由 `teamPostResultSchema` 回显 `refs`，`teams.get` 原样透出 → 团队时间线在气泡上方显引用 chip（乐观行直接用回执的 refs）；旧日志 / 无引用的消息没有该键，读侧不渲染。系统行（join / leave / retract / 预算 override）与成员 `send` 不带 refs。团队页引用与草稿同槽（按 `(node, team)` 键）、发送成功后随草稿清空，「再次发送」只复原正文与 @。
- **读侧拒绝的归属**：越界读取被 ask 拒绝 → 工具结果说明是「工具的权限判定要求确认」（`permission-policy` 的错误文案带 tool's own permission check）；命中 denylist → 工具自己返回「被路径策略拒绝，不是文件不存在」。两种都不复述完整路径（模型自己的入参里已有）。**模型侧不注入正文**：refs 不进 `RunOptions.messages`；唯一注入的是 BeforeLlm 的一行环境信息（`[refs] N attachments: … (use media: action=…)`，见 [context](context.md#injection)），内容由多模态解析器插件的工具按需读。
- Web：Composer 的待发送引用与草稿同槽（按会话键、sessionStorage），`runs.start` 成功后清空；`addRef` 只拦形状（绝对路径 / 长度 / 条数，防手误），被拒时按 `details.reason` 出 i18n 文案。
## canonical team 冻结契约
- `teams.spawnFrozen`：`{ team_id, frozen }` → `TeamSummary`（含 `spawn_frozen?`，`false` 时字段缺省）；permission 为 `write`。team-scoped control token 只能操作自己的 team，其它 team 返回 `not_found`。冻结是 Team 元数据，`teams.update` 不修改该字段；冻结期间该 Team 的 create / hire / 人类 `agents.create`（含 `from_session_id`）/ reinstate 均返回 `team_frozen`，只有 `frozen: false` 解冻。CLI 为 `vessel team freeze|unfreeze <team_id>`。
- `teams.retract`：`{ team_id, message_id }` → `{ team_id, message_id, retracted_message_id }`（`message_id` 是新 tombstone，`retracted_message_id` 是目标）；permission `write`，team scope 校验同其它 `teams.*`。日志保持 append-only：只追加一条 `kind:'system'`、`system_event:'retract'`、`content:''` 的 tombstone，不删除 / 不改写原消息，也不级联删除后续回复。错误：Team 不存在 `not_found`；目标不在可读窗口（最近 1000 条）`not_found`（details `team_code: message_not_found`）；目标为 system 行 / tombstone `invalid_params`；目标已被撤回 `conflict`（`already_retracted`）；归档 Team 复用 `team_archived`。
## canonical kanban 契约（q-kanban-view addendum）

任务看板查看器（Web UI `#/kanban`）的数据面。板文件 = 个人侧外层仓 `D:/Application/APP/Vessel/docs/dev/kanban/board.json`（`kanban.board_path` 已指；main 维护，形状 `{board,updated,columns,note,tasks:[{id,title,column,owner,branch,progress}]}`）；归档 = 板**同目录** `archive.json`（append-only，`{archive,note,entries:[Task+archivedAt+cycle?]}`）。设计源流：q-kanban 设计文档（design/q-kanban）的 §4.4 校验分级 / §6.2 条件轮询 / §9.2 归档约定；本实施按任务书改道为服务端 canonical RPC + apps/web 内置域（不做插件）。

- **路径解析（装配层，serve 只收绝对路径）**：config `kanban.board_path`（snake_case YAML → `KanbanConfig.boardPath`；~ 展开、相对进程 cwd）→ 缺省 `<cwd>/docs/dev/kanban/board.json`（仅代码缺省；代码仓无 `docs/dev/`，生产板恒经 `kanban.board_path` 指个人侧外层仓 `docs/dev/kanban/board.json`）。cwd = repo 根 / 舰队 worktree 根（fleets/<name> 本身是 git worktree）。注入点 `src/cli.ts` gatewayOptions.kanban；未注入 = 方法仍进 manifest，handler 返回 `not_found`（teams.* 先例）。archive 路径恒由板路径派生（同目录 archive.json），**不读文件内指针**——杜绝不可信路径诱导读。RPC 不接受自由路径参数（读白名单 = 装配注入的那一个板）。
- **`kanban.get`（read）**：`params: { if_mtime_ms?, if_size_bytes? }` → `{ unchanged: boolean, mtime_ms, size_bytes, board?, path? }`。双条件命中 = 只 stat 不读文件，回 `{unchanged:true,mtime_ms,size_bytes}`（一次 RPC ≈ 一次 stat，供 UI 可见期廉价轮询）；不命中 / 无条件 = 读 + 解析 + 归一化，回 `{unchanged:false,board,path,mtime_ms,size_bytes}`。`board = { board, updated?, note?, columns: string[], tasks: [{id,title,column,owner?,branch?,progress?}], warnings: string[] }`。**校验分级（宽进严出，坏任务不拖垮整板）**：板级 fail-closed（文件缺 → `not_found`；parse 失败 / 顶层非对象 / 缺 board 标题 / tasks 非数组 → `internal` 带路径原因；> 2 MiB → `quota_exceeded`）；列缺省 / 空 → 从 tasks 的 column 去重推导（出现顺序）+ warning；task.column 未命中 columns → 保留任务，UI 归「未分类」兜底列 + warning；缺 id/title/column 或类型错 → 跳过该任务 + warning；可选字段类型错 → 丢字段 + warning；重复 id → 留首 + warning；未知键忽略（前向兼容）；任务数软上限 2000（截断 + warning）。
- **`kanban.archive`（write，用户验收专用）**：`params: { id, cycle? }` → `{ ok: true, id, archived_at, board, mtime_ms, size_bytes }`（board = 归档后的新板归一化形状，UI 一次 RPC 即更新）。**触发纪律（用户裁定）：绝不自动归档**——只有用户在 KanbanView 卡片上勾选验收（经确认弹窗）才调本方法。语义 = 把 task 从 board.tasks 移除 + 追加进 archive.json entries（条目 = 原始 task **全字段快照** + `archivedAt`（ISO，必填）+ `cycle?`），并刷新 board.updated。**写序 = 先 archive 后 board**：中途失败最坏留「两侧都有」的重复（可恢复），不丢任务；id 已在 archive entries → 跳过追加只删板（重试自愈，append-only 不重复）。archive 存在但损坏 / 不可读 → `conflict` fail-closed（绝不覆盖，维护者负责修复）；archive 不存在 → 新建（archive/note/entries 形状与现有约定一致）。板任务不存在 → `not_found`。**并发**：进程内 mutex 串行化读改写 + 写前重读板（最小化窗口）；跨进程并发（维护者 agent 同时编辑 board.json）无文件锁——data-lock 是 dataDir 级不适用，冲突窗口 = 重读到 rename 之间，最坏维护者该次编辑被覆盖（板文件 git 可恢复）；接受该风险，不做跨进程锁。两文件写均走 core `atomicWrite`（temp+rename，按路径排队）。
- **错误码**：复用冻结集，不扩 union——`not_found`（板文件 / 任务缺 / 未注入）、`invalid_params`（参数形状）、`quota_exceeded`（板超 2 MiB）、`conflict`（archive 损坏 / 读失败）、`internal`（parse / IO）。
- **UI**：apps/web `domains/kanban/KanbanView.tsx`，导航 Chat 组独立项「看板 / Kanban」（`#/kanban`）；三列按 board.columns 序 + 未分类兜底；GHOST 样式（ghost-control utilities）；手动刷新无条件读，可见期 30s 轮询带双条件，document.hidden 暂停。
