# 工具执行与 runtime 解耦（目标态）

> 用户原话：「我们的工具调用系统能不能和 runtime 本身拆分开，通过消息队列和并发的方式将处理工具调用的系统组织为一个独立的系统，而不是耦合在代码里，导致每次更新工具都需要重启 gateway。」
>
> 本页是**目标 / 迁移态**，不是现态：现态见 [tools](tools.md#engine-exec)（engine 双路执行）/ [plugins](plugins.md) / [extensions](extensions.md) / [host](host.md)。
> **本页的协议设计未直接实施**（只到设计 + §6 的一次性尖刺读数）；四个动机随后由 P2 外置 + engine 池以**不同路线**落地——[ADR-106](../adr/ADR-106-engine-pool.md)（accepted；上游裁决与冻结指针见该 ADR 头注）。本页原文保留作设计史，被取代处就地标注。
>
> **被取代路线对照**（现态以 ADR-106 + tools.md 为权威）：
>
> | 维度 | 本页目标 | 现态（P2 + 池） |
> |---|---|---|
> | 帧 / 传输 | 长度前缀 JSON 1MiB、只用继承管道、禁 TCP 回环（§4.1 / §5.2） | NDJSON JSON-RPC 8MiB；child=stdio，pool=TCP loopback + 双 token（ADR-106 决策 2） |
> | 路由粒度 | read/edit/write 默认不搬（§3.3） | 白名单四工具全搬 worker（P2 用户拍板）；subscribe/media/vessel 留 in-process |
> | 配额 | 每工具信号量 + 有界队列（§4.5） | 无队列（明确不建）：进程级 maxInflight 准入快拒 + LB 换家重试（ADR-106 决策 7） |
> | bounded 回执 | sidecar 回 bounded=true 不许原样放行（§5.3） | worker 同一份 core 闸自裁 → 信封 bounded:true → host ctx re-mark（engine-client/forward.ts） |
> | 开关 | `VESSEL_TOOL_HOST` env（§7） | YAML 双开关 `tools_engine.mode` × `gateway.engine_pool.size`，缺省关 |

## 0. 结论

1. **工具面（registry）不能搬走，只能搬执行**。`PluginHost.listTools()` 就是系统提示里的工具表，是 prompt surface 的唯一来源；把它放到另一个进程等于给工具面造第二份真相源。所以 B 形态只搬 handler，registry / 声明式边界 / 出口闸 / 权限判定全部留在 core。
2. **A（进程内可重载宿主）今天已经做了 60%，剩下 40% 的代价实测不可忽略**：定义级热换（`tools` scope + `unregisterTool` + 调用开始时取一次定义）已经存在；缺的是**模块代码重载**，而唯一不重启的办法（cache-busting `import()`）实测**每次重载留下 ≈1.3 MB 常驻内存、GC 不回收**（§6.4）。所以 A 只能做成「有限次热重载」，改工具代码彻底不重启这件事 A 做不到。
3. **推荐「先 A 后 B，B 只覆盖风险/重量级工具」**：bash / web / MCP 先搬，`read` / `edit` / `write` 留 in-process。判据是读数不是口味：`read` 单次 1.7ms，一次 pipe 往返 0.15ms = **+9%**；而 `bash` 单次 98ms，同一往返 = **+0.15%**（§6.2 / §6.3）。**（已被取代：P2 用户拍板白名单四工具全搬 worker，IPC 税接受——见 banner 对照表 / ADR-106；+9% 判据保留作设计史。）**
4. **这不是性能优化**。repo 自己的 `run.timing` 把 gap 拆成 `tools_ms` + `us=`，既有观测里「我们中间那段」只占 run 的 0.9–1.2%（中位 68–136ms，**任务方提供的既有读数，本单未复核**；复现方式见 §6.6 第 7 条）。解耦会**增加**延迟，收益全在可运维性（热更新 / 隔离 / 配额）。

## 1. 四个动机逐条核查：今天到底疼不疼

| 动机 | 真实收益 | 今天疼吗 | 证据（今天的事实） | 解耦能给多少 |
|---|---|---|---|---|
| **热更新**（改工具不重启） | 改插件代码不再需要进程重启 | **疼，但疼点很窄** | ① 配置 / 权限 / 工具面 / MCP 四个 scope **已经能热应用**（`gateway.reload` 的 `permission` / `tools` / `mcp` / `plugins`）；② **能力插件的模块代码不能热重载**，`plugins.reload` 对 in-process 插件如实返回 `restart_required`，文档写明「不谎报已重载」（[plugins](plugins.md) 热重载 E3）；③ 重启代价：node 启动 `ready=2.28s`（真实数据 344 会话；空数据根 0.45s，见 `perf(startup)` b7f02ccf）；④ 重启会**打断在飞 run**：`node-drain.ts` 先写 `resume_after_restart` 再 `interrupt('shutdown')`，且明确「不 await 任何模型流 / 长工具 / 后台进程，预算只有 2s」——在飞的那次工具调用丢失，resume 从 checkpoint 重跑，**副作用可能重复** | B 形：热重载 = 换一个 sidecar 进程，实测 spawn + 握手 45–85ms（§6.2），比 node 重启 2.28s 小两个数量级，且不碰 run |
| **崩溃隔离** | 一个工具的 panic 不再带走整个进程 | **疼过一次，但根因不在工具** | `panic(main thread)` 是**进程级**的：那个 bun 进程立刻没了，其下 node / hub 不被一起杀（[BUN-WIN32-SEGFAULT](../operations/BUN-WIN32-SEGFAULT.md) §1）。工具是 in-process 插件，所以**任何工具里的原生调用踩空 = 该 node 上所有会话一起断**（含 async bash 作业表，它是进程级的） | 爆炸半径从「整个 node」缩到「该工具进程」；但 0.58 那次事故的根因是代理 HTTP 手写流泵，解耦不会让它不发生 |
| **并发与配额** | 每工具并发 / 队列上界 / 立即失败 | **疼，而且这是唯一「今天完全拿不到」的东西** | 今天只有两层：`Scheduler` 的 `maxConcurrency`（缺省**无上限**）+ `perBodySerial`（同 body 串行）；工具层只有 `concurrencySafe` 的**批并发**，`Promise.all` **没有任何上界**（`tool-calling-loop.ts`）。一次响应里模型给 8 个 `concurrencySafe` 调用就真的并发 8 个，没有每工具、没有全局工具配额 | B 形才有落点：sidecar 里每个工具一个信号量 + 有界队列，队列满即 typed error（不静默排队） |
| **跨机执行**（工具跑在别的机器） | 重工具不占本地资源 | **不疼** | 没有用户诉求；且与路径类工具的语义直接冲突：`cwd` / `deny_paths` / `allowed_roots` 是**本地**事实，`bash` 明确「不是沙箱」，跨机执行会让「读哪个文件」这件事失去参照 | **v1 明确不做**（判据见 §8.1）。要做也是另一套传输与鉴权，不属于本文 |

一句话：**热更新的收益是「把 2.28s + 在飞调用丢失」换成「<100ms + 无感」，崩溃隔离是买保险，配额是今天缺失的能力，跨机不做。**

## 2. 现状事实（设计之前先钉死这些）

| 环节 | 今天在哪 | 结论 |
|---|---|---|
| 工具定义注册 | `PluginHost.registerTool`（`packages/core/src/runtime/plugin-host.ts`），唯一注册表 | 注册表**留在 core** |
| 工具面 → 请求 tools[] | `ToolExecutor.listToolSchemas()` → `ExecutionUnit.ensureToolPin`（会话起点快照） | 注册表仍是**执行唯一真相**（live `getTool`）；请求面是会话快照视图（tools-body-snapshot），换形态时这两层语义**不许变** |
| 执行 | `ToolPipeline`（core）→ `tool.handler(args, ctx)`（插件代码） | 只有 handler 需要搬 |
| 出口闸 | `tool-result-gate.ts`（core）：单条 ≤ 16k token，头 30% / 尾 70% + 落盘路径；幂等靠 `markToolResultBounded` 回执 | 闸**只能在 core**，回执是**进程内** WeakMap（跨进程不可伪造，这是好事）**（现态补充：worker 用同一份 core 闸自裁后经信封 `bounded:true` 声称，host forward 在 ctx 上 re-mark——回执仍是 host 侧 WeakMap，见 §5.3 标注）** |
| 权限 | `PermissionPolicy.authorize()` 在 handler **之前**；工具的 `checkPermission` 是**插件代码** | A 形无损；B 形要拆「声明式部分留 core / 动态部分走一次 RPC」 |
| 路径边界 | `plugins/tools/basic-tools/src/index.ts`：内置 denylist `~/.ssh` `~/.aws` `~/.gnupg` + 配置 `deny_paths` / `allowed_roots`，`realpath` 判定 | 今天**只在执行侧**校验（这正是 B 要补的两侧校验） |
| async bash 完成唤醒 | 进程级 sink 槽（`registerAsyncBashCompletionSink`）+ BeforeLlm hook 注入 `vessel:notice` | B 形要有一条 `tool.call.progress`（`kind: 'notice'`）把完成事件送回 core |
| 已能热应用的面 | `gateway.reload` 的 `plugins` / `config` / `permission` / `tools` / `mcp`（`src/gateway/gateway-reload-wiring.ts`、`src/config/hot-apply-appliers.ts`） | A 形的地基已经存在 |
| 子进程插件先例 | 体验插件：换行分隔 JSON-RPC、帧上限 1 MiB、握手令牌只经参数下发（不进 env）、心跳 15s、重启预算 **10 分钟 3 次**、`engines.vessel` semver 门禁（`packages/serve/src/plugin-host/**`） | B 的协议 / 生命周期**照抄这套口径**，不另造 |

**两条不能忽略的约束（决定 B 的边界）**：

1. `ToolContext` 里带 `events`（EventStream）、`signal`（AbortSignal）、`messages`（快照）、`cwd` —— **不可序列化**。今天 `basic-tools` 四个工具、`web-tools` 两个、MCP 全都读 `ctx.signal`；`packages/agent` 的几个工具还读 `ctx.events` / `ctx.messages`。所以 B 只能承载「只依赖 args + 必要环境量」的工具，其余的声明 `needs_ctx` 留在 in-process。
2. **同一插件出现两份模块实例是已经踩过的坑**：`basic-tools` 的 async sink 槽挂在 `globalThis` 上，注释写明「插件的模块实例和装配层 `import` 的那个实例不一定是同一个」（按目录 / 自身根两条路径解析时会出现两份），表现是「一声不响地不投递」。这是 A 形（同进程多份实例）的固有风险，也是 B 形的额外好处：**一个 sidecar 进程里只有一份实例**。

## 3. 两种形态

### 3.1 A：进程内可重载插件宿主（版本化 registry）

拆成两半看，因为一半已经在跑：

| | A1 定义级热换（**已落地**） | A2 模块代码重载（**未落地**） |
|---|---|---|
| 做法 | `tools` applier：旁路 host 装一遍插件算出目标工具集 → 与真实 host 求差 → `registerTool` / `unregisterTool` 一次性替换 | 只能靠 cache-busting `import(url + '?v=N')` 让 ESM 重新求值 |
| 在飞调用 | **已经安全**：`ToolPipeline` 在调用开始处 `getTool()` 取一次定义，之后 guardrail / hook 改写都从 `pluginHost` 重取，旧定义被在飞调用握着直到结束 | 同上（旧定义对象仍被引用），前提是 module namespace 不被提前 GC |
| 代价（实测） | 0（毫秒级，`install` + 4 个工具 1.7ms） | **每次 ≈1.3 MB 常驻**（basic-tools 50 次 +66 MB，调用 GC 后不回落）；20 行小模块 0.5 MB/次。中位重载耗时 1.0–1.3ms |
| 释放 | `plugin.dispose()` 只有一次机会（宿主收口时调），且 `basic-tools` 明确「不杀作业、不清表」 | 老版本模块没有 dispose 时序，定时器 / 子进程 / MCP 连接无人回收 |

**A 的结论**：A1 已是现态，A2 只能做成「**有限次热重载**」——比如每进程最多 N 次（N 由内存预算定：1.3 MB/次 × 50 = 65 MB，够一次开发循环，不够一天）。超了就要么让驻留内存涨，要么重启进程。**「改工具代码永不重启」这个诉求，A 形解决不了。**

### 3.2 B：独立工具执行进程（同机 sidecar）

形状（registry 不动，只换 handler）：

```
模型 ──► tool-calling-loop ──► ToolPipeline（core）
                                ├─ guardrail / BeforeTool hook
                                ├─ 权限（core：声明式边界 + 工具动态判定 RPC）
                                ├─ handler（in-process 插件）   ← 路由表决定
                                └─ handler（sidecar 代理）──► tool.call.request ──► toolhost 进程
                                                              ◄── tool.call.result / .progress
                                ├─ ToolResult guardrail / AfterTool hook
                                └─ 出口闸 16k（core，唯一）
```

| 维度 | A（含 A1+A2） | B（sidecar） |
|---|---|---|
| 热更新工具**代码** | 有限次（内存涨 1.3 MB/次） | 换进程：**45–85ms**（实测 spawn + 握手），可无限次 |
| 崩溃隔离 | **不可能**（同进程） | 该工具进程死，core 把在飞调用收成 `tool_host_crashed`，run 继续 |
| 并发 / 配额 | 只能加在 core（进程内计数），一崩全丢 | 每个工具一个信号量 + 有界队列；sidecar 重启后配额状态自然重建 |
| 单次延迟 | 0 | +0.15ms（1 KB 往返）+ 大结果的搬运（1 MB = 6.4ms） |
| 新增复杂度 | 低（复用 reload / applier） | 协议、生命周期、双份超时、取消、背压、版本兼容、混合态 |
| 失败模式 | 一个插件拖死全进程 | 多一类失败：sidecar 起不来 / 半死 / 版本不匹配 |

### 3.3 推荐路线

**阶段 A（先做，成本小）**：

1. 把 `tools` applier 的语义说清并补一条判据：**定义级热换是默认路径**（改 schema / 配置 / 权限走这里，不重启）。
2. 给 A2 一个明确定位：`tools.reload_code` 只做**有限次**热重载（带上界与计数，超界如实返回 `restart_required`），不做成「永不重启」的承诺。
3. 把「插件两份实例」这个坑写成门禁（装配层用同一份 resolve 结果；sink 槽这种写法标注为反模式）。

**阶段 B（后做，只覆盖风险/重量级工具）**，迁移顺序与理由：

| 顺序 | 工具 | 为什么这个顺序 |
|---|---|---|
| 1 | `bash` | 最重（98ms 中位）、最危险（能起任意进程、能吃内存）、IPC 开销占比最小（+0.15%）；配额收益最大 |
| 2 | `web_fetch` / `web_search` | 已有 SSRF / robots / 每 run 配额三道闸，天然是「重且外发」的东西；`concurrencySafe: true`，正是需要限并发的那类 |
| 3 | MCP 工具 | 数量动态（外部 server 提供）、单个 server 崩不该带走 node；握手时自报工具集与 core 对账 |
| 4 | `read` / `edit` / `write` | **最后，且默认不搬**：单次 1.7ms 量级，IPC 往返 +9%；路径边界对本地 `realpath` 最敏感，跨进程只会让「两侧校验」更难证明一致 |

判据（不是偏好）：**IPC 开销 / 工具单次耗时 < 1% 才值得搬**。bash 0.15%、web（网络 RTT 数百 ms）≈0.1%、read 9%（不值得）。

> **已被取代**：P2 白名单 read/edit/write/bash 全搬 worker（用户拍板，蜂群统一工具池方向接受 IPC 税，ADR-106 上下文）；本节迁移顺序与 <1% 判据保留作设计史。现态执行位置见 [tools.md](tools.md#engine-exec)。

## 4. 协议草案（B）

### 4.1 传输与帧

- **只用继承来的 stdin/stdout 管道**（`Bun.spawn(..., { stdin: 'pipe', stdout: 'pipe' })`）。管道天然满足「不许开一个谁都能连的本地端口」：**没有监听面**，句柄只存在于父子之间，没有端口可扫、没有 ACL 要配。
- 帧 = 4 字节大端长度 + UTF-8 JSON 正文；**上限 1 MiB**（复用 `MAX_PLUGIN_MESSAGE_BYTES` 同值，不新造第二个常量）。
- 体验插件用的是换行分隔 JSON——本协议不用换行分隔，理由是 bash 的 stdout 里天然含换行，长度前缀更省事（这里刻意与子进程插件不同，因为它还要承载文本流）。

> **已被取代（pool 分支）**：ADR-106 决策 2 选 TCP loopback + 双 token（detached + gateway restart adopt 语义否决 stdio 控制通道）；帧 = NDJSON JSON-RPC 8MiB，复用 child wire。child 分支仍 stdio。本节「只用管道 / 长度前缀 1MiB」保留作设计史；§6.2 尖刺读数为 e79b9faa 基线历史实测。

### 4.2 生命周期帧

| 帧 | 方向 | 载荷要点 |
|---|---|---|
| `toolhost.hello` | core → sidecar（首帧） | `{ protocol: 1, epoch, token, plugin_dirs, tools: [...] }`；`token` 只经帧下发（**不进 env**，env 会被工具的子进程继承——沿用 0.48 M1 口径） |
| `toolhost.ready` | sidecar → core | `{ protocol: 1, epoch, version, tools: [{ name, needs_ctx, path_fields, has_dynamic_check }] }` |
| `toolhost.heartbeat` | 双向 | 15s 心跳（与子进程插件 `PLUGIN_TIMEOUTS.heartbeat` 同值） |
| `toolhost.drain` | core → sidecar | 停止接新调用；在飞调用最多等 `drain_ms`（缺省 2000ms，与 `PLUGIN_TIMEOUTS.terminate` 同值）后 `SIGKILL` |

握手超时 5s、单调用默认 deadline 与 `PLUGIN_TIMEOUTS.rpc` 对齐（10s，可被 `tool.timeout` 覆盖）。

### 4.3 调用帧

| 帧 | 方向 | 载荷要点 |
|---|---|---|
| `tool.call.request` | core → sidecar | `{ call_id, name, args, deadline_ms, cwd, boundary: { deny_paths, allowed_roots }, session_id, run_id }` |
| `tool.check` | core → sidecar（**可选**） | 工具的**动态** `checkPermission`（插件代码）走一次 RPC：`{ call_id, name, args } → { decision: allow\|deny\|ask, reason? }`。只在 `has_dynamic_check` 时发生；声明式边界不在这里 |
| `tool.call.progress` | sidecar → core | `{ call_id, seq, kind: 'stdout'\|'stderr'\|'notice', bytes }`；**v1 不把它喂给模型**（闸是一次性的、整条的），只用于 liveness / UI / async bash 唤醒；速率上限 4 帧/秒/调用，超出丢弃并计数 |
| `tool.call.result` | sidecar → core | `{ call_id, ok, content, bounded_hint?, original_bytes, elapsed_ms }` |
| `tool.call.failed` | sidecar → core | `{ call_id, code, message }`，`code ∈ {tool_error, timeout, denied, bad_args, host_crashed}` |
| `tool.call.cancel` | core → sidecar | `{ call_id, reason }`；best-effort，sidecar 必须同时响应自己的 deadline |

**结果语义必须是「一条最终结果」**：模型看到的东西不变（一条 `role: tool` 消息，过 16k 闸）。为什么不做流式喂模型：闸的输入是**整条结果**（`estimateTokens` + 头尾切 + 落盘路径），逐段喂会绕过它，且 1 MB 的搬运只值 6.4ms（§6.2），没有为省这点延迟拆协议的必要。

### 4.4 超时与取消（两侧都要有，且语义一致）

- core 侧：`deadline = min(tool.timeout ?? ∞, tool_host.call_timeout ?? 10s)`；到点先发 `tool.call.cancel`，再等 `cancel_grace`（缺省 500ms），仍未回则判 `timeout` 并把该 `call_id` 记为孤儿（后到的 `result` 直接丢弃，**不写回上下文**）。
- sidecar 侧：自己也算 deadline（防止 core 卡住），到点杀子进程组并回 `tool.call.failed{timeout}`。
- 取消的真语义：`bash` 要杀**进程组**，不是杀 shell（今天 in-process 的 `ctx.signal` 就是这么用的）。
- 幂等：同一 `call_id` 的第二次 `result` 一律丢弃并计数 `tool_host.duplicate_result`。

### 4.5 有界（三个维度都要写死）

| 维度 | 缺省 | 超界行为 |
|---|---|---|
| 帧 | 1 MiB | 丢弃 + 计数 + `tool_host.frame_too_large`（不静默截断，截断的 JSON 是毒药） |
| 单结果 | 2 MiB 传输上限；>16k token 由 core 闸裁 | sidecar 先落盘（与今天 `boundToolResult` 同一个落盘根），只回「头 + 尾 + 落盘路径」 |
| 队列 | 每工具 `queue_max=32`、全局 `queue_max=256` | **立即** `tool_host_queue_full`（不排队、不静默等）——排队会让模型以为工具慢，而不是「被限流了」 |
| 并发 | 每工具 `concurrency=4`、全局 16 | 同队列（进队列即有界等待，队列满即失败） |

**注意**：今天 `concurrencySafe` 的批并发是「无上限的 Promise.all」。上配额等于改行为——这条要单独立项、单独观测，不要捆在解耦里一次做完（否则出问题分不清是解耦还是限流）。

> **未实现且明确不建**（ADR-106 决策 7 / 备选 (h)，宪法 10）：现态无队列——engine 进程级准入（ΣinFlight ≥ maxInflight 或 rss 软阈）快拒 `engine_busy`，node LB 拦截换家重试；loop 批并发仍无上限。本节队列 / 每工具信号量取值保留作设计史。

### 4.6 崩溃后语义

| 情形 | core 收成什么 | run 怎么走 |
|---|---|---|
| 管道 EOF / 进程退出 | 在飞调用 → `tool_host_crashed`（`ok:false`），**不自动重试** | 按普通工具失败折回上下文，loop 继续（模型自己决定要不要再来一次） |
| 重启预算内（10 分钟 3 次，同子进程插件） | 立即重拉 sidecar，失败的调用已经是失败，不补 | 同上 |
| 超出预算 | sidecar 标记 disabled；该路由的工具**保留在工具面但调用即失败** `tool_host_unavailable` | 不谎报 `Tool "bash" not found`——「能力在但坏了」与「能力不存在」是两条不同的事实，模型的动作不一样 |
| 结果已发出但 core 已判超时 | 丢弃 + `tool_host.duplicate_result` 计数 | 与 in-process 的 timeout 语义一致（今天也是「超时即失败」） |

## 5. 安全与边界（写死，不许在实现期打折）

1. **执行侧不能是更松的入口**。三条校验必须同时成立：
   - **core 侧声明式校验（新增）**：工具在 `toolhost.ready` 里自报 `path_fields`（如 `bash: ['cwd']`、`read: ['path']`）。core 在**下发前**用与 sidecar 同一份实现校验 `deny_paths` / `allowed_roots`：命中 denylist → 直接 `deny`（**不发出请求**，更不下发 `ask`）。
   - **sidecar 侧执行时校验（保留）**：在真正 `open()` 的那一刻再判一次 `realpath`（TOCTOU 窗口只能缩，不能消）。
   - **一致性**：两侧**共用同一个判定模块**（`deny_paths` / `allowed_roots` / `realpath` 只有一份实现），sidecar 不得自带一份宽松版本；配置由 core 在 `tool.call.request.boundary` 里下发，不从 sidecar 自己的配置里读（否则「两侧」变成「两个配置」）。
2. **IPC 只允许回环**：默认（也是唯一推荐）形态是**继承管道**，没有监听面。若某天必须用 socket（跨语言 sidecar / 平台限制），硬约束是：只能 AF_UNIX / 命名管道，权限 `0600`（win32 走 named pipe 默认 ACL），**禁止 TCP 回环端口做默认实现**；握手令牌每 epoch 轮换、只经 `toolhost.hello` 下发、不进 env、不进 argv（argv 会进 ps）。**（TCP 回环禁令已被 ADR-106 决策 2 取代——pool = TCP loopback + 首帧 auth 双 token 分权，用户裁决 C；named pipe 硬化留演进。远程 engine 仍禁止。）**
3. **结果仍走同一个出口闸**：`gateToolResult` 只在 core，`bounded` 回执是**进程内 WeakMap**，所以 sidecar 无法自称「我已经裁过了」——这个不可伪造性是设计的一部分，实现时不许改成「sidecar 回一个 bounded=true 就原样放行」。**（已被取代：P2 批准跨进程 bounded 回执——worker 用同一份 core 闸自裁，信封 `bounded:true` 只是声称，host forward 校验形状后在 host ctx re-mark（`engine-client/forward.ts`），回执仍是 host 侧 WeakMap；裁剪实现单源，见 [tools.md](tools.md#engine-exec)。）**
4. **凭据与环境**：sidecar 不拿 gateway / node token（无 HTTP 面，也不需要）；只拿自己的插件目录与只读工具目录；`dataDir` 写权按需声明（同子进程插件的 `permissions.fs` 口径）。工具内部起的子进程继承 sidecar 的 env，所以 env 里不许有秘密。
5. **审计不新增通道**：`tool.call.started` / `tool.call.completed` 仍由 core 发（单一出口），事件里加 `host: 'inproc' | 'sidecar'` 与 `host_epoch`；sidecar 自己的日志只写自己的日志文件（1 MiB 轮转，同子进程插件）。
6. **配额与权限是两件事**：配额满返回的是 `tool_host_queue_full`，不是 `deny`——前者是资源，后者是策略，混成一个词会让模型的补救动作错。

## 6. 尖刺读数（先量再设计）

### 6.1 口径

- 平台：**win32 bun 1.3.9（经 WSL 互操作调用）**，仓库在 `/mnt/d`（drvfs）。**不是** Linux 原生 bun，也不是纯 Windows 目录——`spawn` 一侧被这个口径抬高了（子进程是 Windows 进程）。CI 的 Linux bun 下的读数**待测**（§6.6）。
- 基线：`e79b9faa`，2026-11-17 18:36–18:52 +0800（读数随环境变，**别把下面的数字当指标**，复现脚本见附录 A）。
- 方法：帧 = 4 字节大端长度 + JSON，一问一答（RTT，不是吞吐）；每次测量先 3 次热身。IPC 与模块重载各 2 轮，in-process 各 5 轮；表里给每轮的中位数。

### 6.2 同机 IPC 往返（一次性尖刺）

| 载荷 | stdio 管道（无监听端口） | 回环 TCP 127.0.0.1（对照） |
|---|---|---|
| 1 KB | **0.151 / 0.142 ms** | 0.039 / 0.057 ms |
| 100 KB | **0.278 / 0.260 ms** | 0.791 / 0.701 ms |
| 1 MB | **6.753 / 6.378 ms** | 32.300 / 29.520 ms |
| 冷启动 → 首帧回包 | 84.1 / 44.5 ms | 53.7 / 47.8 ms |

读法：
- 小载荷上管道比 TCP **慢约 2.5–3 倍**（0.15ms vs 0.05ms）——但这是 0.1ms 级的差别，对任何工具都可忽略；**大载荷上管道反超**（1 MB：6.4ms vs 30ms），因为 TCP 多一次用户态 ↔ 内核拷贝。
- 所以「管道更安全」不是拿性能换的，管道在 1 MB 上还更快。
- 冷启动 45–85ms 是 sidecar 生命周期预算的基础数：**值得长时间常驻，绝不 per-call spawn**（per-call 会让 `read` 从 1.7ms 变成 50ms+ —— 推算，见 §6.5）。

### 6.3 in-process 工具调用基线（真 ToolPipeline，不是模拟）

| 项目 | 各轮中位数（bash 5 轮 / read 3 轮） | 备注 |
|---|---|---|
| `bash echo hi` 端到端（MemoryPluginHost + basic-tools + 权限 + 闸） | **98.15 / 97.90 / 103.78 / 101.32 / 102.03 ms** | 输出 `退出码: 0\nstdout:\nhi\n`，与真机路径同一份 handler |
| 裸 `Bun.spawn('bash', ['-c', 'echo hi'])` | 87.38 / 82.65 / 102.76 / 81.90 / 87.82 ms | 同一个进程里同一命令，剥掉管道 |
| 两者中位数差 | 10.76 / 15.24 / 1.02 / 19.41 / 14.21 ms | **落在 spawn 自身噪声里**（p95 到 220ms）。结论：管道自身开销 **上界 20ms**，精确值待测；裸 spawn 占端到端的 **84–100%**（逐轮算），即「耗时几乎全是进程创建」 |
| `read`（40 行）端到端 | **1.69 / 1.70 / 1.71 ms**（每轮 200 次） | 无子进程，纯文件 I/O：**延迟最敏感的工具** |
| 插件 `install` + 管道构造 | 1.7 / 1.7 / 5.8 ms | A 形热换的天花板成本就在这里 |

### 6.4 形态 A 的关键未知量：模块重载（一次性尖刺）

`import(url + '?reload=N')` 各 50 次，**循环结束后调用 `global.gc()` 再读数**：

| 模块 | 首次 | 中位 | p95 | RSS 净增（50 次，GC 后） | 折算 |
|---|---|---|---|---|---|
| 20 行小模块 | 1.82 / 2.22 ms | 0.12 / 0.16 ms | 0.99 / 1.16 ms | **+25.99 / +26.14 MB** | ≈0.5 MB/次 |
| `basic-tools`（≈2.4k 行） | 30.42 / 33.74 ms | 1.02 / 1.34 ms | 1.78 / 1.79 ms | **+84.47 / +65.67 MB** | ≈**1.3 MB/次** |

读法：**GC 回收不了**（收尾前 214.28 MB → GC 后 219.13 MB，还在涨）——模块表按 URL 留记录，这是规范行为，不是泄漏 bug。所以 A2 的「重载」在内存上是**单调**的：50 次开发循环 = +66 MB，200 次 = +260 MB（按 1.3 MB/次线性外推，未实测到 200 次）。**这是「A 形只能有限次热重载」这条结论的唯一依据，也是它最值得复核的一条**（换 Linux 原生 bun 复测，§6.6）。

### 6.5 若走 sidecar：单次调用增加多少（**推算**，用 6.2–6.4 的数）

| 工具 | 今天 | sidecar 推算增量 | 相对增幅 | 判断 |
|---|---|---|---|---|
| `bash`（1 KB 结果） | 98–104 ms | +0.15 ms（一个 pipe 往返） | **+0.15%** | 可忽略 |
| `bash`（1 MB 结果） | — | +6.4 ms（大帧搬运） | 相对命令本身仍可忽略 | 可接受 |
| `web_fetch`（网络 RTT 量级，本单未测） | 数百 ms | +0.15…0.3 ms | **<0.1%** | 可忽略 |
| `read`（40 行） | 1.7 ms | +0.15 ms | **+9%** | **不值得**（这是「read/edit 不搬」的量化依据） |
| 热重载一次工具代码 | node 重启 **2.28 s**（+在飞 run 被打断） | 换 sidecar **45–85 ms** | ~1/30 | 主要收益 |
| 常驻内存 | 1 个进程 | +1 个进程（本单测到的 bun 进程基线是 **127 MB**，含脚本与已装载模块；纯空进程读数见 §6.6 第 3 条） | — | 成本，需按 no. 计入 |

## 7. 兼容与回退

- **开关**：`VESSEL_TOOL_HOST=inproc | sidecar`，**默认 `inproc`**（今天的行为一个字节不变）。可被 `config.yaml` 的同名键覆盖（env 优先，与其它 `VESSEL_*` 一致）。**（已被取代：现态是 YAML 双开关 `tools_engine.mode: child|pool` × `gateway.engine_pool.size`，缺省关零回归，无 `VESSEL_TOOL_HOST` env；未 wire 工具天然 in-process，无 engine in-process 模式。）**
- **路由粒度是每工具，不是每进程**：`tool_host.tools: { bash: sidecar, web_fetch: sidecar, read: inproc }`。**混合态是一等公民**，不是过渡期补丁：迁移顺序就是靠它一条条搬的。
- **旧插件不改就能跑**：`install(host)` 契约不变。B 形的接线方式是「core 注册一个代理 `ToolDefinition`，handler 把请求 marshal 到 sidecar」；插件作者不写一行新代码，也不需要知道 sidecar 存在。
- **工具面不因形态而变**：`listTools()` 仍只由 core 的 registry 产生；sidecar 在 `toolhost.ready` 里自报的工具集用来**对账**，不参与生成工具面。对账不一致 → **fail-closed**：该工具的调用立刻 `tool_host_surface_mismatch`，并如实上报（不偷偷降级成 in-process，否则「改了一半」会长期住在配置里）。
- **回退**：改一个配置项 + 一次 `gateway.reload`（不需要重启：路由表由 `tools` scope 的 applier 一并替换）。回退后工具面、schema、权限判定都不变——这也是「registry 留 core」的直接好处。
- **版本兼容**：`toolhost.hello/ready` 带 `protocol`（整数，不兼容就 +1）+ `version`（semver）。语义同 `engines.vessel`：**不支持就不握手**，core 回落到 inproc 并记一条 `tool_host.version_incompatible`，不尝试半途兼容。

## 8. 风险清单与判据

| # | 风险 | 为什么成立 | 压它的手段 |
|---|---|---|---|
| 1 | **双份实现漂移** | 两侧都要校验路径，两份实现必然分叉 | 判定只有一份实现，core 下发边界配置；sidecar 不许自己读配置 |
| 2 | **序列化不匹配** | `ToolContext` 带 events / signal / messages，不可序列化；先搬错工具会静默丢能力 | 工具在 `ready` 里自报 `needs_ctx`；有 `needs_ctx` 的工具**禁止**路由到 sidecar（启动期校验，不是运行期才发现） |
| 3 | **崩溃被误读成「可重试」** | `bash` 的副作用不可逆 | 明文：崩溃 = 调用失败，**不重试**；重复执行只能由模型显式决定 |
| 4 | **配额捆在解耦里做完** | 今天 `Promise.all` 无上限，上配额本身就是行为变更 | 分两单：先解耦（行为等价），再上配额（单独观测） |
| 5 | **延迟回退藏在长尾** | `read` +9% 不是平均值，是每次调用的固定税 | 路由判据（§3.3）；迁移动手前先在 shadow 模式下量同一工具两条路径 |
| 6 | **IPC 被做成监听端口** | 「本地端口」是最省事的实现，也是最容易变成一个谁都能连的入口 | 协议层只实现管道；socket 分支要单独评审 + 权限位 + 每 epoch 令牌 |
| 7 | **观测断点** | 跨进程后事件、日志、耗时各在一处，出问题先怀疑网络 | 事件仍由 core 单一出口发；`run.timing` 的 `tools_ms` 必须含 sidecar 往返；sidecar 日志独立文件 |
| 8 | **生命周期状态机本身是 bug 温床** | spawn / 握手 / 心跳 / drain / 重启预算 / 半死 | **照抄子进程插件那套**（10 分钟 3 次、15s 心跳、2s drain），不新造一套；先拿它当 golden |
| 9 | **win32 管道边界** | 本项目在 win32 上出过进程级段错误；跨进程 + 取消 + 流泵是已知的危险组合 | §6.6 第 6 条先测；失败模式按「宁可杀进程，不要半开」 |
| 10 | **复杂度税** | 协议 + 生命周期 + 超时 + 背压 + 版本 + 混合态，维护面比今天三个 reload scope 大一个量级 | §8.1 的判据：**不满足就不做** |

### 8.1 什么情况下这个改造**不值得**做

1. **改工具代码的频率 ≤ 每月一次**：A1 已经覆盖「配置 / 权限 / 工具面 / MCP」的热应用，剩下的只值一次 node 重启（2.28s）。
2. **崩溃主因不在工具代码**：0.58 那次是代理流泵的原生实现；修原生路径（已改 passthrough）比解耦便宜得多，且解耦不防这一类。
3. **没有「每工具配额」的真实诉求**：并发压力来自模型轮次（同一响应多个工具）而不是工具本身时，core 里加一个全局信号量就够了，不需要一个进程。
4. **工具面继续收缩**：本项目的判据是「能被其他工具替代的工具就不该存在」，工具数量在减少——需要隔离的工具越少，sidecar 的固定成本（一个常驻进程 + 一套状态机）越摊不开。
5. **`read` / `edit` / `write` 占调用量绝大头**：它们不该搬（+9%），那 B 的收益面就只剩 `bash` / web / MCP——如果这三类的调用占比本来就低，收益也就低。**先量调用分布，再决定要不要 B**（本文没有这份分布数据，标注为待测）。**（已被取代：四工具全搬 worker，见 banner 对照表。）**

```ts
  socket: { data(s, c) { pending = cat(pending, new Uint8Array(c)); const r = split(pending); pending = r.rest;
      for (const f of r.out) handle(f, (b) => s.write(b)); }, open() {}, close() {}, error() {} } });
} else { const w = Bun.stdout.writer();
  for await (const c of Bun.stdin.stream()) { pending = cat(pending, new Uint8Array(c));
    const r = split(pending); pending = r.rest; for (const f of r.out) handle(f, (b) => w.write(b)); w.flush(); } }
function cat(a: Uint8Array, b: Uint8Array) { if (a.byteLength === 0) return b;
  const o = new Uint8Array(a.byteLength + b.byteLength); o.set(a, 0); o.set(b, a.byteLength); return o; }
```
