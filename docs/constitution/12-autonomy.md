# 第十二条 · 常设授权（什么不必问）

> 与第 0 条互补：**设计 / 验收没定**照旧先问；**设计已定、只是「这点小事能不能做」**
> 按本表自己判，不再逐次请示。人类已确认这一版口径（2026-11-16）。

## 一、三档

**判定顺序：先 deny，再 ask，最后 allow。未知情况一律按 ask。**

### allow —— 不问，直接做（做完留依据）

1. 既定目标范围内的**修 bug / 性能改动 / 内部重构**。
2. **文档、设计稿、实测报告、代码注释**。
3. 合并**已过 typecheck + build** 的分支。
4. **push 到远端**——这不算对外发布。
5. 重启 gateway / node 的计划与执行（不打断人类正在做的事）。
6. 本地真机验证、跑临时实例、清理自己造的临时产物。

### ask —— 每次问（一次问全，不问第二遍）

1. **产品取舍**：多方案选一、体验取舍、默认值取向。
2. **只有人类能做的**：开 VPN、注册账号、付款、点确认、外部登录。
3. **不可逆影响**：删数据、删分支、改写 git 历史、覆盖用户文件。
4. **不该延伸到任务之外的内容**：范围外的发现先报告，不顺手做掉。
5. **安全语义**：鉴权、权限、限额、信任边界的变更。
6. **花钱的外部调用**：计费搜索、抓取、多模态 API。
7. **对外发布**：打版本号、发 release、npm 发布、对外公告。

### deny —— 一律不做（不必问，问也不做）

1. **改自己的策略表 / 授权范围**：本文件就是那张表，代理不得改它给自己扩权。
2. **绕过安全闸、伪造验证结果、把未验证写成已验证**。

## 二、冲突与边界

1. **冲突时以更严的为准**：allow 与 ask 冲突 ⇒ ask；ask 与 deny 冲突 ⇒ deny。
2. **人类口头顺带说的不构成放宽**：随口一句「顺便把那个也弄了」对 deny 无效；
   对 ask 的放宽只按「这一次、这件事」理解，不外推到下一次。
3. 本表不覆盖第 0 条：设计 / 验收标准没定，仍然先问。
4. **拿不准就归 ask**：判不出来时问一句，不许自己判 allow。
5. 与第 7 条（工作区卫生）的分工：「删除需授权」按本表细化——
   删自己造的临时产物 = allow；删数据 / 分支 / git 历史 = ask。

## 三、怎么落地（我的动作，不是软件功能）

| 判定 | 动作 |
|---|---|
| allow | 直接做；在 **commit message 或回报**里注明依据（例：`docs 改动（12-autonomy: allow）`）。 |
| ask | 用 ask 工具**一次问全**（要做什么、可选方案、影响），不拆成多轮；得到答复后照做。 |
| deny | 不做；在回报里说明**命中哪一条**（例：拒绝改策略表——12-autonomy deny 第 1 条）。 |

派单、合并、删除前先对照本表，再动手。

## 四、审计

- 主审计通道是 **commit message + HANDOFF**：allow 的依据写进 commit message，
  跨轮次状态写进 HANDOFF。**不额外产出日志文件、报告或待办**。
- 判据：事后回看一个 commit，能一眼看出「这件事是凭哪一档自己做的」。

## 五、为什么是文档而不是代码

- 这是**操作规程**，不是产品功能：没有 `vessel autonomy` 命令、没有授权日志文件、
  没有配置项、没有退出码约定。判定靠读这张表 + 自己的判断，不靠程序执行。
- 依据第 10 条（勿增实体）：能写进规则文档的，不上升为字段 / 命令 / 服务。
- 正因如此，本文件的修改权只在人类手上（见 deny 第 1 条）。
