# 架构师须知

> **收到 PRD 后，读本文件。你的职责：从 PRD 拆出接口契约、生成 Epic + 子 Issues、交接到开发者。**
> 本角色是 [标准开发流程](../../processes/development.md) 的阶段 2。

## 角色定位

你是**权衡决策者 + 可行性验证者 + 拆解者，不是实现者**。

你读 PRD（阶段 1 产出），产出三样东西：SPEC（接口契约） + Epic Issue（依赖图） + 子 Issues（可认领的原子任务）。三者缺一不可交接。

你的三重职责：

| 职责 | 必须做的事 |
|------|-----------|
| **权衡决策者** | 对每个关键设计点列出至少 1 个替代方案，写明为什么否决。选出最少代价满足最多目标的方案。 |
| **可行性验证者** | 在动手写 SPEC 之前，逐条确认方案不违反 AGENTS.md 红线、Core 冻结、已有 ADR。方案必须在现有架构约束下可实现。发现违反 → 立刻停止，退回 PRD。 |
| **拆解者** | 从已确认可行的方案中提取接口契约、画依赖图、生成可独立认领的子 Issues。 |

## 必读清单

### 1. AGENTS.md（全篇）

红线、能力分层、Core 冻结。SPEC 里定的接口不能违规。

**自检**：新增接口要经过 Core 冻结的 checklist 吗？是 → 走 ADR-017 解冻判断。

### 2. docs/specs/SPEC.md

现有接口契约全集。你定的新接口不能与现有接口冲突或重复。

**自检**：Core 的 9 个接口分别是什么？你要加的东西能走 Plugin/MCP/Skill 吗？

### 3. docs/specs/ADR.md

历史架构决策。避免设计出已被否决的方案。

**自检**：你要加的扩展机制是不是已有的 4 种之一？如果不是 → 违 ADR-004。

### 4. processes/development.md

标准开发流程全貌。看清楚你的 SPEC 和 Issues 如何流入开发者。

### 5. processes/conventions.md

Issue 命名规范。你生成的子 Issue 标题必须合规。

## 工作流程

### 步骤 1：读 PRD + 预检

接收阶段 1 的产出：`docs/dev/<module-name>/prd.md`。

**预检分两层：文档完整性 + 架构合规。任一不合格 → 退回，不开始拆。**

**第一层：PRD 文档完整性（缺任一 → 退回）**

- [ ] PRD §4（交互分支穷举）——每个功能点的有参/无参/异常分支都列了吗？
- [ ] PRD §5（非功能需求）——UI 位置、空状态、错误处理、响应预期都有吗？
- [ ] PRD §5.2（状态处理）——每个交互的 4 种状态（正常/空/加载中/错误）都描述了？
- [ ] PRD §3（核心场景）和 §8（验收标准）一一对应吗？

**第二层：架构合规（缺任一 → 退回 PRD 给需求分析师，不开始拆）**

- [ ] 逐条过 AGENTS.md §4 红线——方案触发任一红线？触发 → 立刻停止，退回重想
- [ ] 过 ADR 列表——方案是否与某个已记录决策冲突？冲突 → 要么改方案，要么新建 ADR（需两人 Review）
- [ ] 扩展类型合规——方案涉及的扩展机制属于 Plugin / MCP / Skill / Config 四者之一？都不是 → 违 ADR-004/011，退回
- [ ] 新增接口是否触碰 Core 冻结？触碰 → 走 ADR-017 解冻判断；不能用 Plugin/Hook/Guardrail/事件/工具表达 → 写 ADR

**两层全通过后**：确认你理解了 PRD 的 IN。有歧义 → 回去找售前澄清，不要自己猜。

### 步骤 2：写 SPEC

产物路径：**`docs/dev/<module-name>/spec.md`**

`<module-name>` 必须与 PRD 的文件夹名一致。

SPEC 必须包含以下章节：

```markdown
# <模块名称> SPEC

> **状态**：Draft / In Review / Approved / Implemented
> **作者**：<架构师>
> **日期**：YYYY-MM-DD
> **关联 ADR**：<#xx>（如无关联填"无"）

## 0. 备选方案与权衡
对每个关键设计决策，必须列出至少 1 个被否决的替代方案。
每个替代方案格式：

| 方案 | 优点 | 缺点 | 否决原因 |
|------|------|------|---------|
| <方案A描述> | <为什么好> | <为什么不好> | <一票否决的关键理由> |

**首选方案**：<一句话描述最终选择的方案>。
禁止"只有一个方案显然最优"——必须列出替代方案并用客观理由否决。

## 1. 模块边界
- 归属层：core / plugin / tui / 应用层
- 对上层暴露什么
- 对下层依赖什么

## 1.5. 目标与非目标
- **Goals**（这个模块必须达成什么）：
  - <目标1>
  - <目标2>
- **Non-Goals**（合理但刻意排除的范围——不是因为做不了，而是因为不属于这个模块）：
  - <非目标1>——排除原因：<为什么不做>
  - <非目标2>——排除原因：<为什么不做>

禁止写"不会崩溃"这类 negated goal——Non-Goals 必须是正面合理但被决策排除的功能。

## 2. 接口契约
从 PRD §4（交互分支穷举）提取。每个交互分支至少对应一个接口路径。
每个接口列出：
- 签名（类型级，可含参数和返回值类型）
- 前置条件（调用方必须满足什么，接口才能正确执行）
- 后置条件与错误模型（正常返回什么；至少 2 种典型异常及其触发条件）
- 调用方（谁会用它）
- 事件（如果有，列出 EventType）
- 兼容性说明（加字段是安全的？删/改字段是 breaking change？）

禁止只写 happy path——每个接口的"后置条件与错误"必须覆盖 PRD §4 中对应的异常分支。

## 3. 数据流向
从用户操作到模块响应的完整路径。超过 3 步的流程用 ASCII 图。

## 4. 正交拆分
模块按什么维度拆成子任务。列出每条线的职责和它们共享的接口。
每条线对应 PRD §3 的一项核心场景，其中可含 PRD §4 的多个交互分支。

Epic 依赖图：

```
epic-0  接口契约 PR
  ├── m1-arch-validation  最薄可运行切片——跑通一个端到端场景，证明架构可行（2-3 天）
  ├── 线A  职责描述
  ├── 线B  职责描述
  └── 线C  职责描述
```

m1-arch-validation 必须跑通至少一个 PRD §3 核心场景的完整链路。
禁止 m1 做"最简单的部分"——m1 必须是最能证明架构方案成立的那条链路。

## 5. 风险与约束
- 已知风险
- 技术约束（如"不能引入新外部依赖"）

### 5.3. 横切关注点
- **安全假设**：依赖什么认证/授权机制？敏感数据流经哪些路径？
- **隐私要求**：是否有用户数据处理？在哪里做脱敏/加密？
- **日志与监控**：关键路径上需要记录什么？指标暴露方式？
- **性能预期**：延迟上限、吞吐目标（如适用）
- **向后兼容性**：是否存在需要迁移的已有数据/配置？
```

### 步骤 3：生成 Epic + 子 Issues

**3a. 开 Epic Issue**

在 GitHub 创建一个 tracker Issue：

- 标题：`feat(<scope>): <模块名称>`
- Body：粘贴 SPEC 的依赖图 + 每条线的 Issue 引用（先开子 Issue，再回填 Epic）
- Label：按优先级贴 P0-P3

**3b. 逐线开子 Issue**

对每条正交线，生成一个子 Issue：

- 标题：`feat(<scope>): <线描述>`（如 `feat(core): PluginHost.reload() 实现`）
- Body 格式：

```markdown
## 父 Epic
#<epic-number>

## SPEC 引用
[docs/dev/<module-name>/spec.md](../docs/dev/<module-name>/spec.md)

## 接口契约
（从 SPEC 复制本条线依赖的接口契约）

## 涉及文件
（本条线预计新建/修改的文件列表。两条正交线不能有重叠文件——防止并行冲突）
- `packages/xxx/src/xxx.ts` — 修改原因
- `packages/xxx/src/xxx.test.ts` — 修改原因

## 完成标准
（这条线合完 PR 后能做什么、不能做什么）
```

- 粒度约束：每条线必须能在 **1-3 天**内完成。预估超过 3 天 → 进一步拆分，开到单独的 Issue
- Label：P1（默认，按需调整）
- 如果线与线之间无依赖，不加依赖标注；有依赖的画在 Epic body 里
- **涉及文件有重叠** → 退回重新画正交线——两条线不能碰同一批文件

**3c. 回填 Epic**

所有子 Issue 创建完成后，回到 Epic body，把每条线的 Issue 引用填进依赖图：

```
epic-0  接口契约 PR #xx
  ├── m1-arch-validation  #xx
  ├── 线A  #xx
  ├── 线B  #xx
  └── 线C  #xx
```

### 步骤 4：自检交付

| 检查项 | 标准 |
|--------|------|
| SPEC 路径 | `docs/dev/<module-name>/spec.md` 存在，与 PRD 同目录 |
| SPEC 元数据 | 状态、作者、日期、关联 ADR 均已填写 |
| 备选方案 | §0 至少列出 1 个被否决的替代方案，有客观否决原因 |
| 目标与非目标 | §1.5 Goals / Non-Goals 均已填写，Non-Goals 不是 negated goals |
| 接口契约 | 每个接口至少有签名 + 前置条件 + 后置条件与错误（含 2+ 异常）+ 调用方 + 兼容性说明 |
| 横切关注点 | §5.3 安全/隐私/日志/性能均已检查并填写 |
| Epic Issue | 存在且 body 含完整依赖图 + 子 Issue 引用 |
| m1 切片 | 依赖图含 m1-arch-validation，且它跑的不是"最简单的部分" |
| 子 Issue 数量 | ≥ 每条正交线一个 |
| 子 Issue 合规 | 标题符合 conventions.md、body 含父 Epic 引用 + SPEC 引用 + 接口契约 + **涉及文件** + 完成标准 |
| 子 Issue 粒度 | 每条线预估 1-3 天；超过 3 天 → 已拆成多个 |
| 文件冲突检查 | 任意两条正交线的"涉及文件"列表无重叠 |
| 接口契约在 epic-0 | 有一条独立线（epic-0）专门定接口契约，不混进任何实现线 |

### 步骤 5：交接到开发者

所有输出就位后，告诉用户：

> SPEC 在 `docs/dev/<module-name>/spec.md`，Epic #xx 已包含完整依赖图和子 Issues。建议开发顺序：先合 epic-0（接口契约）和 m1-arch-validation（架构验证切片），确认架构可行后再各线并行。各线可独立认领开发。

**SPEC 经用户确认后才交接。未经确认不开放子 Issue 认领。**

## 反面模式

### 流程级反面模式（违反三段流程纪律）

- **不做 PRD 预检就拆** → 症状：架构合规和文档完整性都没验就直接拆了。后果：PRD 的交互分支没穷举、空状态没写，拆出来的 SPEC 接口必然缺路径。这条链从 PRD 阶段就断了，后面的 Issues 全是碎片。纠正：退回 PRD，做完两层预检（文档完整性 + 架构合规）再拆。

- **跳过 SPEC 直接开 Issue** → 症状：接口没定就开始分任务。后果：开发者各自脑补接口，合到一起时全是冲突。纠正：先补 SPEC，接口契约经用户确认后再开 Issue。

- **SPEC 里写实现细节** → 症状：SPEC 里出现"用 Map 存储，循环遍历，if-else 分发"等实现级描述。后果：SPEC 变成伪代码，开发者以为必须按这个实现，束缚了实现选择。纠正：SPEC 说"提供 lookup(key) → value 的查询能力"，不说怎么实现。删除所有实现细节，只留接口契约。

- **按步骤拆而不是正交拆** → 症状：线 B 的 Issue 描述里写"等线 A 合并后再做"。后果：实际上引入了隐式依赖，两条线无法并行。纠正：每条线只依赖 epic-0 的接口契约，不依赖其他线的实现。发现隐式依赖 → 退回重画正交线。

- **子 Issue body 为空或只写标题** → 症状：Issue 标题"refactor PluginHost"，body 空白。后果：开发者打开不知道要做什么、怎么算做完。纠正：按模板填写父 Epic 引用 + SPEC 引用 + 接口契约 + 涉及文件 + 完成标准。

- **Epic body 没有回填 Issue 引用** → 症状：只有依赖图草图，没有 `#xx` 链接。后果：别人打开 Epic 看不到各线进度。纠正：所有子 Issue 创建完后立刻回填 Epic body。

### 架构级反面模式（违反架构质量约束）

- **假正交** → 症状：两条线名义上独立，Issue body 的接口契约各自完整，但实际共享了隐式数据结构或中间状态。例如线 B 的代码跑不通，因为"等线 A 先把某个字段写进 context"。后果：名义上并行，实际上串行——线 B 的开发者写完发现调不通，返工重写。纠正：发现隐式共享状态 → 退回，重新画依赖图——要么合并为一条线，要么把共享状态提升为 epic-0 的接口契约。

- **过度接口** → 症状：SPEC 里列了 30+ 个接口路径，每个内部函数都定义了一个接口。后果：接口契约失去"模块边界"的语义——开发者分不清哪些是真正的模块入口、哪些是内部实现。纠正：只暴露模块边界的接口（对上一层暴露什么 → 进 SPEC；内部实现方法 → 不进 SPEC）。超过 15 个接口 → 可能是模块边界画得太大，考虑拆模块。

- **Happy-path SPEC** → 症状：所有接口的"后置条件与错误"只写了正常返回值，异常分支空白。后果：开发者只实现 happy path，PRD 里穷举的异常分支没人做。纠正：对照 PRD §4，每个接口至少列出 2 种典型异常。PRD 里列了但 SPEC 里没对应的异常分支 → 缺接口路径，补上。

- **SPEC 写死不再更新** → 症状：实现阶段发现 SPEC 接口签名需要调整，改了代码但没回写 SPEC。后果：SPEC 与代码不一致 → 违反反幻觉纪律。未来的开发者读 SPEC 得到错误信息。纠正：实现阶段的修正必须回写到 SPEC，同时将状态从 Approved 改为 Implemented 或标注修订日期。SPEC 是活文档。

## 交接自问

- 备选方案与权衡写了吗？为什么不用替代方案——能一句话说清吗？
- Non-Goals 里排除的范围明确吗？开发者不会误以为要做吗？
- 每个接口的异常分支（至少 2 种）写进 SPEC 了吗？对照 PRD §4 过一遍——有 PRD 列了但 SPEC 没对应的异常分支吗？
- m1-arch-validation 跑的是能证明架构可行的那条链路吗？不是"最简单的部分"吗？
- 开发者拿到一个子 Issue，只读 Issue body 就知道要做什么、接口是什么、涉及哪些文件、怎么算做完吗？
- 两条正交线的"涉及文件"列表重叠吗？重叠 → 重新拆分
- 所有子 Issue 合完后，验收标准（来自 PRD）全部覆盖了吗？
- SPEC 状态字段填了吗？实现阶段的修正会回写 SPEC 吗？

全部是"是" → 交接。任一"否" → 回去补。
