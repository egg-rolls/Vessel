# 文档管理者须知

> **修改任何文档前，必须先读完本文件。按顺序读，读完一项自检一项。**
> 跳过任何一项 = 写出违反规范的文档，审查时会被打回。

## 为什么必须先读这些

Vessel 的文档分两层——永久文档（specs/guides/role/api）和临时文档（dev/）。永久文档是仓库的宪法：只讲设计是什么，不讲做到哪了。混入"当前""暂不""延后"等状态词 = 文档过期、歧义、误导。

角色文档体系说明见 [docs/role/README.md](README.md)。

更重要的是，**文档是写给 AI 读的**。DOC-STANDARD §7.1 定义了什么是好文档：不是给 AI 一个禁止清单，而是激活 AI 的判断力。你不先理解这个方法，写出来的文档不是在帮 AI——是在误导它。

## 必读清单（按此顺序）

### 1. AGENTS.md（全篇）

仓库通用概念手册。文档管理者重点关注 §3 文档加载策略、§5 反幻觉纪律。

**自检**：永久文档和临时文档的分界线在哪？AGENTS.md §3 的宪法级文档有哪些？

### 2. docs/specs/DOC-STANDARD.md（全篇）

重中之重是 §七 文档设计方法。§§1-6 是格式规范（怎么写才对），§7 是设计方法（怎么思考才对）。

**自检**：你能说出"checklist 式"和"心智模型式"文档的区别吗？§7.2 的写前走链路——你要改的文档属于哪类，走哪条链路？

### 3. 走对应链路（DOC-STANDARD §7.2）

改什么文档，先实际走一遍那个流程：

| 要修改的文档类型 | 写前必走 |
|----------------|---------|
| 开发流程类 | 读相关包代码，理解边界、耦合、测试结构 |
| 审查流程类 | 实际做一次审查：拉 diff、过 checklist |
| 测试类 | 实际跑一遍测试 |
| 架构类 | 读 SPEC + ADR + 代码实现，验证三者一致 |
| 协作流程类 | 实际走一遍 gh issue / gh pr / review 流程 |

**自检**：你实际走过对应流程了吗？还是只读了 DOC-STANDARD 的规则就开始写了？

### 4. processes/conventions.md

Commit message 格式、分支命名。**改文档也要提交——知道怎么写 commit message。**

**自检**：docs 变更的 commit type 是什么？scope 用什么？

### 5. processes/collaboration.md

gh CLI 操作技巧（创建 Issue/PR 的中文处理）。**写出文档后要提 PR——知道怎么操作。**

**自检**：为什么中文 PR 内容要分两步创建？`--body-file` 和 `$(cat)` 哪种更可靠？

## 改完后自检命令

永久文档（specs/guides/role/api）修改后必须执行：

```bash
grep -rn "当前\|目前\|现在\|暂时\|暂不\|延后\|近期\|以后\|pre-MVP\|MVP 范围\|Phase.*实现时" docs/specs/ docs/guides/ docs/role/ docs/api/
```

命中任一即违规，修改后方可提交。
