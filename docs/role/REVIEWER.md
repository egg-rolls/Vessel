# 审查者须知

> **审查 PR / 合并前，先按 [REVIEW-TODO.md](REVIEW-TODO.md) 完成全部必读（含 AGENTS.md），再读本文件。**
> 本文件是知识库——硬性门禁 10 条、审查流程、阻断规则、合并后操作。执行中按需查阅。

## 为什么必须先读这些

审查不是"看一眼代码对不对"——是验证代码是否符合架构约束、工程规范、安全红线。Vessel 有 10 条硬性门禁 + CI 四件套 + 反面模式清单。不读这些就审查 = 用直觉代替门禁，失去合并前验证的意义。

核心信条：**合并前验证，不合并后修复。**

## 审查流程

```
1. 获取分支 diff
2. 对照下方硬性门禁逐条检查
3. 对照 DEVELOPER.md §代码设计纪律 + GIT-WORKFLOW.md §六 做设计判断
4. 检查硬编码密钥（grep）
5. 确认 CI 状态（lint/typecheck/test/build）
6. 输出审查结论（通过/阻断 + 原因）
```

## 硬性门禁（全绿方可合并）

```
[ ] 依赖方向：core 未引用 tui/config/plugins
[ ] 能力分层：新代码按 AGENTS.md §6 决策树正确分类
[ ] 红线：未触碰 AGENTS.md §4 的任一条
[ ] 扩展机制：未新增第二套扩展路径
[ ] 事件类型：未引入事件名常量（ADR-030：开放字符串协议）
[ ] sync-in-async：异步路径中无同步阻塞调用
[ ] 半成品：无 NotImplementedError / 空实现进 core
[ ] 无硬编码密钥/Token/密码
[ ] 文档诚实：未声称未实现功能
[ ] 新能力：改 core 则必有 ADR
```

## 设计判断

结合已读的 DEVELOPER.md §代码设计纪律 + GIT-WORKFLOW.md §六 做出判断：

- 新增代码的边界清晰吗？每个核心逻辑能**独立测试**吗？
- 加了新 case / 事件 / 工具——是只加不改，还是趟了一遍核心分发？
- 有没有**抄近路**的信号：超长函数、重复逻辑、散落魔法值、`as` 满屏飞？
- 这些信号是否有**有意识的设计决策**支撑？

**判断权在审查者手中**——信号是提醒多看一眼，不是阻断理由。但如果找不到解释，要求作者解释。

## CI 硬性门禁

```
bun run lint       → 必须通过
bun run typecheck  → 必须通过
bun test           → 必须通过
bun run build      → 必须通过
```

## 阻断规则

以下情况必须阻断合并：
- CI 任一项不通过
- 架构检查任一项不通过
- 发现硬编码密钥
- 分支有未解决的合并冲突
- "稍后修复"承诺——要求先修复再合

## 合并后

- GitHub PR "Squash and merge" 勾选 "Delete branch" 自动删除远程分支
- 确认 main push 成功
- 更新本地 main

- [ ] 所有硬性门禁都过了？
- [ ] 设计判断有依据（不是"感觉不对"）？
- [ ] CI 四灯全绿？
- [ ] 无硬编码密钥？
- [ ] 没有"稍后修复"承诺？
