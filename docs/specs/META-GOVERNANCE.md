# 规范的规范（META-GOVERNANCE）

> 本文档定义 Vessel 项目中**治理文档自身的准入标准、深度梯度、内容分类、修剪机制**。
> 永久规范：描述治理体系的设计原则，不描述当前在治理什么。
> 具体规范清单见 `docs/role/DOC-MANAGER.md` 必读清单。

---

## 一、核心公理

**规范为解决已发生（或极大概率将发生）的痛苦而存在，不为预防想象中的问题。**

规范有四种成本：编写成本、阅读成本、执行成本、更新维护成本。每一条规则都在交税。没有真实痛点，不新增规范。

---

## 二、准入判断：三条标准

新增一条规则或一份治理文档前，三条必须**全部满足**。任一不满足 → 不写进正式规范。

### 2.1 是否已反复踩过同类坑？

- ✅ 通过：同样的问题已发生 2 次及以上。
- ❌ 不通过：只是"未来有可能会出错"，从未实际发生。

```
例（通过）：需求散落 Issues、AI 反复猜测用户意图、同一功能修多次 → 需要 PRD 模板
例（不通过）：想象未来多人协作会文档乱放 → 仅你+Agent 两人，问题尚未发生
```

### 2.2 犯错的代价有多大？

- **高代价** → 值得正式规范：生产 bug、数据错误、分支被冲掉、需求跑偏导致大量代码作废。
- **低代价** → 不需要正式规范：文档位置稍乱、commit 信息偶尔潦草——改一下就行。

### 2.3 规则能否低成本被执行？

规则写了但没人/Agent 能做到 → 废纸。能执行 = 以下两种形态至少占一个：

1. **工具强制**（优先）：Issue 模板、CI 校验、Agent TODO 强制项、pre-commit 钩子。
2. **简短模板**（次选）：复制粘贴即可完成，不需要大段散文填写。

```
反例："所有需求都要完整填写来源、优先级、拆分理由"——但没有模板、没有工具
     → 人嫌麻烦跳过，Agent 也跳过 → 无效规范
```

## 三、深度梯度：四层递进

不一步到位。从 L0 往 L4 递进，按需升级。

| 层级 | 形式 | 篇幅 | 适用场景 |
|------|------|------|---------|
| **L0** 口头约定 | 脑子记住，不写文档 | 0 行 | 小项目、坑很少、仅你+Agent |
| **L1** 简短模板 | Markdown 片段、Issue 模板、代码注释 | 10-50 行 | 开始反复出现小问题；多数中小项目停在这里 |
| **L2** 正式文档 | 独立 md 文件，分章节，写"怎么做" | 50-200 行 | 多次踩坑，代价中等偏高 |
| **L3** 完备体系 | 全套方法论：来源、背景、例外、推理、反例 | 200+ 行 | 多人正式商业团队，持续踩大量高代价坑 |

**原则**：个人/小团队项目，上限 L1-L2。L3 的方法论存为个人学习笔记，不进入项目强制规范。

---

## 四、内容分类：三类分离

每条内容必须归类到以下三者之一。禁止混放。

| 类别 | 标记 | 存放位置 | 约束 |
|------|------|---------|------|
| 🔒 **强制规则** | "必须" | 项目规范文档 | 违反会出 bug/返工。尽可能绑定工具。 |
| 📖 **指导建议** | "推荐" | 规范文档末尾（独立小节） | 最佳实践，不强制。Agent 可不严格遵守。 |
| 🧠 **背景学习** | — | `notes/` 或个人笔记 | 理论、方法论、历史复盘。**Agent 默认不读取**。 |

### 4.1 判断标准

```
问：违反这条规则会出 bug 或导致返工吗？
  → 是 → 🔒 强制规则
  → 否 ↓

问：这条内容对人/Agent 的决策有帮助，但不遵守也不会出错？
  → 是 → 📖 指导建议
  → 否 ↓

问：这条内容用于理解"为什么这样做"而非"怎么做"？
  → 是 → 🧠 背景学习，放 notes/
```

### 4.2 Agent 专项约束

给 Agent 读的规范：

- 少叙事，多用列表。
- 能变成模板就不要写成大段文字描述。
- 区分【Agent 必须遵守】和【人类开发者阅读】的文档集。
- Agent 的上下文是有限资源——每多一行文档，就挤占一行推理空间。

## 五、修剪审计

每完成一个 Phase，对全部治理文档执行一轮删减。逐条问：

```
1. 如果删掉这条规则，最坏会发生什么？损失多大？
2. 过去一个 Phase，这条规则真正被执行过几次？
3. 能否把这条文字规范改成一个模板或工具，替代大段文字？
4. 这是强制必须做（🔒），还是最佳参考（📖），还是背景知识（🧠）？

→ 删掉损失很小 → 删除或移到 notes/
→ 只靠人自觉、无工具辅助 → 简化或降级为 📖
→ 属于 🧠 → 移到 notes/，从 Agent 阅读路径中移除
```

## 六、层级判定参考

以下展示治理模型如何对典型治理文档进行分类。新增文档时以此为参考基准。
具体文档的层级随项目阶段演进，实际判定以 §二（三条准入）和 §三（四层梯度）为准。

| 文档 | 层级 | 痛点来源 | 类别 |
|------|------|---------|------|
| `processes/conventions.md` | L1 | commit 格式不统一 | 🔒 |
| `docs/specs/ISSUE-SPEC.md` | L2 | Issue 缺标签、TUI 细节膨胀 | 🔒 |
| `docs/specs/GOVERNANCE.md` | L2 | 需求存放混乱 | 🔒 |
| `docs/dev/DEVELOPMENT-PLAN.md` | L2 | 不知道当前阶段和阻塞项 | 🔒 |
| `docs/specs/DOC-STANDARD.md` | L2 | 永久文档混入状态词 | 🔒 |
| `docs/specs/GIT-WORKFLOW.md` | L2 | main 被乱推、合并冲突 | 🔒 |
| `processes/collaboration.md` | L2 | 中文 CLI 出错、孤儿分支 | 🔒 |
| `docs/role/REQUIREMENTS-ANALYST.md` | L3 | 需求散落 Issues、AI 反复猜测用户意图 | 🔒 |
| `docs/role/ARCHITECT.md` | L3 | 接口未定义就开工、并行冲突 | 🔒 |
| `docs/role/DEVELOPER.md` | L2 | 代码硬规则、PR 模板、DoD | 🔒 |

### 6.1 L3 文档的降级使用规则

`REQUIREMENTS-ANALYST.md` 和 `ARCHITECT.md` 是 L3 完备模板。使用时按需降级：

| 场景 | 降级方式 |
|------|---------|
| Bug 修复（单人单天） | 跳过需求分析师和架构师阶段，直接 DEV-TODO |
| 小增强（单人 1-3 天） | PRD 只填 Problem Statement + 验收标准，不填全套 12 章 |
| 模块功能（多人协作、需接口契约） | 完整走 PRD → SPEC → Epic → Issues 全流程 |
| 大模块/新方向（影响排期） | 完整走 + 更新 DEVELOPMENT-PLAN.md |

判断标准：**改动涉及接口契约（其他人/Agent 需要知道"这个接口长什么样"）→ 走架构师阶段。不需要接口契约 → 不走。**
