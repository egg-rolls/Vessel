# 0.55 · 「发消息卡很久」的归因与修复

**一句话**：用户点发送之后，`ExecutionUnit.loadStoredHistory` 对时间线做**整份读**
（0.54 B3 的口径，18.3 s→0.3 s 那一单只修了 `sessions.events` 的读侧，**没修发送路径**）。
在我这份 58.5k 事件 / 6.2k 块的真实会话上它实测 **6.98–7.44 s**，占「点发送 → 第一个
`llm.request`」的 **92%**，而且这段时间**事件循环是阻塞的**（整个网关的 RPC 与事件帧一起停住）。
改成「上次折到哪 + 尾部续读」之后，热态第 2/3 次发送由 **6.81 s / 7.63 s** 降到
**0.28 s / 0.17 s**，端到端由 **7.74 s / 8.68 s** 降到 **0.59 s / 0.46 s**。

> 全部读数来自**只读拷贝**（`D:\tmp\latency\...`，脚本同目录、不入库）与一台**临时网关**
> （`--serve 8799` + `--data-dir D:\tmp\latency\data`，避开 8642/8644）。会话
> `09f82ac6-82fc-4dcc-9693-a4991d663863` 的拷贝：`max(seq)=58,474`（起读时）、6,205 块、
> 34 MB、会话壳 1.8 MB / 977 条消息 / 413 个已占位 call id。

## 0. 结论摘要（先看这 6 条）

1. **「卡」不在 RPC 上，也不在占位 / 估算 / 会话壳**：`runs.start` 的 RPC 往返是 **3–6 ms**
   （冷启动首个 82 ms），用户正文与 `run.started` 之间 40–50 ms。真正卡住的是**RPC 之后**
   那段没有任何 `await` 可以喘气的工作：整份读时间线 + 投影 + 段起点。
2. **整份读 = 7.0 s，其余一切加起来 ≈ 0.45 s**（热态）。见 §2 的分段表。
3. **「裁剪工具结果时做了全量工作」这条怀疑，在这个会话上被证伪**：`planClearedToolResults`
   0.3 ms（413 个 id）、`withClearedToolResults` 7.8 ms、体积判据 0.4 ms、上界估算 6.8 ms
   （1.19 M 字符）。它们是 O(窗口) 的一次线性扫描，不是 O(消息数 × 已清 id 数)。
4. **上界估算器一次发送只被调 2 次**（请求视图 13.9 ms + 段起点 `tokenCount` 冷态 240 ms、
   热态 0.1 ms），没有「每调一次扫 1 M 字符」的放大。
5. **会话壳（1.8 MB json）不在热路径上做大头**：`session.load` 16–29 ms、`shell.save`
   26–39 ms（含 fsync），一次发送 2 读 2 写 ≈ 100 ms 量级。**它不是「卡很久」的原因**，
   但它是「卡 0.6 s」里仅次于读的那一档。
6. **改法不新建真相源、不改任何落盘格式**：把投影抽成可续算的游标（`ProjectionCursor`），
   用 0.56 的范围读只补尾巴；任一判据不成立就**整份读**并留痕。等价性用 302 种切法自证。

## 1. 链路与打点位置（先量）

「用户点发送 → 消息真的出去」在代码里是两段，中间有一次 `void`，这就是为什么
**RPC 很快、卡的感觉却很强**：

```
runs.start (RPC)
  └─ agent-control.start → AgentService.admit
       ├─ resolve 成员/body → ensureExecutionUnit（首条消息要 spawn body：+11.7 s，见 §6.3）
       ├─ trackInbox（inbox hold）+ submitMessage → scheduler.submit
       └─ startExecutionUnitRun  ── void ──► executeExecutionUnitTurn
                                              └─ ExecutionUnit.executeRun
                                                   ├─ acquireSessionLease
                                                   ├─ composeRunSystemPrompt
                                                   ├─ loadStoredHistory      ← 整份读在这里
                                                   ├─ seedWorkingContext / 锚点
                                                   ├─ compactAtSegmentStart  ← 段起点压缩判定
                                                   ├─ freezeSegmentClearedToolResults（占位集合）
                                                   ├─ publish run.started
                                                   └─ 初始 writeRunRecord + saveSessionState
                                                        └─ runToolCallingLoop → buildRequestMessages
                                                             → estimateRequestViewTokens
                                                             → publish llm.request
```

`runs.start` 在 `void executeExecutionUnitTurn(...)` 那一行就返回了，所以 **RPC 不在关键路径上**；
但 `executeExecutionUnitTurn` 的前半段（整份读 + 投影 + 段起点）是**同步占满事件循环**的
（读的 JSON.parse、投影的两遍循环、`reconcile` 的签名计算都在微任务里跑），于是：

- 用户看到的「卡」= 网关进不去任何 RPC / 推不出任何事件帧的那几秒；
- 连 `runs.get` 轮询本身都会超时（实测 instrumentation 期出现过 `TimeoutError`）。

打点方式：`performance.now()` 差 + 已落盘事件的 `ts`（`run.started` / `user.message` /
`llm.request` 的 `ts` 都来自同一个时钟），所以**分段表不需要修改任何口径**。

## 4. 修法（语义逐条等价）

**投影本身是折叠（fold）**：`fold(fold(∅, A), B) === fold(∅, A ++ B)`。而窗口只会 append，
所以「上一次已经折到 seq = N 的消息 + 日志里 N 之后那一段」与「整份重投影」逐条相同。

| 文件 | 改什么 | 量 |
| --- | --- | --- |
| `session/project-messages.ts` | 抽出 `ProjectionCursor` / `createProjectionCursor` / `extendProjection`；`projectMessages()` 变成「空游标 + 一次 extend」（**只有一份折叠实现**）。游标额外记录 `seq` / `count` / `lastRequestTokens` / `rewoundSeen`（原来 `execution-unit` 里那三个派生量各有一份实现，现在都从游标出） | +147 |
| `runtime/execution-unit.ts` | `loadStoredHistory` 改「取游标 ⇒（日志头 == 已折到的 seq）一条不读 /（头更大）范围读 `sinceSeq` 之后那段并折进去 /（任一判据不成立）丢游标 + 整份读」。新增 `restoreProjection` / `rememberProjection` / `isContiguousTail` 与 3 个上界常量 | +217 |

**判据（不成立只许放宽，绝不许窄化）**——`isContiguousTail`：

1. 有数据；
2. 没读满 `PROJECTION_TAIL_MAX_EVENTS = 2000`（读满 ⇒ 尾巴比一段还长，不知道日志头在哪）；
3. 起点严格新于已折到的 seq（重叠 / 倒退 ⇒ 文件被换过）；
4. seq 严格递增，且最后一条**正好等于** `lastSeq()`（中间有洞 ⇒ 有别的东西动过盘）；
5. `lastSeq()` 缺失（实现没给）⇒ 不增量。

判据不成立时：`this.projectionCursors.delete(sessionId)` + `logger.debug('session projection
cursor dropped')` + **整份读**。**永远不会**出现「少给几条然后正常返回」。

**上界（第十一条）**：`PROJECTION_TAIL_MAX_EVENTS=2000`（与前端首屏一段同量级）、
`PROJECTION_CURSOR_MAX_SESSIONS=2`（EU 正常只服务一个 session，rotate 窗口会短暂看到两个）、
`PROJECTION_CURSOR_MAX_TOOL_CALLS=20_000`（超了就不留游标 ⇒ 内存有界，代价是下次整份读）。

**已知的唯一共享面**：游标里的消息对象与窗口里的是同一批（不深拷贝 —— 视图 1.3 MB，每次
发送复制一遍没意义）。唯一的就地写是 `assignMessageIdentities`（`run_segment`，幂等 + 续编），
本模块每次 extend 末尾都会再跑一次，所以共享不产生漂移（这条写在 `ProjectionCursor` 注释里）。

**等价性自证**（脚本 `D:\tmp\latency\eq.ts`，不入库、不进门禁）：真实 58,552 条事件的日志，
对 **302 种切法**（1 处 / 中点 / 末尾前一条 / 100 等分 / 200 随机切点，`applyClearedReplacements`
两种口径）比较「整份投影」与「分段折叠」，JSON 逐条深比较 **全部相等**；派生量
`seq=58552 / count=58552` 与 `lastSeq()` 一致。

一处必须单独处理：切点可能落在 `llm.response` 与它的 `tool.call.started` **之间**
（整份投影的预扫描先收齐全部 started 再建消息，所以那条 assistant 的参数必然被 started 覆盖；
分段折叠时它已经在上一段建好了）。用 `backfillToolCallStarts` 在本段末尾补齐 —— 正常段一次
都不会走到（`emittedHere` 已过滤）。

## 5. 改前 / 改后（同一会话、同一临时网关、同一台机器）

热态 = 同一进程第 2、3 次发送（用户真实体感就是这一档）。

| 指标 | 改前 | 改后 | 倍数 |
| --- | --- | --- | --- |
| 请求 → `run.started`（第 2 次 / 第 3 次） | 6,811 ms / 7,634 ms | **279 ms / 173 ms** | 24× / 44× |
| `user.message` → `llm.request` | 928 ms / 1,041 ms | **306 ms / 283 ms** | 3.0× / 3.7× |
| **端到端：点发送 → 第一个请求** | **7,739 ms / 8,675 ms** | **585 ms / 456 ms** | **13× / 19×** |
| 其中「读日志」 | 6,979–7,388 ms（整份） | **116 / 133 ms**（尾部 8–9 条，走 0.56 范围读） | ~55× |
| `shell.load` | 16–29 ms | 23.6–28.9 ms | 不变 |
| `reconcile` | 20–37 ms | 20–31.7 ms | 不变 |
| `compactAtSegmentStart` | 0.1 ms（热） | 0.1 ms | 不变 |
| `initialSave` | 66–103 ms | 135–198 ms | 同档噪声（这段主要是 fsync） |
| 首次发送（冷态，body spawn + 整份读） | 20,743 ms | 20,743 ms | **不变**（见 §6.3） |

**尾部读 116–133 ms 为什么不是 4 ms**：0.56 设计里「缺省一页 100 条 ≈ 4–8 ms」是**纯读**
成本；实测这一档里还包含 `settled()`（写者排空）、`readdir` 6,205 个块名、`wal.manifest`
二分定位、以及 `lastSeq()`（wal 尾 + 尾块）。离线量到的同一段：`lastSeq` 2.7 ms、
`tail-100` 30.6 ms、`tail-500` 25.2 ms。所以发送路径现在剩下的是**固定定位开销 ~120 ms**，
与事件条数几乎无关 —— 这一档已经和「一次 `sessions.get`（119.7 ms）」同量级，不再是瓶颈。

## 6. 顺手：三件附带结论

### 6.1 RPC 固定开销 250–350 ms 的构成（同一台机器、loopback HTTP、同进程、热态 median/5 次）

| RPC | 中位耗时 | 响应字节 | 说明 |
| --- | --- | --- | --- |
| `health.get` | **0.7 ms** | 0.8 KiB | 传输 + 信封 + JSON 就是这一档 |
| `agents.tree` | 0.8 ms | 0.1 KiB | 同上 |
| `capabilities.list` | 4.8 ms | 65.3 KiB | 载荷序列化开始显形 |
| `sessions.get` `message_limit=0` | 0.6 ms | 0.1 KiB | 早退，不读壳 |
| `sessions.get` `message_limit=1` | **119.7 ms** | 1.6 KiB | **会话壳 1.8 MB load+parse + 派生摘要** |
| `sessions.get` `message_limit=200` | 148.9 ms | 213.6 KiB | 再 +29 ms（取消息 + 序列化 214 KiB） |
| `sessions.events limit=100` | **163.5 ms** | 34.4 KiB | 范围读的固定定位开销（见 §5 末段） |
| `sessions.events limit=500` | **352.8 ms** | 184.9 KiB | +189 ms ≈ 一页 500 条的块扇出 + 185 KiB 载荷 |
| `runs.start` | 5.8 ms | 0.2 KiB | 只到 `scheduler.submit`，**不含**跑一轮 |

**结论：这个环境下「固定开销」不是传输（0.6–0.9 ms），而是两次 O(会话) 的读**——
一次是「为了存在性校验就把 1.8 MB 会话壳读+parse」（`sessions.get`：0.6 → 119.7 ms 的跳变
就是它），一次是「时间线范围读的固定定位」（`sessions.events`：163.5 ms 起）。
250–350 ms 那一档对应的是「`sessions.get` + `sessions.events(页顶)` 串起来」的形状，
**与 WS 帧传输无关**；要再降只能动这两处（§7）。

### 6.2 「现场 39.9 s vs 基线平台 18.8 s」的 2 倍差

**做不到用活集/并发解释**，只能给一条**同向**的旁证：同一段整份读代码、同一份 34 MB 拷贝，
在新进程里第 1/2/3 次读是 **1,238 / 1,209 / 3,969 ms**（JS 堆 0.9 MB → 55 MB），
在真机网关（堆几百 MB、6k 块 + 34 MB 会话在活集里）是 **6,979–7,388 ms**。
也就是说「同一段代码在长寿进程里慢 3–6 倍」是**可复现**的，方向和 2 倍差一致；
但我**没有** 39.9 s 那台环境的读数，所以不能把 2 倍差归因成「活集/并发」——
如实说：**未解释**，与 0.56 §10 的结论同档。

### 6.3 顺带发现（本单不改，留给下一单）

1. **网关起来后的第一条消息额外付 ≈ 11.7 s**（`ensureExecutionUnit` / body spawn：插件安装、
   工具表拼装、`ensureRuntime`）。它一次性，但头一条消息的体感是 20.7 s。
2. **`sessions.get` 为了一次存在性校验就 load 1.8 MB 壳**（0.6 → 119.7 ms）。
   首屏四页 + 一次 `sessions.get` 就接近 700 ms，这一档比「范围读」本身贵。
3. **`sessions.events` 的范围读固定定位 ~160 ms**（一次 `readdir` 6,205 个块名 + manifest 二分
   + `lastSeq`）。0.56 的实现按「页」付这笔钱，首屏四页就付四次。
4. **测量过程里的一个未解现象**：装上逐段打点（往 stderr 写）之后，**同一进程的第 2 次发送
   偶尔会卡死**（100% CPU、事件循环不响应、只剩 `loadStoredHistory` 之前的打点）。把打点
   全部撤掉后，同样的 3 轮发送连续跑通（改前改后各验证一次）。我没有定位到根因，
   所以**不声称**它是产品 bug，也不排除是我那版打点自身的副作用（stderr 写入 / 审计字段）。
   如果后面有人再装打点，这条要复现一次。

## 7. 未做 / 下一步（按收益排序）

1. **尾部读的固定开销**（116–133 ms）：`readdir` 6209 个块名可以按「manifest 二分 + 顺序开块」
   省掉（`blocks.ts` 已经有 manifest；缺的是「不需要全量 names」的路径）。收益：发送 0.28 s → 0.1 s 档。
2. **`sessions.get` 的存在性校验不要读整份壳**：库层已经有 `listRich` 缓存与 `stat` 短路，
   但 `sessions.get` 走的是 `load()`。收益：首屏/刷新每页 −120 ms。
