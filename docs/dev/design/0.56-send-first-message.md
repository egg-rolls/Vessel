# 0.56 · 「重启后第一条消息：输入框清空了、列表里却没有」

**一句话**：chat 发送**没有本地先行渲染**，消息只能等**服务端回显**；而服务端回显
（`user.message`）排在「body spawn + `loadStoredHistory` 整份读」之后。进程刚重启时
这两样都全额付出，于是「点发送 → 屏幕出东西」是一个**几秒到几十秒的空窗**；空窗里
用户再发一条，它就按队列语义进了 inbox（这不是 bug，见 §3）。

---

## 1. 链路（打点位置）

```
点发送  apps/web  ChatView → runs.start (RPC)
  └─ serve gateway → src/run-control.ts → AgentService.admit
       ├─ resolve 成员/body → ensureExecutionUnit（createBinding + entryFor）
       ├─ ensureRuntime            ← body spawn（0.56 前 admit **await** 它）
       ├─ trackInbox（inbox hold）+ emitMessageQueued + submitMessage
       └─ startExecutionUnitRun ── void ─► executeExecutionUnitTurn
            └─ ExecutionUnit.executeRun
                 ├─ acquireSessionLease
                 ├─ loadStoredHistory      ← 重启后没有进程内游标 ⇒ 整份读
                 ├─ compactAtSegmentStart / freezeSegmentClearedToolResults
                 ├─ publish run.started
                 └─ publish user.message   ← **前端从这一刻才可能显示这条消息**
```

## 2. 先量（真机，58,645 事件 / 6,205 块的会话只读拷贝）

| # | 段 | 读数 | 说明 |
| --- | --- | --- | --- |
| ① | `runs.start` RPC → 返回 | 冷态含 spawn（见 ③）；热态 0.6–6 ms | 0.55 §2 已量 |
| ② | `eventLog.lastSeq` | **3.9 ms** | 尾窗 + 尾块，不读整份 |
| ③ | `loadStoredHistory` 整份读（`eventLog.read()`） | **998.7 ms** | 58,645 条 34 MB；长寿网关里同一段是 6.98–7.44 s（0.55 §2 ⑦） |
| ④ | 折叠 `extendProjection` | **9.5 ms** | 58,645 事件 → 994 条消息 |
| ⑤ | **尾部续读**（`sinceSeq` + `limit`） | **12.1 ms**（尾巴 50 条） | 0.56 范围读 |
| ⑥ | body spawn | 0.55 §6.3 记 **≈ 11.7 s**（真机）；本单**没有**重新量到（见 §5） | 插件安装 + 工具表拼装 + EU 构造 |

**第一段超时的位置就是 ③**（以及在冷态叠在它前面的 ⑥）：两者都在 `user.message`
发布**之前**，且都不在 RPC 返回**之后**能被打断的地方 —— 用户看到的就是空白消息区。

### 2.1 第二条消息为什么进 inbox（不是 bug）

`admit` 的顺序是「inbox hold → 入 body mailbox → scheduler.submit」。body 正在跑时
scheduler 里同一 body 只有一个 run，第二条**排队**（`status: queued`），消息按设计
落 durable inbox 并 `hold` 成 pending（`trackInbox` 是唯一 hold 写入点）—— 这一层是
「不丢消息」的写前日志，不是失败。**它保持不变**，本单只把「第一条的可见延迟」压下去。

## 3. 修法

### A. 投影游标落盘（`packages/core/src/session/projection-cache.ts`）

`projectionCursors` 是**进程内** Map（`PROJECTION_CURSOR_MAX_SESSIONS = 2`），重启 /
换 body 就空 ⇒ 第一次发送必然整份读。现在把游标**也**写成一份快照
`sessions/<id>.projection.json`（原子写、`durable: false`、best-effort、永不抛），
读侧变成三级回退：

```
内存游标（热态） → 落盘快照（重启/换 body） → 整份读（没有任何可用游标）
```

- **写点**：① 整份读刚成功（不留白付一次）；② run 收尾 `finishEventLog` 之后
  （把本轮事件折进去，让下次重启的尾巴只剩几条）。两处都是**同步序列化 + 异步落盘**：
  游标里的消息对象与活动窗口共享，交给异步写者去序列化会写出半截视图。
- **判据没有豁免权**：落盘快照与内存游标走**同一段代码**（`isContiguousTail`：有数据 /
  没读满 2000 条预算 / 起点严格新于已折 seq / seq 严格递增且末条 == `lastSeq()`）。
  不成立 ⇒ 删内存游标 + 删快照 + `logger.debug('session projection cursor dropped',
  {source})` + 整份读。**永远不会**「少给几条然后正常返回」。
- **不进 `reconcileCachedProjection`**：那条路径的硬约束是「不读会话壳里的任何游标」，
  本单没有碰它 —— 快照装的是**日志的折叠**，不是壳里的视图。
- **读口形状**：`ProjectionCachePort` 挂在 `RunJournalFactory` 上（装配层唯一给「写能力」
  的地方），EU 的读路径仍然只有只读事件日志口。

**等价性（真机数据自证）**：58,645 条事件，取 27 个切点（1/2/3、中点、倒数 2/1、全长、
10 等分、10 个随机点），「切成两段 + 快照 JSON 落盘再读回 + 折叠尾巴」与「整份投影」
逐条 JSON 深比较：**checked=24 / skipped=3（前三刀折出来没有消息，按设计不存）/
mismatches=0**。脚本用生产代码（`serializeProjectionCursor` / `FileProjectionCache` /
`cursorFromProjectionSnapshot`），不是另写一份。

### B. body spawn 出关键路径（`packages/agent/src/service.ts`）

`admit` 里原来 `await this.ensureRuntime(entry)`：一条消息的 RPC 返回要等整具 body
把插件装完、工具表拼完、EU 构造完（真机秒级）。现在：

- `admit` 只 `startSpawn(entry)`（`void ensureRuntime(...).catch(warn)`）——**不等**；
- spawn 的唯一等待点留在 `startExecutionUnitRun`（D1 不变量：消息**出队 + 消费之前**
  body 必须起得来，这两件事今天就在那一处）；
- spawn 失败 ⇒ 那条 catch 现在会：`logger.error('agent.body.spawn_failed')` +
  `inbox.unhold`（消息回到 unread，人可以读回正文、下次准入重投）+ handle 收成
  `failed`（`run.failed` 可见 / `runs.get` 查得到）。**不再**有「RPC 直接抛
  `spawn_failed`，而消息还没落 inbox」那条会让人以为「发送失败但文案没了」的路。

## 4. C. 前端乐观渲染（设计，未实现）

**问题**：chat 走 `runs.start`，只有 `team-send.ts` 有本地先行渲染；chat 没有，所以
「输入框一清空 = 屏幕空着」。

**身份方案**（关键：不能靠正文，guardrail 会改写）：

1. 点击发送即生成 `pending_id = crypto.randomUUID()`，本地插入
   `{ kind: 'pending', pending_id, content, at }` 到当前会话的待确认队列（按会话 id 分桶，
   切会话不串）。
2. `runs.start` 返回的 `run_id` 立刻挂到这条 pending 上（`pending.runId`）——这是
   **首选合并键**：服务端回显的 `user.message` 事件 `data.run_id` 与 `run.started` 的
   `run_id` 同源，命中即「确认」，用它替换 pending。
3. 回显里**没有** `run_id` 的旧服务端（回退键，按序合并）：同一会话内一旦收到
   `user.message`，且它的 `content` 与队首 pending 的正文相同（或已知是 guardrail
   改写：`run.started.input` 前缀匹配）⇒ 认领队首那条。按**顺序**认领，不按内容全局匹配
   ——否则同一句话发两次会互相认领。
4. 认领成功后 pending 立即移除；服务端消息**不用**本地正文覆盖（正文权威永远在服务端，
   guardrail 改写要看得见）。
5. 超时（`runs.start` 失败 / 15 s 内没有任何 run 事件）⇒ pending 变成
   `{ kind: 'failed', reason }`：卡片显示「未发送 · 重试 / 删除」，重试复用同一条正文走
   同一个 `runs.start`，**不新开 pending**（同一 `pending_id` 保持到成功或人删掉）。
6. 刷新页面：pending 不进 transcript 持久层（它们只在客户端内存 + 一个
   `sessionStorage` 备份），刷新后只剩服务端投影 —— 「刷新后只有一份」的判据靠这一条。

**改动面**：`apps/web/src/domains/chat/ChatView.tsx`（发送处插入 pending + 订阅
`run.started`/`user.message`/`run.failed` 收敛）、新增 `pending-sends.ts`（状态机 +
合并键）、`transcript-items.ts`（**dup-hunt 刚改过 `inputsByRun`**：pending 作为**独立
条目类型**渲染，不进 `inputsByRun` 的认领集合，避免与「只收人类输入」的现有判据打架）。

**判据**：点击 → 同一帧出现灰态消息；服务端回显后转正且**不重复**；刷新后只剩一份；
断网/网关重启 ⇒ 变「发送失败 + 重试」，重试成功后只有一条。

**为什么本单没实现**：本机环境下这台 node 起不了一次 run（见 §5），前端改动没有任何
可验证路径；而这条改动正好压在 `transcript-items.ts` 的消息身份上（dup-hunt 刚合并），
盲改的风险大于收益。设计交给下一单（有可跑环境时）落地。

## 5. 本单没能验证的部分（如实记录）

1. **真机端到端「点发送 → 对方看到」的改前/改后读数：没有拿到。** 本机隔离网关
   （`--data-dir D:/tmp/send-first/data2`、假 provider）在**任何** `runs.start` 之后 3–5 s
   内进入事件循环阻塞：RSS 从数百 MB 涨到 **6.3 GB**、`/health` 超时、`node.log` 无新行
   （连 `executeRun` 入口的临时打点都没打印）、provider 一次请求都没发。**空会话同样复现**
   ⇒ 与会话大小、与投影快照无关；并且在**改任何代码之前**就已复现（02:34Z 首次观察）。
   0.55 §6.3 第 4 条记的是同一现象（「装上逐段打点之后……偶尔会卡死」），本单把它变成了
   **可稳定复现**，但没定位根因 —— 它值得单独一单（现象：`node start` + 第一次
   `runs.start` ⇒ 事件循环死、内存无界增长）。
2. 因此 A 的收益是**分段量**（§2 ③ vs ⑤：998.7 ms → 12.1 ms，同一会话、同一台机器、
   同一份数据）+ 24 刀等价性；不是端到端读数。**B 的 RPC 返回时间同样没有真机读数**。
3. A/B 的验证到此为止：`bun run typecheck` ✅、`bun run build` ✅（typecheck + lint）、
   A 的等价性 24/24。**没有**任何一条「已在真机网关上跑通」的说法。
