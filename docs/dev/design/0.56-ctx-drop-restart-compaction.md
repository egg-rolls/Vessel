# 重启后同一会话的请求长度掉一大截（ctx-drop）

会话：`09f82ac6-82fc-4dcc-9693-a4991d663863`（main 自己那条，1M 预算的 placeholder 会话）。
现象：重启 gateway 之后，同一会话的请求消息数 / 估算 token 双双掉一大截。

## 1. 掉的那一截是什么

是一段 **compaction（压缩）**：766 条消息被一条 1441 字符的摘要替换。

事件日志（只读副本）里的直接读数：

| seq | 事件 | 读数 |
| --- | --- | --- |
| 125421 | `llm.request`（重启前最后一条） | 1940 条消息 / estimated 616,696 / context_max 1,000,000 |
| 125660 | `run.completed`（旧进程最后一次 run 收尾） | — |
| 125661 | `context.compacted`（**新进程第一个段起点**，run 72cc6123） | removed 766 / remaining 1175 / reason auto |
| 125662 | `message.compaction` | kept 1173 / removed 766 / 摘要 1441 字符 |
| 125670 | `llm.request`（重启后第一条） | **1179 条消息 / estimated 362,951** |

差：−761 条消息、−253,745 estimated tokens（−41%）。同一段里 `llm.response` 回报的
`prompt_tokens` 也从 616,378 掉到 362,9xx 量级，所以这是**真的**请求变小，不是显示口径。

不是另外两个嫌疑：

- **老消息整体不进请求**：不存在这种机制；请求永远从窗口整窗出发（`buildRequestMessages`）。
- **老工具结果变占位符**（`core.context_projection` = placeholder，keepRecentMax 10 / 5% / volumeRatio 0.2）：
  这条在重启前后**逐条相同**（同一份 `SessionState.cleared_tool_call_ids`、同一份
  `context_projection`），段起点只冻结一次；它省的是请求视图里 90 条工具结果的正文
  （约 144k tokens），而且**原文还在事件日志里、可按需重读**，不是损失。

机制名与位置：

- 压缩判定：`packages/core/src/context/context-manager.ts:1500` `shouldCompact()`
  → `this.tokenCount > max * threshold || isOverMessageCap() || volumeExceeded`。
- 触发点：`packages/core/src/runtime/execution-unit.ts:1111` `compactAtSegmentStart()`
  （**只在段起点**跑：每个 run 的起点 / resume）。
- 替换语义：`ContextManager.applyCompaction()` → `applyCompactionToMessages()`（摘要插到头部，
  被摘要覆盖的消息从窗口里删掉）。

## 2. 为什么偏偏是重启之后

判据只有一个数会因重启而变：**锚点系数（anchor.ratio）**。

`tokenCount = max(round(整窗上界估算 × factor), provider 地板)`，其中
`factor = anchorRatio`（实测比值 ≈1.0）或 **`NO_ANCHOR_SAFETY_MARGIN = 1.15`**（没有锚点时）。
锚点来自会话壳的 `SessionState.context_anchor`，由 `adoptStoredAnchor()` 在段起点注入；
**壳里没有这个字段、或锚点记的模型与当前模型不同 ⇒ 锚点作废 ⇒ 乘 1.15**。

把这份历史（`seq <= 125660` 折出来的 1885 条消息，整窗上界估算 **754,822**）分别喂给
同一条段起点路径，量出来的差别正好跨过 0.85 阈值：

| 段起点输入 | factor | tokenCount | 阈值 850,000 | 结果 |
| --- | --- | --- | --- | --- |
| 壳里有锚点（ratio 0.99948） | 0.99948 | 754,430 | 未越过 | **不压缩**，请求 1888 条 / 509,460 字符 |
| 壳里没有锚点、没有日志 | 1.15 | 867,898 | 越过 | **压缩**，请求 1115 条 / 308,880 字符 |
| 壳里没有锚点、有日志（本次修复后） | 0.99948（从日志复原） | 754,430 | 未越过 | **不压缩**，请求 1888 条 / 509,460 字符 |

三条都是同一份落盘历史、同一个 EU 代码路径，唯一变量就是锚点。所以：

- 「重启 ⇒ 更激进」不是设计，而是**判据用的口径与显示用的口径不是同一个**：
  - 显示 / 事件里的占用（`llm.request.estimated_tokens`、`context_max` 卡）走 runtime 账本，
    乘的是实测比值（≈1.0）；
  - 压缩判据 `shouldCompact()` 走**窗口自己**的 `tokenCount`，而窗口只有在
    `setContextAnchor` 被转发时才拿到锚点。**成员体的包装层 `RoleAwareContext`
    （`packages/agent/src/runtime.ts:150`）恰恰没有这个成员** —— 于是成员会话的判据
    永远退回 `NO_ANCHOR_SAFETY_MARGIN`（×1.15），对 1M 预算就是凭空多报 113k tokens。
  - 实测：那条请求 provider 真报 616,378（62%），判据却拿 867,898（87%）去比 85% 的线；
    换成实测比值同一个窗口只有 754,302（75%）—— **整条判定是这 15% 边距推过去的**。
- 旧代码把这条路走得**完全静默**：`context.compacted` 只写 removed / remaining / reason，
  没有估算、没有系数、没有阈值；`adoptStoredAnchor` 丢掉锚点时也不留任何日志。
  事后的会话数据里没有任何一处能回答「为什么这次压缩了」。
- 至于重启这一下戳动了哪个输入：判据的余量本来就只有 6~8%（754k 的窗口 vs 867k 的线
  之间还差 85k，而窗口内容在「壳缓存 / 日志整份折」两条路上实测差 6.6%：
  433,776 vs 460,682），所以**任何一个百分之几的输入抖动都能翻过线** ——
  重启恰好换掉了历史的复原来源（壳缓存 / 落盘快照 / 整份读）。这正是「判定不该依赖
  这种输入」的证据，而不是「重启改了规则」。

同一进程内的对照（证明「重启」本身不该有影响）：同一份历史放进同一个 EU 连跑两次，
第二次（热态）与第一次（冷启）的请求逐条相同（1888 vs 1890 条 = 只差这一轮新加的 2 条，
字符数 509,460 vs 509,469）。

排除项（都量过，均与重启无关）：

| 机制 / 参数 | 触发条件 | 重启前后是否变化 | 影响 |
| --- | --- | --- | --- |
| placeholder 占位（`core.context_projection`） | 段起点冻结，`cleared_tool_call_ids` 落盘 | **不变**（同一份集合 932 条 id） | 请求视图 −约 144k tokens，**可复原**（原文在日志里） |
| keepRecentTokenRatio 0.05 / keepRecentMax 10 / volumeRatio 0.2 | 声明里写死 | 不变 | 0 |
| compaction（`shouldCompact` token 维度） | `tokenCount > 0.85 × maxTokens` | **变了**：判据口径 ×1.15，显示口径 ×1.0 | **−253,745 tokens / −761 条消息，不可复原** |
| compaction 体积维度 | 保留的 10 条工具结果原文 > 20% 窗口 | 不变（实测 2,590 tokens） | 0 |
| 条数兜底（`isOverMessageCap`） | > 10,000 条 | 不变（1941 条） | 0 |
| `derived_upto_seq` / `projection_cache_seq` | **读侧不参与判定**（只作缓存提示） | 126553 / 126049 | 0 |
| `context_anchor` | 由壳注入；丢则退回 1.15 | **变了** | +15% 虚报 = 阈值提前 |

## 3. 这一截丢了有没有损失

- **占位（placeholder）那部分：不是损失。** 只改请求视图，原文留在事件日志里，工具可以
  重读；模型也知道被清掉的 call id（trim 卡）。
- **压缩那部分：是损失。** 766 条消息从窗口里删掉、被 1441 字符摘要取代，落盘时
  `SessionState.messages` 里也没有它们了（只剩日志里的历史事件）。运行时没有任何
  「按需读回被压缩消息」的通道 —— 模型再也看不到那些内容。所以这次「变小」是实打实的
  信息损失，不是口径变化。

## 4. 判定与修法

判定：**bug**（同一条会话、同一份落盘，重启前后「模型看到什么」不该变化）。错在两处，
都不在阈值本身：

1. **判据口径与显示口径不是同一个数**：判据读窗口的 `tokenCount`，而成员体包装层
   （`RoleAwareContext`）不转发 `setContextAnchor` ⇒ 窗口永远按 ×1.15 高报；
   显示读 runtime 账本 ⇒ 按实测比值。同一时刻两个数差 15%。
2. **判据的输入会静默消失**：锚点只活在一个可丢的字段里，丢了不留痕、也没有回落来源。

修法（本 commit，全部在 `packages/core/src/runtime/execution-unit.ts`）：

1. **判据口径收敛到账本**（`compactionWouldBeMarginOnly`）：段起点先按账本口径
   （= 显示口径 = 有锚点时的实测比值）算一次；如果「窗口说过线、账本说没过线」，
   这次**不压缩**，并记 `segment compaction skipped (no-anchor margin only)`（warn，
   带两个数、阈值、锚点比值、消息条数）。方向是安全的：少压不会撑爆（provider overflow
   + 下一个段起点兜住），而反方向是不可逆的信息损失，代价不对称。
   真的超预算时账本自己就过了线（实测：400k 窗口下 754,302 > 340,000 ⇒ 照常压缩）。
2. **锚点从事件日志复原**（`adoptStoredAnchor` + `recoverAnchorFromLog`）。锚点的两个分量
   本来就躺在日志里：`llm.response.usage.prompt_tokens`（分子）与
   `llm.request.estimated_tokens`（分母，同一口径的请求视图上界估算）。壳里的锚点不可用
   （缺字段 / 模型不一致）时，回扫一次尾部范围读（512 条，实测最后一条请求离日志尾 239 条）
   把它算回来，比值与 `recordProviderPromptTokens()` 完全同口径。于是
   **同一份落盘 ⇒ 同一个系数 ⇒ 同一个压缩判定**，重启等价。
   复原出来的锚点会随下一次 `saveSessionState` 写回壳，自愈。
3. **判据输入显式落盘**（`segmentCompactionDecision` → `context.compacted.data.decision`）：
   `trigger`（token / tool_result_volume / message_cap）、`estimate_upper`、`anchor_ratio`、
   `factor`、`token_count`（账本口径）、`window_token_count`（窗口口径）、`threshold`、
   `messages_before`、`context_max`，外加顶层 `messages_before`。请求长度掉一大截时，
   事件里直接写着「估算多少、乘了哪个系数、跟哪条线比」。
4. **不许静默**：壳里锚点不可用时记 `context anchor recovered from event log`（info，
   带 reason / ratio / prompt_tokens / request_estimate）；真的复原不出来才记
   `context anchor unavailable at segment start`（warn，说明本次判据用了 ×1.15 与后果）。

### 等价性验证（同一份落盘历史，逐条比请求）

脚本：`tmp/analysis/repro2.ts` / `repro3.ts`（临时目录，不提交）。fixture = 真实会话
`seq <= 125660` 折出来的 1885 条消息（`estimate_upper = 754,822`，与重启前最后一条请求同段）。

| E 壳里没有锚点、有日志（修复后） | **1888 条 / 509,460 字符** | **无** | 1.00974 |

成员体路径（`RoleAwareContext` 形态：不转发 `setContextAnchor`）：

| 场景 | 请求 | 压缩 |
| --- | --- | --- |
| W1 壳里有锚点（修复前：压缩） | **1888 条 / 509,460 字符** | 无 |

## 5. 残留风险 / 没回答完的

- **不能百分之百证明这次事故里最后一个百分点是哪个输入贡献的**：旧进程被 Bun segfault
  打断，重启前的会话壳已被后续 run 覆盖，落盘里没有留下那一刻的 `context_anchor`。
  能证明的是：判据用的数（867,898）比 provider 真报的占用（616,378）高 41%，
  而换成实测比值后同一个窗口只有 754,302 —— 也就是说这条会话是在**离真实上限还很远**
  的时候被压缩的；再叠上「窗口内容在壳缓存 / 日志整份折两条路上实测差 6.6%」，
  任何百分之几的抖动都足以翻线。修法把这两条路都堵上了（口径收敛 + 锚点可从日志复原），
  并把判据输入写进事件 —— 下一次同类问题可以直接从 `context.compacted.decision` 读答案。
- 备份兜底没有做：压缩本身仍然是不可逆的信息损失（设计如此，摘要取代原文）。
  如果要求「压缩也不许丢」，那是另一个决策（保留索引 + 按需读回通道），不在本次范围。
- `NO_ANCHOR_SAFETY_MARGIN` 仍然在完全没有历史（新会话 / 空日志 / 拿不到配对的用量）时
  生效 —— 那时没有可比的实测比值，保守是唯一选择；但它不再能因为「壳少一个字段」
  或「包装层不转发」而生效（`compactionWouldBeMarginOnly` 会拦下并留痕）。
