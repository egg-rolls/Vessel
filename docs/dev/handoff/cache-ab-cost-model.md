# placeholder vs passthrough：一笔账

标签约定：**[实测]** 直接来自本机落盘数据（events / runs / sessions 的字段）；
**[推算]** 由实测值换算（估算 token 折算、比例回推）；**[假设]** 本机观测不到、只能给区间或外部输入（单价、重取率）。

**一句话结论**：在本机 164 个真实会话（645 段 / 25,756 次请求）上，placeholder **净赚**——
省下的缓存 prompt 是 4.845 亿 token，失效代价 1,332 万 token，比例 **36 : 1**；
临界缓存折扣 **r\* = 2.68%**（只要 `p_cache_read / p_input > 2.68%` 就赚，deepseek-flash 的示例价是 10%）[实测+推算]。
按示例价折算：省 13.08、失效 3.24、**净 +9.85**，≈ 这批流量缓存 prompt 账单（94.77）的 **10.4%** [推算+假设单价]。
**但这个结论 100% 依赖「段内冻结」**：反事实（集合每条请求都重算）净收益从 **+9.85 变成 −72.37** [推算]。
唯一能翻符号的未测量项是**重取率**：贴现到口径 B 时，重取率 >37% 才会把 +9.85 吃光 [假设]。

## 1. 成本模型（可计算版本）

对每个 **run（= 一个段）** `s`、该段的每一次请求 `k = 1..N_s`：

| 项 | 公式 | 本机能否观测 |
| --- | --- | --- |
| 收益（每次请求都吃） | `Δ_s = Σ(被清工具结果原文 token − 占位 token)`，`save_s = Δ_s × N_s` | Δ [推算，原文 token 取运行时注记]，N_s [实测] |
| 收益折钱 | `benefit_s = save_s × P_cache_read` | 依赖单价 [假设] |
| 代价（只在集合变动的那一段的第一条请求上发生一次） | `sfx_s = prompt_first_s − prefix_tokens(p_s)`，`p_s` = 最早被**本段新清**的那条消息的位置 | prompt_first [实测]，prefix [实测标注] |
| 代价折钱（主口径） | `costMiss_s = sfx_s × (P_input − P_cache_read)` | 单价 [假设] |
| 代价折钱（重写口径，单列） | `costWrite_s = sfx_s × (P_cache_write − P_cache_read)` | 1.25x 溢价体现在 P_cache_write [假设] |
| 第三项代价（模型看不到被清结果 → 重取工具） | `costRecall_s = recall × Σ被清原文 token × P_input (+ 回填后跟着跑完本段 × P_cache_read)` | **观测不到** [假设] |
| 净收益 | `net_s = benefit_s − costMiss_s (− costRecall_s)`，正 = placeholder 更便宜 | — |

三条必须写清楚的结构性事实（都在代码里，不是判断）：

1. **占位集合在段起点算一次就冻结**，段内一个字都不改（`execution-unit.ts:806` `freezeSegmentClearedToolResults`，
   在 `execution-unit.ts:1589` 于 seed/压缩之后、本段第一条请求之前调用；`pop` 之后下一段起点重算）。
   ⇒ 段内请求是「同一条被截短的历史 + 追加」，前缀稳定，缓存继续命中。
2. **失效只发生在「本段比上段多清了新 id」的那一刻**，失效长度 = 从最早被新改写的那条消息到请求末尾。
   因为新被清的 id 一定**晚于**上一段已经清掉的位置（保留窗口只往后滑），所以受保护前缀一直延伸到上一段的边界，
   而不是整段历史。数据里可以直接看到这个单调性（§3.1 的 `pos` 列：5 → 32 → 98 → 103 → 142 → 151 → 171 → 227 → 242）。
3. **收益按请求次数重复，代价每个段只吃一次** ⇒ 是否划算 ≈ `Δ × N_s × r` vs `sfx × (1 − r)`，
   其中 `r = P_cache_read / P_input`。这就是为什么「便宜的缓存」越便宜、段越长，placeholder 越赚。

价格无关的判据（记进报告的就是它，不依赖单价）：

```
r* = Σsfx / (Σsave + Σsfx)      # 临界缓存折扣：p_read/p_in 高于 r* 就赚
```

价格来源：**仓库不内置任何厂商价**（`docs/operations/CONFIG.md:236`「Vessel 不内置任何厂商价格」；
`src/usage-pricing.ts` 的价格完全来自 `pricing.models.<model>` 配置）。本报告用
`docs/operations/CONFIG.md:230-234` 的**示例价**（volcengine/deepseek-flash：input 0.27 / cache_read 0.027 /
cache_write 0.3375 / output 1.10，每 1M token）当 **[假设]** 单价，真机请用 `--pricing` 换成自己的账单。
金额单位 = 价格表计价货币（本报告不假设它是人民币还是美元）。

## 2. 数据与方法

数据源（全部本机、无联网、不调模型 API）[实测]：

| 数据 | 用途 |
| --- | --- |
| `sessions/*.json` | 落盘消息正文（工具结果原文、`tool_call_id`、占位文本长度） |
| `runs/*.json` | 段（run）归属与会话排序 |
| `events/<run_id>.jsonl` | `llm.response.usage`（prompt / cache_read，逐请求）+ `context.changed{message_count, token_count}`（运行时逐条 token 注记）+ `llm.request.message_count`（段起点边界） |
| `usage/index.ndjson` | 交叉核对（本次未用于主账） |

**这份语料是「纯 passthrough」的真实流量**：全部 1,110 个事件文件里 `context.cleared_tool_result` 事件 **0 次**
（`execution-unit.ts:824` 才会发这个事件），说明 0.53「占位 default = passthrough」在本机是名副其实的；
只有 2 个会话的落盘历史带着更早版本写进去的 `[cleared ` 占位文本（已按闸门跳过）。
所以本报告的算法是：**在真实 passthrough 流量上反事实地算出 placeholder 的账**，
段起点体积、逐请求 usage、缓存命中率全部是这批真实运行实测出来的，不是模拟器。

三个关键取数决定：

1. **段起点边界**用 `llm.request.message_count`（实测），不用消息 timestamp
   （timestamp 边界在换 body / 接管类会话上会偏，实测过一版：`dc8c1bb9` 用 timestamp 会算成 0 条）。
2. **Δ 与失效前缀用运行时注记**，不用我自己的重算：
   运行时每次追加消息都会发 `context.changed{message_count, token_count}`，我按 `message_count` 建了两张表
   （`cum[mc]` = 前 mc 条的 token 估算，`delta[mc]` = 第 mc 条追加时的增量），于是
   「被清工具结果的原文 token」= `delta[位置]`、「失效位置之前的前缀」= `cum[位置−1]`，**都不是我猜的**。
   被清结果里 **100.0%** 拿到了注记（缺失时退回 `estimateMessageTokens` 并标记）。
3. **先证明估算值能折算成计费 token**：

```
$ bun scripts/measure-cache-ab.ts --validate
事件文件数: 1110，可比对请求数: 32280
比值 p05=0.9616  p50=0.9986  p95=1.0067
±5% 内占比: 95.0%
判定: 通过 —— 运行时估算可直接折算成计费 token
```

（`context.changed.token_count` 与供应商 `usage.prompt_tokens` 在同一 `message_count` 上对齐，
中位偏差 **0.14%**。这是本报告所有「token 数折钱」的前提，也是实测。）

三道闸门（宁可少算，不许算歪）：

| 闸门 | 跳过数 | 原因 |
| --- | --- | --- |
| 落盘历史里已有 `[cleared ` 占位文本 | 2 个会话 | 「不占位」基线在磁盘上已不可逆（原文只在 events 的 `tool.call.completed` 里） |
| 落盘历史里已有 `Auto Compact` 摘要 | 24 个会话 | 压缩把历史改写了，段起点重建不可信 |
| 段起点注记与实测 prompt 偏差 >35%（段起点 ≥20 条消息才判） | 1 段 / 645 段 | 疑似**供应商侧静默截断**（见 §6） |

会话分类判据（判据本身来自数据，不是手工打标）：工具结果 token 按「发起它的那次调用」的家族归属，
`team`（agent/ask/inbox/send/hire…）≥50% 或 工具调用 ≤2 / 请求 ≤4 → **团队短任务类**；
`read`（read/glob/grep/list…）≥50% → **长文件阅读类**；`bash` 等 shell ≥50% → **多工具大输出类**；其余 → **混合类**。

- **多工具大输出类**：主战场，净 +9.45，`r* = 2.3%`。会话级 30 赚 / 8 亏。

Δ×请求 = **484.5M**（= 13.80% 的 prompt token）。

## 4. 与既有结论对账

- **保留体积 ≤4.7%**（`docs/dev/handoff/measure-tool-result-clear.md`、`ADR-104:28`）↔ 本报告「省掉 13.80% 的 prompt token」：
  两者是同一个现象的不同分母（工具结果约占 prompt 的 14–15%，清掉其中 95%）。**不矛盾，互为交叉验证**。
- **ADR-104:29「前缀缓存上界 37.0% → 74.8%」**：那是「可缓存前缀**上界**」，不是已实现的成本。
  本报告实测这批流量在 passthrough 语义下缓存命中 **97.62%**，而一次集合变动只损失 `sfx × (1−r)`，
  摊到全场是 **0.379% 的 prompt token / 3.42% 的账单**。ADR 的结论（0.53 默认 passthrough）
  在**风险**上是保守的；本报告只补一句：**纯从钱看，冻结集合的 placeholder 在这批流量上是赚的（约 10% 账单）**。
- **ADR-104:50「段边界是硬成本」**：本报告把它量化了 —— 反事实「集合每条请求都重算」：

```
$ bun scripts/measure-cache-ab.ts --per-request-invalidation
合计  … netMiss -72.372053（反事实）
```

**冻结不变式值 +82.2**（+9.85 vs −72.37）。也就是说：只要有人把占位决策改成「每条请求重算」，
这笔账当天从赚 10% 变成亏到 76% 的账单。这比「占位本身贵不贵」重要得多。

## 5. 在线 AB 实验设计（**未执行，等批准**）

前提：本报告的结论是**离线折算**。要真花钱验证的只有两件事：
(a) 两个模式下供应商实际回传的 usage 是否如模型所述；(b) **重取率**（离线观测不到，也是唯一能翻符号的项）。

### 5.1 AB-1：usage 重放（便宜、确定，验 (a)）

**做法**：选真实会话，按段顺序把**落盘消息**投影成两份请求序列——
`A = passthrough`（原样）、`B = placeholder`（`withClearedToolResults(planClearedToolResults(段起点快照))`）——
以 `max_tokens=1` 顺序发出，只读回 `usage`（`prompt_tokens` / `cache_read_input_tokens` / `cache_creation_input_tokens`）。
**不让模型做任何决策**，所以没有 agent 行为上的非确定性。

- **选样标准**：① 该会话有 ≥60 次请求且 ≥10 条被清（否则 Δ≈0，测不出东西）；② 快照未含 `[cleared ` / `Auto Compact`；
  ③ 100% 请求拿到运行时注记；④ 覆盖三类 + 一个对照。给出具体 6 个（本机实测会话 id 前缀）：

| # | 会话 | 类型 | 段 | 请求 | Σprompt | 实测 hit | ΣΔ | 模型预测 net | 一轮两模式成本 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | `dc8c1bb9` | 多工具大输出 | 132 | 958 | 450.5M | 99.4% | 101.6M | **+2.26** | 22.69 |
| 2 | `e66c5e94` | 多工具大输出 | 147 | 809 | 340.7M | 99.6% | 80.0M | **+1.69** | 16.77 |
| 3 | `27d958ca` | 多工具大输出 | 6 | 444 | 104.4M | 99.3% | 20.4M | +0.48 | 5.43 |
| 4 | `45e21f17` | 长文件阅读 | 5 | 283 | 23.7M | 86.3% | 6.8M | +0.14 | 2.44 |
| 5 | `f189f83e` | 混合（**输家**） | 2 | 284 | 50.2M | 99.4% | 0.2M | −0.06 | 2.85 |
| 6 | `a48a17ce` | 团队短任务（**对照**，占位不触发） | 1 | 113 | 6.3M | 76.6% | 0 | 0.00 | 1.05 |

- **样本量（统计口径，不是拍脑袋）**：以「段」为配对单位，模型给出的段级净收益
  `mean = 63,502 token、sd = 68,741`（`dc8c1bb9`，132 段）/ `mean = 42,691、sd = 55,816`（`e66c5e94`，147 段），
  `n = (1.96+0.84)² σ²/δ²` → **9–14 段**即有 80% 功效。样本里两个大会话就带 279 段 ⇒ 统计上**严重过量**，
  所以样本量由「覆盖不同会话类型」而不是由显著性决定。
- **每个会话跑几轮**：**2 轮**（A/B 与 B/A 交替，抵消时间漂移）；**只有当某会话两轮的 Δcost 符号相反**
  才补第 3 轮。轮与轮之间间隔固定（缓存 TTL 之外，避免跨轮残留）。
- **非确定性控制**：同 model / 同 system prompt（两种模式复用**同一份**冻结字符串，因为 system prompt 是运行时拼的、
  不在落盘消息里）；同一组 `cache_control` 断点位置；串行背靠背发送保证段内缓存热；
  每轮记录逐请求 usage，若某段 `cache_read/prompt` 与模型预测偏离 >5% 或首请求 `cache_read > 0`（脏缓存），该轮作废重跑。
- **预估花费**（示例价 [假设]，`max_tokens=1` 使 completion 可忽略）：
  一轮（6 会话 × 两模式）= **≈51.24**；2 轮 **≈102.47**；3 轮 **≈153.71**。
  按实际合同价可能是示例价的 1–3 倍 ⇒ **申请额度上限 200**（本轮先用 2 轮 ≈102.5 的方案）。
  省钱旋钮：把每个段的重放截断到前 12 条请求（失效代价全在第 1 条，Δ 收益线性可外推）≈ 省 40–60%。
- **判定阈值**（先写死，不许事后改）：
  1. **主判**：6 个会话合计 `cost(B) − cost(A) < 0`，且落在模型预测 **±50%** 内（模型预测合计 **−4.52**，
     其中 5 个非对照会话净 +4.52）。通过 ⇒ 结论「placeholder 更便宜」升级为**在线实证**。
  2. **失效项单判**：B 相对 A 多出来的未命中 token（`Σ(prompt − cache_read)` 之差）≤ 0.5 × 实测节省（模型给的比值是 1:36，这里放 18 倍余量）。
  3. **形状判**：5 个非对照会话里 ≥4 个 Δcost 符号与模型一致；输家 `f189f83e` 判为「打平或小亏」即算命中。
  4. **对照判**：`a48a17ce` 两模式 billing 差 = 0（±0.5%）。若不为 0 ⇒ 测量链路有问题，整批作废。
  - **回滚闸**：单轮累计花费 > 60，或前 3 个会话的 Δcost 合计 > +1（符号反了）⇒ 立刻停，不改默认，回报并重推模型。

### 5.2 AB-2：行为 AB（贵，验 (b) 重取率与质量）

**做法**：选 8 个**新任务**（每类 2 个：长文件阅读 / 多工具大输出 / 团队短任务 / 混合），同一份任务描述
分别在两种模式下真跑（allowlist 固定工具集），每个任务每模式 3 次（温度 0 也无法完全消除，
所以用任务内配对 + 3 次取中位）。观测：`tool.call.completed` 条数与 token 量、工具结果重复率
（同一命令/同一文件被重复读）、`run.completed` 是否成功、以及逐请求 usage。

- **样本量**：8 任务 × 2 模式 × 3 次 = **48 个 run**；配对单位 = 任务（n=8），
  检出「重取率差 ≥10pp」的功效约 0.7，检出 ≥15pp 约 0.9 [假设：重取率 sd ≈10pp]。
- **预估花费**：以本机 run 中位数（≈40 次请求、均 prompt ≈130k）估，一个 run ≈ 5.2M prompt token
  ≈ **0.15–0.45**（示例价，取决于命中率）；48 个 run ⇒ **≈7–22**，再加 completion（output 价 1.10/1M）约 **+10**。
  总预算 **≤40**。**但**：行为 AB 会污染真实会话/工作目录，必须在**一次性租户 + 副本工作区**里跑。
- **判定阈值**：以 AB-1 得到的实测 `net` 为基准，把这里的观测重取率代入
  `net − recall × Σ被清原文 × (P_input + 后续请求 × P_cache_read)`；
  **只有净收益仍 >0 且质量指标不降（成功数不少、工具重复率上升 ≤20%）才算 placeholder 可以推给更多会话**。
- **判不动的边界**：若 AB-2 的观测重取率落在 **37%–71%**（口径 B / A 的盈亏平衡点），
  说明这笔账取决于任务分布，应按 §6 的开口项去决定「哪些会话值得开占位」，而不是全局一刀切。

**停在这里等批准**：AB-1 需要花钱（≈102.5，上限 200），我没有执行；AB-2 需要真实任务与隔离环境，更没有动。
