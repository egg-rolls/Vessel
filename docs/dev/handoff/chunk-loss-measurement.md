# 运行中刷新到底丢多少正文

> 测量时间 2026-11-14T13:11Z，worktree `chunk-loss`，基线 `235a40f8`。
> 样本：本机 217 个真实会话的 `events.ndjson`（166,807 条事件 / 1,048 个 run），
> 全部数字可用 `bun run scripts/measure-chunk-loss.ts --limit=400` 复现。
> 数据目录是活的（别的 agent 正在写），重跑时 run 数会漂 ±几，百分比稳定。

## 0. 一句话（可直接引用）

**环 1 万条槽 ≈ 一个 run 最后 200 秒的流式输出**（槽/秒为**实测**：长 run 46–52，短 run 27–33；「200 秒」是**推算** = 10000 ÷ 49.3）。所以：

> 跑 **5–10 分钟**的 run，**82%** 会在刷新时丢正文，一旦丢就**中位丢 9.8%**、最坏**整段 100%**；
> 跑 **>10 分钟**的 run，**94%** 会丢，**中位丢 21.6%**。全量（653 个有正文的 run）在 run 末尾刷新一次，
> 合计丢 **81.7 KB 正文（≈ 4.7 万字）**。
>
> 口径：run 时长 / 正文 / 段骨架是**实测**（`llm.stream.summary`）；「刷新时刻」与丢失字节是**构造重放 + 插值推算**
> —— 把 653 个真实 run 截断到末尾再按环容量求头部丢失。真·运行中快照见 §2.4（7/9 丢 60.5%–100%），方向一致。

而**放大到 5 万**：≤10 分钟的 run **一例不丢**，只剩 36 个超长 run，合计丢 **9.9 KB**（丢者中位 9.6%，最坏 39.6%）。
放到 20 万：**全部归零**（以上同为构造重放推算）。

但这两个数字都还有一层没说到，它改变结论 —— 见 §2.5：
**这些「丢掉的正文」100% 已经躺在磁盘的 `llm.response` 里**，丢的只是「屏幕能不能重建」，
不是数据。真正只存在于环里的正文，只有**一个在飞请求**的那一段（中位 1.7 KB，最大 13.8 KB）。

## 1. 量的是什么（每个数字都标口径）

`refresh-gap-design.md` §1.2 的丢失窗口：`lost = [1, ring.oldestSeq-1] ∩ {尚未变成 messages 的事件}`。
本报告把右边的集合实体化：**环是按 tenant 全局的 FIFO**（`event-buffer.ts`），一条事件占 1 槽，
刷新时只保最后 N 条，溢出的从**头部**淘汰 ⇒ 丢的一定是该 run 发布序列的一段**连续前缀**。

三种口径，全文严格区分：

| 标记 | 含义 | 本报告里的例子 |
| --- | --- | --- |
| **实测** | 磁盘 ndjson 里已有的事实，不是估计 | `llm.stream.summary` 的 `chunk_count / bytes / first_seq / last_seq / started_at / ended_at`；结构事件条数与 `ts`；`llm.response.data.content` 字节；`session.saved` 条数 |
| **推算** | 从实测插值/折算，误差可界定 | 段内 chunk 按时间均匀分布；被切断那一段按条数比例折算字节；字节→字符（实测 1:1.77）；并发摊薄 |
| **合成** | 重放构造的样本 | 把历史 run 截断到进度 p 造出的「运行中快照」 |

为什么 `llm.stream.summary` 足以支撑实测：`execution-unit.ts` 里 `recordStreamChunk` 对**每个**
chunk 都 `nextSeq += 1`（per-run，不重置），所以 `max(last_seq)` 就是该 run 的 chunk 事件条数；
段内 `last_seq - first_seq + 1 == chunk_count` 恒等成立 ⇒ **条数和字节都可对账，不需要 chunk 本体**。

## 2. 实测结果

### 2.1 环被谁吃掉了：正文只占 1.7%

这是整件事的根因，先看它：

```
环槽构成  合计 7,792,779 槽 = 正文 133,007(1.7%) + reasoning 2,091,978(26.8%)
                            + tool_call_delta/finish 5,428,447(69.7%) + 结构事件 139,347(1.8%)
```

- **正文（`text_delta`）只占环的 1.7%**；96.5% 的槽被 reasoning 和 **tool_call_delta** 吃掉。
  tool_call_delta 是大头：工具参数是一个 fragment 一个 chunk 流下来的，写一个大文件就是几千条。
- 正文 chunk 平均 **11.5 B/条**（实测 1.45 MB / 133,007 条）—— chunk 粒度极细，条数被放大。
- reasoning 总量是正文的 **16.4 倍**（23.86 MB / 209 万条），且 `llm.response` **不落** reasoning
  ⇒ reasoning 是 100% 环内独占，正文只是顺带被挤。

也就是说：**你的正文在和一个 60 倍于自己体量的噪声流抢同一个 FIFO。**

### 2.2 环 1 万 = 一个 run 最后 200 秒

| 时长桶 | run 数 | 典型槽/秒（实测） | 正文中位（实测） |
| --- | --- | --- | --- |
| ≤2 min | 332 | 32.6 | 1.9 KB |
| 2–5 min | 136 | 27.0 | 2.2 KB |
| 5–10 min | 67 | 46.5 | 2.1 KB |
| >10 min | 118 | 49.3 | 1.9 KB |

10,000 / 49.3 ≈ **203 秒**。这就是「1 万」的真实语义：**不是 1 万个事件的历史，是这个 run 最后 3 分半的输出**。
注意**时长和正文量几乎无关**（每个桶正文中位都是 ~2 KB）—— run 的时长被 reasoning 和工具吃掉了，
所以「跑得越久正文越多」这个直觉是错的，跑得越久只是**越容易被挤掉**。

### 2.5 关键反转：丢的正文 100% 已在磁盘

上一张表最后一列：**9/9 个未完成 run 的正文，100% 已被 `llm.response.data.content` 落盘**。
全量看也一样：653 个 run 的 `llm.response` 副本 = 1.45 MB = 流式正文的 **100.0%**（实测）。

因为 `llm.response` 是**每个 LLM 请求完成就写**的，不等 run 结束。所以：

| 正文的哪一部分 | 在哪 | 运行中刷新会不会丢 |
| --- | --- | --- |
| **已完成的那些请求**（可能占整个 run 的 100%） | 磁盘 `events.ndjson` 的 `llm.response`，**但不在 `messages`**（`sessions.get` 明确不派生，见 §4） | **数据不丢，屏幕丢** |
| **正在流式输出的那一个请求** | 只有 chunk，在环里 | 环装不下才真丢 |
| reasoning（全库 23.86 MB） | 只有 chunk，在环里（`llm.response` 不含 reasoning） | 环装不下就真丢（只影响回看） |

`messages` 侧为什么是 0：正文只在 `run.completed` / checkpoint 时经 `saveSessionState` 进 `SessionState`，
实测这些会话里 **run 运行期间 `session.saved` = 0 条**。所以运行中 `sessions.get` 拿不到本 run 的正文，
刷新后整个屏幕内容**只能**靠环重建 —— 这就是 100% 这个数字的来源。

**环到底该多大？** 唯一必须靠环的部分是「一个请求的在飞窗口」（实测）：

- 单请求 chunk 峰值：中位 **903** 条，p90 **3,165** 条，最大 **11,154** 条
- 单请求正文峰值：中位 **1.7 KB**，p90 **3.2 KB**，最大 **13.8 KB**
- 单 run 正文 chunk 总数：中位 **172** 条，p90 **350** 条，最大 **1,242** 条

⇒ 现役 **10,000 条已经装不下最长的单个请求**（最大 11,154 条 > 10,000）；
⇒ 只要 **约 1,242 个「正文专用槽」**就能装下本机最大 run 的全部正文。
差别在于：现在这 1,242 条正文要和 5.4M 条 tool_call_delta 抢同一个 FIFO。

## 3. 解决方案对照表

「能解决到多少」都按同一把尺子：**在 run 末尾刷新时，653 个 run 里还有几个会丢正文、丢多少 KB**。

| # | 方案 | 能解决到多少（实测推算） | 改动面 | 代价 |
| --- | --- | --- | --- | --- |
| ① | **只靠环（现状）** | 29.7% 的 run 会丢；丢者中位 16.4%；合计 **81.7 KB**（长 run 94% 会丢） | 0 | 已是现状；环覆盖 ≈200 秒，且随并发摊薄（峰值 7 个并发 ⇒ 有效 ≈28 秒，推算） |
| ② | **环放大到 5 万** | 5.5% 的 run 会丢；只剩余 >10 分钟的 36 个；合计 **9.9 KB**；≤10 分钟**全免** | `DEFAULT_MAX_HISTORY` 常量 + hub 装配 2 处（`src/bootstrap.ts:1649`、`src/cli.ts:782` 传 `maxHistory`），共 ~5 行 | 内存 5×（环是常驻 RunEvent 对象，非磁盘）；**回填够不到**：单帧 `MAX_EVENTS=10_000` 是硬顶 + `MAX_BUDGET_BYTES=4 MiB`，客户端 `MAX_BACKFILL_PAGES=6` ⇒ 6 页上限，5 万只剩 1 页余量，工具结果大的 run 会被字节预算先咬住 ⇒ 必须同时抬高页数或改成按 `until_seq` 续拉到 `run.started` |
| ③ | **磁盘回填已完成部分 + 运行中正文靠环** | **≈100% 的正文零丢失**（实测：已落盘副本 = 流式正文 100.0%）；残缺只剩「在飞那一个请求」，中位 1.7 KB / 最大 13.8 KB | **小**：投影函数**已经存在** —— `packages/core/src/session/project-messages.ts` 的 `projectMessages` 就把 `llm.response → {role:'assistant', content}`（含 reasoning_content / tool_calls），agent 自己的上下文重建已在用。缺的只是让 `sessions.get` 对「未完成 run 的尾部」也走一次同一投影（现在它的注释明确写「不派生、不回填」，`gateway/methods/sessions.ts`）。不动事件模型、不动环 | 首包延迟 +1 次事件日志尾部读（只读 `seq > derived_upto_seq` 的增量，实测每 run 几 KB）；写盘量 **0 增加**（数据本来就在写）。**风险**：`keep_messages` 是 `sessions.get().messages` 的下标语义（`gateway/methods/agents.ts:59,293`）⇒ 派生会让下标漂移，必须「只追加尾部、前缀不变」或给派生部分单独字段 |
| ④ | **事件持久身份彻底解决**（chunk 有稳定 id + 可续传，或 chunk 直接持久化） | **100%**，含在飞窗口（刷新后续传，一个 chunk 都不丢） | 大：事件模型加身份/幂等键、chunk 落盘或 WAL、回填协议支持「按 seq 续传」、客户端去重 | 写盘量（推算）：全量 chunk 落盘 ≈ 760 万条 / ≈1.9 GB，是现有写量（16.6 万事件）的 **×46**；折中是**只给 `text_delta`/`reasoning_delta` 落盘并按 256 B 聚合** ⇒ 新增 ≈9.9 万条 ≈ 现有写量的 **0.6×**（见 ⑤） |
| ⑤ | **（补充，最便宜）按 kind 分槽 + chunk 聚合** | 正文只占 1.7%：给它独立 2,000 槽即可装下全库任一 run 的全部正文（最大 1,242） | 小-中：`event-buffer` 支持按 kind 分配额度（或给正文单独一条 ring）；`recordStreamChunk` 按 256 B / 50 ms 聚合 tool_call_delta | 内存 +~2,000 槽（≈0.5 MB）；聚合让 tool_call_delta 条数降 1–2 个数量级，**首包更快**（帧更少）；代价是流式观感变粗（256 B 一跳） |

**推荐组合**：`③ + ⑤`。③ 用已有的磁盘数据把「屏幕缺内容」根治（几乎无写盘成本），
⑤ 把环的 1.7% 需求从「和 60 倍噪声抢」变成「独占 2,000 槽」，顺手把首包延迟降下来。
②（5 万）单独上也能解决 94.5% 的 run，但**它是把 1.7% 的需求放大 5 倍去救，且回填链路还得跟着改**，
性价比不如 ⑤；若想「一行改动先止血」，②+抬高 `MAX_BACKFILL_PAGES` 是唯一当天能上的。

## 4. 磁盘回填（③）能覆盖哪些、覆盖不到哪些、为什么

**能覆盖**（实测：`llm.response` 副本 = 流式正文 100.0%）：

- 每个**已完成 LLM 请求**的完整正文 —— 整个 run 的最终回答文本都在这里，一个字节不少。
- 已落盘的工具结果（`tool.*`）、结构事件、`llm.stream.summary` 的段骨架（条数/字节/时间戳）。
- 刷新后连 `messages` 都不用等：`llm.response` 比 `saveSessionState` 早得多，run 中途就已写盘。

**覆盖不到**：

1. **正在流式输出的那一个请求**的部分正文。原因：`llm.stream.summary` 和 `llm.response` **都只在请求结束时写**
   （`flushStreamSegment` 在 request 末尾跑），在飞的那一段在磁盘上**根本不存在**。
   量级（实测）：≤ 单请求正文峰值 = 中位 1.7 KB / p90 3.2 KB / 最大 13.8 KB。
   这部分只能靠环 —— 而这恰好就是 §2.5 说的「环真正的刚性下限 ≈ 11,154 条」。
2. **reasoning 正文**（全库 23.86 MB，是正文的 16.4 倍）。原因：`llm.response` 只存最终 content，
   不含 reasoning_delta。要回填 reasoning 只能走 ④（chunk 落盘）或 ⑤（聚合后落盘）。
   影响面：只影响「回看思考过程」，不影响最终答案。
3. **tool_call_delta 的中间态**（参数逐 fragment 流出时的半成品）。同 1，请求没结束就不存在。

**为什么「已落盘但 screen 还是丢」**：`sessions.get` 返回的是 `SessionState.messages`，它只在
`run.completed`/checkpoint 落盘；`llm.response` 是另一条事实（事件日志）。`sessions.get` 的代码里
明确写着「消息身份…由 core 在落盘前盖上，本方法只读库里的那一份，**不派生、不回填**」
（`gateway/methods/sessions.ts`）。所以这不是缺数据，也不是缺投影函数 ——
`projectMessages`（`packages/core/src/session/project-messages.ts`）早就把 `llm.response`
映射成 assistant 正文了，**agent 自己的上下文重建一直在用它**，只是这条路径没接到「人看的那个视图」上。

## 5. 真机上取真样本的步骤

上面 §2.4 的 9 个样本是「进程被杀/休眠」留下的冻结快照，够真但不可控。要**主动**取一次：

1. 开一个会话，让 agent 跑一个长任务（比如写一个 800 行的文件，或让它连续输出 8 分钟）。
2. 等它跑到 5 分钟以上（环里已被挤出 1 万条），**在浏览器里按 F5**。
3. 刷新完成后立刻把该会话的落盘文件复制一份（别等 run 结束，否则正文会补齐、现象消失）：
   ```bash
   # Windows 落盘根目录在 C:/Users/<你>/.vessel/data/sessions，WSL 里对应 /mnt/c/...
   cp -r /mnt/c/Users/<你>/.vessel/data/sessions/<session_id> /tmp/sample-$(date +%s)
   ```
4. 用这份快照跑本脚本（它只读 ndjson，不需要节点依赖）：
   ```bash
   bun run scripts/measure-chunk-loss.ts --session=<session_id> --ring=10000,50000 --top=10
   ```
5. 同时记录屏幕现象（哪一段正文消失了、消失的是不是 run 的开头），与脚本给出的「丢失区间」对照。
   两者一致 ⇒ 模型正确；不一致 ⇒ 把屏幕截图和快照一起存下来，回来查。

也可以在真实网关上直接看：刷新后浏览器 Network 里 `replay` 帧的 `from_seq` 是否等于
`latest_seq - 10000 + 1` —— 是，则说明客户端确实顶到了环的下界（即 `refresh-gap-design.md`
§1.2 的确定性重算结论在真机上成立）。

## 6. 复现与局限

```bash
# 全量（217 个真实会话）
bun run scripts/measure-chunk-loss.ts --limit=400 --top=10 --ring=10000,50000,200000 \
  --progress=0.25,0.5,0.75,0.99

# 只看真·运行中样本
bun run scripts/measure-chunk-loss.ts --limit=400 --json | grep -i unfinished

# 换一个环容量档位 / 只看某个会话
bun run scripts/measure-chunk-loss.ts --ring=20000 --session=<id>
```

局限（都不影响上面的结论方向，只影响第三位有效数字）：

1. **chunk 本体不落盘** ⇒ 段内时间位置是均匀插值（推算）。只有被切断的那一段受影响，已给出精确/上界区间。
2. **闭环世界**：模型假设刷新时只有这一个 run 在烧环。实测并发峰值 **7**，真实场景按并发摊薄会更糟
   （有效覆盖 203 秒 ÷ 7 ≈ 28 秒，推算）⇒ **报告里所有丢失数字都是下界**。
3. `max(last_seq)` 是 chunk 条数的下界（run 末尾若有纯 tool_call_delta 不会进任何段）。
4. `MAX_BUDGET_BYTES = 4 MiB` 能否装下 1 万条 chunk：按 chunk 信封 ~250 B 推算 ≈ 2.5 MB，故 1 万条/帧可行；
   但工具结果大的 run 会先被字节预算咬住，5 万档必须实测验证（见 §3 ②的代价栏）。
5. 数据目录是活的，重跑时 run 数漂 ±几；百分比稳定。
