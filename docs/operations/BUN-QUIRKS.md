# Bun 运行时坑位

> 记录「运行时行为与预期不一致、且已经真的踩过」的坑。每条写清三件事：
> **现象 → 判据（看到什么就认定是它）→ 处置口径**。
> 崩溃类问题不在这里，见 [BUN-WIN32-SEGFAULT](BUN-WIN32-SEGFAULT.md)。

## 1. `AbortSignal.timeout()` 在「只被一次挂起的 await 等待」时不触发

**适用版本**：Bun 1.3.9 / win32-x64（其它版本未复现验证，别默认它已修）。

**现象**：把 `AbortSignal.timeout(ms)` 当作该处**唯一**的超时保证时，调用方不是「ms 之后
失败」，而是**永久挂起**。这类失败最阴的地方是它不报错：日志没有、异常没有，调用就那么悬着。

**判据**（两次对照得出的结论，缺一不可）：

1. 信号创建后交出去，调用方只 `await` 那一次挂起，进程里**没有别的定时器**在跑
   → abort 事件**从未触发**（实测挂死数十秒，直到被外部杀掉）。
2. 同样的信号，但进程里**另有一个 `setTimeout`** 在跑 → 大约 ms 之后正常触发。

也就是说：它不是稳定地「不工作」，而是**依赖别的东西替它把事件循环点亮**。这个隐含依赖不
该存在 —— 定时器是否兑现，不能取决于隔壁有没有人。

**影响面**：所有把 `AbortSignal.timeout` 当**唯一**超时手段的代码。实测走到「不触发」的
条件（一次挂起 await + 无其它定时器）恰好是后台任务、回调处理最常见的样子，所以不要用
「平时看着能跑」来排除。

**处置口径**：

- 需要真正的超时保证时，用**显式** `AbortController` + `setTimeout(() => controller.abort(), ms)`，
  并在 `finally` 里 `clearTimeout` —— 自己持有定时器，自己保证它被清理。
- 不要用 `AbortSignal.timeout` 作为唯一手段；若只是「顺手加一层」，也必须保证该处另有真实
  超时（例如底层 fetch 自身的连接超时）。
- **自查口径**（描述式，不指定工具）：找出全部 `AbortSignal.timeout` 用法，逐个判断
  「它是否是该处唯一的超时手段」且「它等待的是一次挂起的 await」；两个都成立就是隐患。

**已处置**：`packages/serve/src/auth/avatar.ts` 的头像代取超时（0.63）已改为显式
controller + `finally` 清理。发现这条的现场是：头像代取在「provider 永不响应」的桩上挂死，
而代码里明明写着 3s 超时 —— 也就是说如果没有这次对照，**「≤3s 超时」会是一条假承诺**。
