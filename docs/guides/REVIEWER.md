# 审查者须知

> **审查 PR / 合并前，必须先读完本文件列出的所有文档。按顺序读，读完一项自检一项。**
> 跳过任何一项 = 审查遗漏，放行的 bug/违规会在未来引爆。

## 为什么必须先读这些

审查不是"看一眼代码对不对"——是验证代码是否符合架构约束、工程规范、安全红线。Vessel 有 10 条硬性门禁 + CI 四件套 + 反面模式清单。不读这些就审查 = 用直觉代替门禁，失去合并前验证的意义。

核心信条：**合并前验证，不合并后修复。**

## 必读清单（按此顺序）

### 1. CLAUDE.md §9 合并审查规则

硬性门禁清单 + CI 四件套 + 阻断规则。

**自检**：你能背出 10 条硬性门禁吗？三条阻断规则是什么？

### 2. docs/specs/GIT-WORKFLOW.md（全篇）

分支模型、合并门禁（架构检查 + CI + 安全 + 回归确认）、审查流程、反面模式。

**自检**：§2.1 的 8 条架构检查清单是什么？§六的反面模式有哪些？

### 3. CLAUDE.md §4.1 代码设计纪律

审查时不仅看"功能对不对"，还要看"结构能不能扛住未来的变化"。读完 §4.1 理解设计判断的视角。

**自检**：你能区分"硬性门禁"（binary check）和"设计判断"（需要动用判断力）吗？

### 4. CLAUDE.md §5 能力分层 + §6 红线

确认新代码放对了层、没碰红线。

**自检**：core 只能因哪三种原因改？新增第二套扩展机制违哪条 ADR？

## 审查流程

```
1. 获取分支 diff
2. 对照 CLAUDE.md §9.1 硬性门禁逐条检查
3. 对照 CLAUDE.md §4.1 + GIT-WORKFLOW.md §六 做设计判断
4. 检查硬编码密钥（grep）
5. 确认 CI 状态（lint/typecheck/test/build）
6. 输出审查结论（通过/阻断 + 原因）
```

## 审查后自检

- [ ] 所有硬性门禁都过了？
- [ ] 设计判断有依据（不是"感觉不对"）？
- [ ] CI 四灯全绿？
- [ ] 无硬编码密钥？
- [ ] 没有"稍后修复"承诺？
