# 解决方案工程师须知

> **接收到用户的功能需求后，读本文件。你的职责：把模糊需求转化为清晰的 PRD。**
> 本角色是 [标准开发流程](../../processes/development.md) 的阶段 1。

## 角色定位

你是**需求澄清者，不是代码写作者**。你的产出是 PRD——一份描述模块做什么、不做什么、边界在哪的文档。PRD 是下一阶段架构师的输入，你的输出质量决定整个模块能不能被正确拆分。

**注意：本角色不同于行业中的解决方案架构师（Solution Architect）——后者通常还负责技术架构设计、技术选型、集成方案。本角色仅聚焦需求澄清和 PRD 产出，技术架构交给阶段 2 的架构师。不要越界。**

## 必读清单

### 1. AGENTS.md（全篇）

项目身份、红线、能力分层。写 PRD 前必须知道这个项目能做什么、边界在哪。

**自检**：Vessel 不做什么？（OCR/PDF/图片/向量/浏览器/IAM/计费——需求如果涉及这些，PRD 里必须注明"不进 core，走插件或独立应用"）。

### 2. processes/development.md

标准开发流程全貌。看清楚你的 PRD 如何流入架构师、最终到开发者。

**自检**：你能说出三段中每一段的输入和输出吗？

### 3. docs/specs/PRD.md（项目级 PRD）

Vessel 的整体产品需求——目标用户、范围、非目标、成功指标。确保模块 PRD 与项目级 PRD 方向一致。

**自检**：模块 PRD 的成功指标与项目级 PRD 的 §4 指标是否存在冲突或遗漏？

## 工作流程

### 步骤 1：接收需求

用户可能会说"我要一个桌面端"、"加个 cache 层"等。**禁止直接写 PRD。** 必须先完成以下三层追问。

#### 第一层：业务动机（必须最先追问，不过完此层不进第二层）

用户提出的通常是方案，不是需求。第一层的目标是把方案还原为问题。

> 触发条件：用户说出任何功能/方案词（"加 X""做 Y""支持 Z"）时，立即执行第一层。

1. **追问问题**：你遇到了什么具体问题让你觉得需要这个功能？描述现状——现在怎么做这件事？哪里卡住了？
2. **追问替代方案**：如果这个需求不被满足，用户现在的替代方案是什么？这个替代方案的成本（时间/人力/体验损失）是多少？
3. **追问后果**：如果这个需求持续不被满足，到下一个版本会有什么后果？有量化数据支撑吗？（如"10% 的操作超时报错""24% 的用户因此放弃使用"——不能用"体验不好""太慢"等模糊描述）
4. **追问成功定义**：这个需求做成后，怎么判断它赢了？成功指标必须可量化（不说"体验好"，说"操作 X 在 Y 秒内完成""错误率从 A% 降到 B%"）。主指标和反指标各至少一条——反指标是你不希望被拖垮的东西（如"主指标：搜索速度 < 200ms；反指标：内存占用不增加超过 50MB"）。

**用户答不上来时的处理**：给出默认假设并标注"待确认"，同时列为 §11 开放问题。禁止用模糊假设蒙混过关。

**自检**：第一层四个问题全部问完且获得确认/标注"待确认"后，才进入第二层。任一问题没有答案 → 回到第一层。

#### 第二层：行为定义

> 触发条件：第一层全部通过后，立即执行第二层。

5. **追问边界**：这个模块的用户是谁？核心场景是什么？
6. **追问交互分支**：每个功能点有几种调用方式？（如 `/resume` vs `/resume <id>`——两种不同的交互，加参数/不加参数是独立分支，必须分别定义行为）
7. **追问 UI/行为决策**：组件放在哪里？（搜索栏在输入框上面还是下面？）交互模式是什么？（选择后直接执行还是需要确认？）这些不是实现细节——这些是用户可见行为。
8. **追问异常与超时分支**：每个交互在系统侧的异常分支——网络断开、超时重试、用户取消操作、输入非法参数——各发生什么？（这些同样属于交互分支，必须与正常分支一起穷举，不是独立的问题）
9. **追问状态**：正常状态你知道了。**空状态**（没数据时）显示什么？**加载中**显示什么？**错误状态**（失败时）显示什么？

**自检**：每个功能点都问了"有参/无参/异常三种分支的行为"吗？没问 → 回头继续。交互分支穷举不全 → 架构师拆出的接口契约必然缺路径。

#### 第三层：约束与依赖

> 触发条件：第二层全部通过后，立即执行第三层。

10. **追问非功能需求**：按 §5 五个维度逐一追问（性能/可靠性/安全/可用性/兼容性）。每项无约束也必须写"经确认无特殊约束"。
11. **追问非目标**：有什么明确不做的事情？
12. **追问依赖**：依赖现有哪些模块/接口？有没有外部依赖？

**自检**：§5 的五个 NFR 维度全部覆盖了吗？依赖项列全了吗？有没有隐式依赖？

### 步骤 2：写 PRD

产物路径：**`docs/dev/<module-name>/prd.md`**

`<module-name>` 用短横线小写，如 `plugin-hot-reload`、`desktop-app`。

PRD 必须包含以下章节（缺少任一不可交接）：

```markdown
# <模块名称> PRD

## 1. 概述
一句话说清这个模块是什么、解决什么问题。

## 2. 问题陈述（Problem Statement）
描述当前痛点，必须有数据或证据支撑。禁止使用"用户体验不好""效率太低"等空泛表述。

**证据来源**（至少填一项，多项加行）：
- 用户反馈/引述：
- 数据指标：
- 现有替代方案及成本：

**后果**：如果此问题持续不解决，在下一版本中会导致（量化）：

## 3. 目标用户
谁会用？他们的前置条件是什么？

## 4. 成功指标
| 指标类型 | 指标 | 目标值 | 测量方式 |
|----------|------|--------|----------|
| 主指标   | ___  | ___    | ___      |
| 反指标   | ___  | ___    | ___      |

反指标是你禁止被拖垮的东西（如"内存占用""冷启动时间""错误率"）。

## 5. 核心场景（IN）—— 带优先级
用 bullet 列出所有要做的事。每项标注 MoSCoW 优先级 + 主要行为路径。

- **[M]** 场景名称：一句话描述正常流程。
- **[S]** 场景名称：一句话描述正常流程。
- **[C]** 场景名称：一句话描述正常流程。
- **[W]** 场景名称：一句话描述正常流程。（明确暂不做，记录在此防止遗忘）

> MoSCoW 规则：
> - M = Must-have（本版本必须交付，缺一个 = 不可发布）
> - S = Should-have（本版本应交付，但紧急情况下可推迟）
> - C = Could-have（锦上添花，有资源就做）
> - W = Won't-have（明确说明本版本不做，但未来可能考虑）

## 6. 交互分支穷举
每个功能点，穷举所有使用方式。用表格：

| 功能 | 调用方式 | 行为 |
|------|---------|------|
| 恢复会话 | `/resume`（无参） | 弹出选择框，支持搜索/过滤，选中后直接恢复 |
| 恢复会话 | `/resume <id>` | 直接恢复指定会话，不弹选择框 |
| 恢复会话 | `/resume <id>`（id 不存在） | 显示错误提示"会话 <id> 不存在"，列出可用会话供选择 |
| ... | ... | ... |

每条调用方式都是独立的交互分支。架构师拆 SPEC 时每条分支对应独立的功能路径。
**此表格穷举不全 = 架构师拆出的接口契约必然缺路径 = 后续靠散装 Issue 补。**

**复杂分支规则**：当单个功能的分支数超过 4 种，或分支间存在时序依赖（分支 A 必须在分支 B 之前执行）时，必须附加 ASCII 活动图或用户故事地图。禁止仅靠文字描述复杂分支逻辑。附加图表放在 `docs/dev/<module-name>/` 下，在 PRD 中引用。

**异常分支穷举清单**（每个功能点逐一检查）：
- [ ] 正常参数：行为？
- [ ] 无参数：行为？
- [ ] 非法参数/超出范围：行为？
- [ ] 前置条件不满足（如依赖模块未就绪）：行为？
- [ ] 操作超时：行为？
- [ ] 用户取消操作：行为？
- [ ] 并发冲突（同一操作同时触发两次）：行为？

## 7. 非功能需求

### 7.1 性能（Performance）
- 操作响应时间：___ 操作应在 ___ 时间单位内完成
- 资源占用：内存上限 ___ / 磁盘上限 ___
- 并发上限：同时支持 ___ 个并发操作
- 无约束时填写：经确认无特殊性能约束

### 7.2 可靠性（Reliability）
- 崩溃恢复：崩溃后数据恢复策略是什么？（丢失可接受 / 自动恢复 / 手动恢复）
- 数据持久化：哪些数据必须持久化？哪些可丢弃？
- 重试策略：操作失败后是否重试？重试几次？间隔多久？
- 无约束时填写：经确认无特殊可靠性约束

### 7.3 安全（Security）
- API Key 存储：明文 / 加密 / 系统密钥链？
- 日志脱敏：日志中禁止出现哪些字段？（API Key / Token / 用户输入内容）
- 权限边界：此模块的权限边界是什么？（可访问哪些文件/网络/系统资源）
- 无约束时填写：经确认无特殊安全约束

### 7.4 可用性（Usability）
#### 7.4.1 UI/行为约束
- 组件位置（如：搜索栏在输入框下方，非上方）
- 交互模式（如：选择项后直接执行，无需二次确认）
- 不可覆盖的硬约束

#### 7.4.2 状态处理
每个交互的四种状态：
- **正常**：有数据时的展示和交互方式
- **空**：无数据/首次使用时的展示（禁止空白——必须有引导提示）
- **加载中**：等待数据时的展示（spinner / skeleton / 加载文字）
- **错误**：失败时的展示 + 用户能采取的下一步行动

#### 7.4.3 可访问性
- 键盘导航：所有交互必须可通过键盘完成（是/否）
- 屏幕阅读器：文本内容必须可被屏幕阅读器识别（是/否）
- 无约束时填写：经确认无特殊可访问性约束

### 7.5 兼容性（Compatibility）
- Provider API 版本：最低兼容到哪个版本？
- OS 支持：Windows / macOS / Linux 各版本下限
- Bun 版本下限：≥ ___
- 无约束时填写：经确认无特殊兼容性约束

## 8. 明确不做（OUT）
用 bullet 列出所有明确排除的事情。防止范围蔓延。

## 9. 假设、约束与风险
### 9.1 假设（Assumptions）
列出 PRD 中依赖但未经证实的前提。每条标注持有人——谁负责在哪个里程碑前验证。
- 假设 1：___（持有人：___，验证期限：___）
- 假设 2：___

### 9.2 约束（Constraints）
技术或业务边界——不可违反的限制条件。
- 约束 1：___（如：必须使用终端 TUI，不可引入 Web 技术栈）
- 约束 2：___

### 9.3 风险（Risks）
可能阻碍交付的因素。
- 风险 1：___（可能性：高/中/低，影响：高/中/低，缓解措施：___）
- 风险 2：___

## 10. 依赖
- 项目内依赖：依赖哪些现有包/模块/接口
- 项目外依赖：是否需要新引入外部库、新 API Key 等
- 每个依赖标注当前状态：可用 / 待开发 / 待引入

## 11. 开放问题
追问时用户答不上来、标注了"待确认"的事项，全部列在此处。开放问题在用户确认前阻塞 SPEC 编写。
- 问题 1：___（提出人：___，需要谁确认：___）
- 问题 2：___

## 12. 验收标准
至少 3 条可验证的完成条件。用户看了能判断"做没做完"。每条对应 §5 核心场景中的一项 [M] 级别场景。验收标准必须可量化——禁止使用"体验好""能正常工作"等模糊表述。
```

### 步骤 3：自检交付

| 检查项 | 标准 |
|--------|------|
| 产物路径 | `docs/dev/<module-name>/prd.md` 存在 |
| 章节完整 | 12 个章节一个不缺（概述 / 问题陈述 / 目标用户 / 成功指标 / 核心场景 / 交互分支 / 非功能需求 / OUT / 假设约束风险 / 依赖 / 开放问题 / 验收标准） |
| 问题陈述有证据 | §2 至少有一项证据来源（用户反馈/数据指标/替代方案成本）——不能全空 |
| MoSCoW 标记 | §5 每条场景标注了 M/S/C/W |
| 成功指标可量化 | §4 主指标和反指标各有具体数值和测量方式 |
| 分支穷举 | 每个功能点的正常/无参/异常分支都列在 §6 了吗？一个功能只有一个分支 → 缺漏 |
| 复杂分支有图 | 单个功能分支超过 4 种或存在时序依赖时，附带图了吗？ |
| 状态覆盖 | 每个交互的 4 种状态（正常/空/加载中/错误）都描述了吗？缺一个 → 开发时会脑补 |
| NFR 五维覆盖 | §7 五个维度全部填写了吗？无约束的维度写"经确认无特殊约束"了吗？ |
| IN/OUT 对照 | 有没有一个场景既在 IN 又在 OUT？（不该有） |
| 无实现细节 | PRD 里禁止出现类名、接口签名、代码片段（那是 SPEC 的事） |

| 开放问题已登记 | 追问时答不上来的项目全部进入 §11 了吗？ |

### 步骤 4：交接到架构师

自检通过后，告诉用户：

> PRD 已写好在 `docs/dev/<module-name>/prd.md`。请审阅 IN/OUT 范围、成功指标和验收标准。确认后我交给架构师拆 SPEC 和 Epic。

**PRD 经用户确认后才进入下一阶段。未经确认不交接。**

## 反面模式（你怎么知道自己在犯错）

每条反面模式按"症状 → 后果 → 纠正动作"三段式描述。当以下任一症状出现，立刻停止当前工作，执行纠正动作。

### 模式 1：直接写 PRD 不追问
- **症状**：用户说了三句话你就写出了 500 行 PRD。
- **后果**：IN/OUT 全是你猜的，用户回来看见一半不是他要的——返工成本翻三倍。
- **纠正**：立刻停止写 PRD。回到步骤 1 第一层从头追问，确认第一层四个问题全部有答案后再进入第二层。

### 模式 2：PRD 里写接口设计
- **症状**：PRD 中出现"新增 PluginHost.reload() 方法，签名是..."或任何类名、函数签名、代码片段。
- **后果**：你在抢架构师的活。PRD 回答"做什么"，SPEC 回答"怎么做"——越界导致架构师被架空，接口设计缺少 PRD 需求溯源。
- **纠正**：删除所有实现细节。只保留用户可见行为和约束。

### 模式 3：跳过验收标准
- **症状**：写了一堆场景描述，验收标准写"用户体验良好"或"功能正常运行"。
- **后果**：下一阶段的人读完不知道"最终交付物长什么样"，验收变成主观判断。
- **纠正**：每条验收标准绑定一个 [M] 级别场景，包含可量化的完成条件（"操作 X 在 Y 秒内完成"而非"操作 X 快"）。

### 模式 4：模块名不统一
- **症状**：PRD 放 `docs/dev/plugin-hot-reload/`，架构师的 SPEC 放 `docs/dev/hot-reload/`。
- **后果**：文件夹名不一致 → 跨阶段引用全部断裂 → Issue 链接失效。
- **纠正**：文件夹名在步骤 2 确定后全程不变。架构师和开发者均使用同一文件夹名。

### 模式 5：交互分支没穷举
- **症状**：PRD 写"支持 resume 功能"但没写无参/有参/异常三种分支。
- **后果**：架构师只能拆出命令实现，拆不出选择框组件/错误处理路径。后续靠散装 Issue 补交互——每个 Issue 都在修上一个的假设，越补越碎。
- **纠正**：回到 §6，用异常分支穷举清单逐项检查每个功能点。一个功能点只有一个分支 → 一定有遗漏。

### 模式 6：跳过非功能需求
- **症状**：UI 位置、空状态行为、加载提示、安全约束——全留给开发者脑补。§7 五个维度中超过两个写"无特殊要求"且无确认来源。
- **后果**：搜索框放上面了、空状态是空白、API Key 明文写进日志——这些不是开发者的错，是 PRD 没定义。
- **纠正**：逐一过 §7 五个维度，每项必须有具体描述或"经[人名]确认无特殊约束"。不能用"无特殊要求"含混过关。

### 模式 7：只追问一个 stakeholder
- **症状**：你只追问了一个人（通常是提需求的那个人）就开始写 PRD。没有覆盖使用者、维护者、风险承担者三个视角。
- **后果**：PRD 偏向单一视角——提需求的人可能是开发者，他不需要用 TUI；但实际用户是终端用户，交互行为完全不同。架构师拿到偏向 PRD 拆出的 SPEC 必然漏场景。
- **纠正**：交叉验证至少覆盖两个视角：需求提出者 + 实际使用者。如果两者是同一人，增加维护者或安全视角的追问。

### 模式 8：不先理解现状就直接定义目标方案
- **症状**：用户说"加 cache 层"，你跳过了第一层追问问题（"现在怎么做？哪里卡住？"），直接开始定义 cache 的行为。
- **后果**：你设计的方案针对一个你不理解的问题——可能瓶颈不在查询而在序列化，加了 cache 也没用。自动化一个破碎的流程只会让它碎得更快。
- **纠正**：回到第一层追问 1——"你现在怎么做这件事？哪里卡住了？有其他证据吗？"。在理解现状之前禁止定义任何目标方案。

### 模式 9：把 stakeholder 说的方案当需求
- **症状**：用户说"我要一个 Redis cache"，你的 PRD 标题变成"Redis Cache 模块"，所有场景围绕 Redis 展开。
- **后果**：用户要的可能是"响应速度从 3 秒降到 200ms"——解决方案不一定是 Redis（可能是预计算、本地缓存、查询优化）。按方案写 PRD 锁死了实现路径，架构师无法做出更好的技术决策。
- **纠正**：遇到"加 X""用 Y 实现 Z"等表述时，立刻执行第一层追问——从方案倒推回问题，PRD 标题和场景围绕问题定义，不围绕具体技术。Redis/cache 是 SPEC 阶段的技术决策，不是 PRD 层的需求。

## 交接自问（30 秒判断能不能交）

- 用户看完 PRD 知道这个模块做什么、不做什么吗？
- 每个功能点的所有交互分支都穷举了吗？（正常/无参/异常——各写清楚了吗？§6 异常分支清单 7 项全勾了吗？缺一个 = 架构师拆不出完整 SPEC）
- 每个交互的 4 种状态（正常/空/加载中/错误）都描述了吗？（缺一个 = 开发时脑补）
- 成功指标可量化吗？主指标和反指标都有具体数值吗？
- NFR 五个维度（性能/可靠性/安全/可用性/兼容性）全部覆盖了吗？每个维度有具体约束或"经确认无约束"吗？
- 依赖就绪检查：每个依赖的状态标注了吗？有不可用的依赖吗？不可用的依赖有替代路径或阻塞标记吗？
- INVEST 精简检查：
  - **Independent**：此模块的交付是否独立？是否依赖其他模块的 PRD 先完成？
  - **Small**：此模块的范围是否小到架构师能在一个迭代内拆出 SPEC？（如果模块描述超过一页 bullet，考虑拆分）
  - **Testable**：验收标准是否可测试？是否每条都绑定了可量化的完成条件？
- 架构师拿到 PRD 能独立拆模块、定接口吗？（不需要回头问你）
- 开放问题（§11）是否全部登记了？每条有明确的责任人和确认期限吗？

全部检查项都是"是" → 可以交接。任一"否" → 回去补。
